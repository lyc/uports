# uports Wrapper And Group Architecture Proposal

## Purpose

This document proposes a refined group design for uports that preserves and
combines the capabilities already present in:

```text
make/uports/                 reusable ports framework and built-in ports
make/uports/Tools/tools.mk   project-side discovery, planning, and dispatch
feeds/                       external or project-specific ports and policy
top-level Makefile           project configuration
```

The proposal is compatibility-first. It does not move project topology into
individual port Makefiles, and it does not remove existing targets such as:

```text
compiler@clisp.build
host@cmake.install
textproc.build
ports.package
```

The main change is conceptual and structural:

> A build instance is a resolved port variant, built under a group profile,
> for a lifecycle target.

Port identity, collection origin, group profile, and variant should be
represented separately even though the user-facing target syntax may combine
them.

## Architecture Boundaries

The system has four distinct layers.

### Port Layer

A port is identified by:

```text
category/port
```

Examples:

```text
lang/clisp
devel/cmake
textproc/expat2
```

A port Makefile declares package behavior:

- source and version;
- dependencies;
- configure and build options;
- patches;
- staging and packaging behavior;
- package manifests.

A port should not need to know whether it came from built-in uports or a feed,
which project selected it, or which project group will build it.

### Port-Collection Layer

Port definitions can exist in multiple collection roots.

The current roots are:

```text
make/uports/<category>/<port>
$(FEEDS)/<category>/<port>
```

`FEEDS` may point inside or outside the current repository.

The current resolver gives a feed port precedence over a built-in port with the
same `category/port`. The resulting package set is therefore a merged logical
port collection, not two unrelated collections.

### Wrapper Layer

`make/uports/Tools/tools.mk` is the project-side wrapper. It currently:

- discovers built-in and feed ports;
- applies feed-over-built-in override precedence;
- validates `PORTS_LISTS`;
- assigns groups;
- calculates group and port metadata;
- composes per-instance environments;
- generates port, category, group, and global targets;
- chooses the physical source directory for a resolved port;
- exports selected host tools;
- dispatches lifecycle targets to the real port Makefile;
- reports package and build status.

This is the correct ownership layer for project group topology.

### Execution Layer

`make/uports/Mk/linux.port.mk` and related files implement one port's lifecycle:

```text
fetch -> extract -> patch -> configure -> build -> stage -> package -> install
```

The execution layer consumes the environment supplied by the wrapper. It
should not need to understand the complete project group graph.

## Current Group Model

A group is a build and installation context, not a package category and not a
port collection.

The current internal and target-oriented representation is:

```text
group@category/port
```

Examples:

```text
bs@devel/autoconf-2.72
host@devel/cmake
textproc@textproc/expat2
compiler@lang/clisp
```

The current special groups are declared through:

```make
special_groups_all += bs host textproc
```

Membership uses:

```make
bs_lists       = ...
host_lists     = ...
textproc_lists = ...
```

The wrapper defines:

```make
PORTS_GROUP_DEFAULT = compiler
```

Ports without an explicit special-group assignment enter `compiler`.

The effective groups are:

```text
bs
host
textproc
compiler
```

## Capabilities That Must Be Preserved

Any redesign must retain the following existing behavior.

### Collection Override

If both roots contain:

```text
make/uports/lang/example
feeds/lang/example
```

the feed version is selected.

Group membership applies to the resolved logical port `lang/example`, not
separately to both physical directories.

### External Feeds

`FEEDS` is a path supplied by the project. It may refer to an external
collection. The wrapper must not assume that feeds live below the project root.

### Port Selection

`PORTS_LISTS` can restrict the active port set and may include explicit grouped
entries.

Unknown selected packages currently fail early. That validation must remain.

### Default And Explicit Groups

Special membership is applied first. Ports without an explicit group receive
`PORTS_GROUP_DEFAULT`.

### Multiple Build Instances

A logical port may be built in more than one group. Each group build has a
separate environment, work suffix, destination, and target.

A logical port may also be built more than once within the same group when it
declares variants. Variants represent configurations, ABIs, or bootstrap
stages of the same port definition. Each selected group-port-variant
combination must have a separate work identity, package identity, and target.

### Environment Overlays

The current environment composition supports:

```text
PORTS_ENVS
PORTS_<group>_ENVS
PORTS_<port>_EXTRA_ENVS
PORTS_<group>_<port>_EXTRA_ENVS
PORTS_<group>_<port>_EXCLUDE_ENVS
TYPE_SUFFIX
```

This is an important capability. The redesign should normalize it, not replace
it with a less expressive model.

### Work And Type Suffixes

Groups derive suffixes used for work directories and package/build identity.
This permits the same port to be built in multiple contexts without sharing
state incorrectly.

### Host Tool Export

`USE_HOSTTOOLS` selects a group whose installed tools are exported to the
wrapper process. Current examples include:

```text
PATH
PKG_CONFIG
CMAKE_BIN
```

The proposal must generalize this behavior rather than remove it.

### Generated Target Families

The wrapper generates:

```text
group@port.suffix
port.suffix
category.suffix
group.suffix
ports.suffix
```

These target forms are useful and should remain compatible.

## Problems To Solve

### Source And Group Concepts Are Easy To Conflate

A feed is a source of port definitions. A group is a build context. They are
orthogonal.

For example:

```text
feeds/lang/clisp
```

may resolve the logical port `lang/clisp`, while:

```text
compiler@lang/clisp
```

describes where and how that resolved port is built.

### Group Definition Is Distributed

Membership, destination, prefix, suffix, environment, host-tool behavior, and
dependency intent are spread across multiple variables and files.

### Encoded Strings Carry Too Much State

`group@category/port` is appropriate as a target name, but it should not be the
only normalized representation of:

- group;
- logical port identity;
- physical origin;
- environment;
- work identity.

### Default Assignment Is Invisible

New ports silently enter the default group. This is convenient during
development but risky for CI and release builds.

### Group Relationships Are Implicit

The current system suggests relationships such as:

```text
bs provides bootstrap tools
host provides executable host tools
compiler consumes host tools
textproc provides libraries
```

but there is no explicit graph or validation.

### Short Port Targets Can Be Ambiguous

The wrapper often generates aliases from the final port name, such as:

```text
clisp.build
```

The canonical identity is `lang/clisp`. Short aliases should only be generated
when the name is unique across the active collection.

### Eager Target Generation Does Not Scale Well

The original `tools.mk` used nested `foreach`, `call`, and `eval` expressions
to materialize most wrapper records and target families while make parsed the
file. `eval` is not inherently wrong, but each use expands its argument and
then asks make to parse the generated makefile text again.

The larger cost comes from eagerly generating the complete target matrix even
when the requested command needs only one port or one diagnostic:

```text
build instances × lifecycle suffixes
+ default and short aliases × lifecycle suffixes
+ categories × lifecycle suffixes
+ groups × lifecycle suffixes
+ global and diagnostic targets
```

On June 19, 2026, with GNU Make 4.4.1 and the current example configuration,
the active plan contained:

```text
42 logical ports
42 build instances
4 groups
9 categories
17 lifecycle suffixes
714 canonical instance lifecycle targets
```

A no-op parse of the complete configuration took approximately 0.16 to 0.18
seconds on the development machine. Selecting only `lang/cpython` reduced it
to approximately 0.09 seconds. A make database inspection reported roughly
1,873 rule lines and 1,673 phony target names for the complete configuration.
These measurements are small enough for the current tree, but they demonstrate
that parse cost and rule count grow with the size of the generated matrix.

The separate optimization task in `docs/00.2-TOOLS.MK.md` completed on June
20, 2026. The current wrapper now uses normalized immediate records and shared
dispatch for canonical, alias, diagnostic, and aggregate target families.

On the same development host, the final full-plan measurements are:

```text
median parse time:             approximately 0.10 seconds
make database rule lines:      378
phony target names:            4
make database size:            approximately 439 KiB
regression assertions:         88
```

The 200-port synthetic plan improved from approximately 0.99 seconds and 7,768
rule lines to approximately 0.07 seconds and 408 rule lines.

Variants make this more important. The principal term becomes:

```text
groups × ports × selected variants × lifecycle suffixes
```

Future variant work must continue treating parse-time performance and
make-database size as architectural constraints. The wrapper now reserves
`variant=default`, supports collision-free nondefault instance keys, and
creates no records for undeclared or unselected variants. Actual variant
selection remains part of the formal group enhancement and must satisfy the
performance budget recorded in `docs/00.2-TOOLS.MK.md`.

## Refined Data Model

The wrapper should normalize five record types.

### Collection

A collection describes a physical root containing ports:

```text
collection id
root path
precedence
kind
optional policy file
```

Example:

```make
PORT_COLLECTIONS = uports project

PORT_COLLECTION_uports_ROOT = $(portdir)
PORT_COLLECTION_uports_KIND = builtin

PORT_COLLECTION_project_ROOT = $(FEEDS)
PORT_COLLECTION_project_KIND = feed
```

Collections listed later have higher override precedence.

### Resolved Port

A resolved port describes the selected definition for a logical identity:

```text
id       = lang/clisp
origin   = project
root     = /path/to/feeds
portdir  = /path/to/feeds/lang/clisp
shadowed = uports, if a lower-precedence definition exists
```

The resolver must produce one active definition for each `category/port`.

### Group Profile

A group profile describes a build context:

```text
name
role
destination
prefix
environment
work suffix
tool exports
group relationships
membership rules
```

### Variant

A variant describes one repeatable configuration of a logical port:

```text
name
environment
work suffix
package suffix
plist selection
variant relationships
```

Examples:

```text
devel/libffi:shared
devel/libffi:static
lang/gcc:core1
lang/gcc:core2
lang/gcc:final
```

Variants are declared by the port because the port owns the supported build
configurations and their package-specific behavior. The project selects which
variants are required in each group.

`default` is the implicit variant for ports that do not declare variants. An
unqualified existing build instance is therefore normalized internally as:

```text
group + resolved port + default
```

Variants are not collections or groups:

- a collection selects the physical port definition;
- a group selects the build and installation context;
- a variant selects one configuration, ABI, or bootstrap stage of that port.

Different upstream versions should normally remain different logical ports,
such as `lang/gcc-14` and `lang/gcc-15`. Variants should represent builds of
one selected port version, such as `core1` and `final`.

### Build Instance

A build instance is:

```text
group + resolved port + variant
```

For example:

```text
group    = compiler
port     = lang/clisp
variant  = default
origin   = project
portdir  = /path/to/feeds/lang/clisp
work     = work.compiler
destdir  = /path/to/local/compiler
prefix   = /usr/local
```

Or:

```text
group    = cross-aarch64
port     = lang/gcc-14
variant  = core1
origin   = project
portdir  = /path/to/feeds/lang/gcc-14
work     = work.cross-aarch64.core1
destdir  = /path/to/local/cross-aarch64
prefix   = /usr
```

Lifecycle targets are operations on this instance:

```text
compiler@lang/clisp.configure
compiler@lang/clisp.build
compiler@lang/clisp.install
cross-aarch64@lang/gcc-14:core1.build
```

The existing shorter form may remain:

```text
compiler@clisp.build
```

but only as an unambiguous alias.

The `:default` qualifier should be omitted from compatible targets.

## Proposed Public Configuration

The public interface should follow existing make naming conventions and avoid
requiring dot-heavy variable parsing.

### Collections

```make
PORT_COLLECTIONS = uports project

PORT_COLLECTION_uports_ROOT = $(portdir)
PORT_COLLECTION_uports_KIND = builtin

PORT_COLLECTION_project_ROOT = $(FEEDS)
PORT_COLLECTION_project_KIND = feed
```

Compatibility mapping:

```make
FEEDS=/path/to/feed
```

becomes an implicit high-priority `project` collection.

Future projects may add more than one feed:

```make
PORT_COLLECTIONS += vendor product

PORT_COLLECTION_vendor_ROOT  = /opt/vendor/uports-feed
PORT_COLLECTION_product_ROOT = $(topdir)/feeds
```

The order is the override order:

```text
uports < vendor < product
```

### Groups

```make
PORT_GROUPS += bs host compiler textproc
PORT_GROUP_DEFAULT = compiler
```

Compatibility mapping:

```make
special_groups_all
PORTS_GROUP_DEFAULT
```

remains accepted.

### Membership

```make
PORT_GROUP_bs_PORTS = \
    devel/m4 \
    devel/autoconf-2.72 \
    devel/autoconf-switch \
    devel/automake-1.17 \
    devel/libtool

PORT_GROUP_host_PORTS = \
    devel/pkg-config \
    devel/cmake

PORT_GROUP_textproc_PORTS = \
    textproc/ezxml \
    textproc/expat2 \
    textproc/json-c \
    textproc/libcsv \
    devel/pcre2 \
    net/libyang2
```

Compatibility mapping:

```make
bs_lists
host_lists
textproc_lists
```

is normalized into the new variables.

Membership always refers to logical `category/port` identity. It must not refer
to a physical feed path.

### Group Profile

```make
PORT_GROUP_compiler_ROLE    = target-runtime
PORT_GROUP_compiler_DESTDIR = $(DESTDIR)/compiler
PORT_GROUP_compiler_PREFIX  = $(PREFIX)
PORT_GROUP_compiler_SUFFIX  = compiler
```

Raw environment values remain available:

```make
PORT_GROUP_compiler_ENVS += \
    USE_ALTERNATIVE=yes \
    ALTERNATIVE_WRKDIR=$(DESTDIR)/compiler/src
```

This maps naturally to existing `PORTS_compiler_ENVS`.

### Per-Port Overrides

Keep the current overlay capability with clearer canonical names:

```make
PORT_lang_clisp_ENVS += WITH_READLINE=yes

PORT_INSTANCE_compiler_lang_clisp_ENVS += WITH_DOCUMENT=no

PORT_INSTANCE_compiler_lang_clisp_EXCLUDE_ENVS += USE_SCM=%

PORT_INSTANCE_compiler_devel_libffi_static_ENVS += \
    WITH_SHARED=no

PORT_INSTANCE_compiler_devel_libffi_static_EXCLUDE_ENVS += \
    WITH_SHARED=%
```

Because `/` and `-` are awkward in generated make variable names, the
framework should provide a documented encoding function. The compatibility
layer continues to accept:

```make
PORTS_clisp_EXTRA_ENVS
PORTS_compiler_clisp_EXTRA_ENVS
PORTS_compiler_clisp_EXCLUDE_ENVS
```

### Variants

A port declares the variants it supports:

```make
PORT_VARIANTS = shared static
PORT_VARIANT_DEFAULT = shared

PORT_VARIANT_shared_ENVS += \
    CONFIGURE_ARGS+=--enable-shared \
    CONFIGURE_ARGS+=--disable-static

PORT_VARIANT_static_ENVS += \
    CONFIGURE_ARGS+=--disable-shared \
    CONFIGURE_ARGS+=--enable-static
```

The project selects variants for a group-port instance:

```make
PORT_INSTANCE_compiler_devel_libffi_VARIANTS = shared static
PORT_INSTANCE_python_devel_libffi_VARIANTS   = shared
```

Variant-qualified instance overlays use the same encoded group and port
identity followed by the variant name:

```make
PORT_INSTANCE_compiler_devel_libffi_static_ENVS += WITH_DEBUG=no
```

This expands into:

```text
compiler@devel/libffi:shared
compiler@devel/libffi:static
python@devel/libffi:shared
```

Group membership alone must not select every declared variant. Selection is
explicit when more than the default variant is required.

Variant-specific package names, plist files, and install behavior remain owned
by the port. The framework must ensure that selected variants have distinct
work and package identities.

## Environment Composition

The effective environment for one build instance should be assembled in a
defined order:

1. framework defaults;
2. project-wide `PORTS_ENVS`;
3. inherited group-profile values;
4. group `ENVS`;
5. logical-port `ENVS`;
6. variant `ENVS`;
7. group-and-port instance `ENVS`;
8. group-port-variant instance `ENVS`;
9. command-line overrides;
10. derived work and type suffixes.

Exclusions are applied to inherited values before the instance additions.
Variant-qualified exclusions follow the same rule.

The framework should expose the result through:

```sh
make port-env GROUP=compiler PORT=lang/clisp
make port-env GROUP=compiler PORT=devel/libffi VARIANT=static
```

The output should identify the source of each value:

```text
DESTDIR=/.../local/compiler          group profile
PREFIX=/usr/local                    wrapper default
WITH_DOCUMENT=no                     instance override
TYPE_SUFFIX=.compiler                derived
```

For the implicit `default` variant, the effective environment and suffixes
must remain compatible with the current group-port result.

## Group Relationships

Group relationships should be explicit, but they must not replace per-port
dependencies.

Variant and bootstrap-stage relationships are more specific than group
relationships. For example, a cross-toolchain may require:

```text
binutils
gcc:core1
libc:headers-startfiles
gcc:core2
libc:full
gcc:final
```

That ordering belongs to build-instance dependencies. It should not be modeled
as separate collections, and stages should not become separate groups unless
they genuinely use different build or installation contexts.

### Tool Providers

Generalize `USE_HOSTTOOLS`:

```make
PORT_TOOL_GROUPS = host bs
```

Groups can export tools:

```make
PORT_GROUP_host_EXPORTS = PATH PKG_CONFIG CMAKE_BIN
```

The wrapper composes tool search order from `PORT_TOOL_GROUPS`.

For compatibility:

```make
USE_HOSTTOOLS=host
```

maps to:

```make
PORT_TOOL_GROUPS=host
```

### Build Relationships

Start with one simple graph:

```make
PORT_GROUP_host_BUILD_USES     = bs
PORT_GROUP_compiler_BUILD_USES = bs host
PORT_GROUP_textproc_BUILD_USES = host
```

This graph establishes group-wide prerequisite ordering and environment
visibility.

It does not imply that every package in `compiler` depends on every package in
`host`. Exact package dependencies remain in:

```text
BUILD_DEPENDS
LIB_DEPENDS
RUN_DEPENDS
```

### Future Typed Relationships

After build ordering is stable, add:

```make
PORT_GROUP_compiler_LINK_USES  = textproc
PORT_GROUP_compiler_RUN_USES   = compiler textproc
PORT_GROUP_compiler_IMAGE_USES = compiler
```

Meanings:

```text
BUILD_USES
  Groups providing commands used while building.

LINK_USES
  Groups whose headers and libraries may be used for linking.

RUN_USES
  Groups visible to installed runtime software.

IMAGE_USES
  Groups whose packages are eligible for a produced image.
```

These relationships define visibility and ordering. They do not synthesize
package dependencies automatically.

## To Be Discussed: System-Provided Dependencies

Status: **To Be Discussed**

Some native host build instances can use a dependency supplied by the host
operating system instead of building the corresponding uports package.

The motivating example is:

```text
host@lang/chezscheme
  requires libffi
  macOS Command Line Tools provide ffi/ffi.h and libffi
```

On macOS, the active SDK may provide:

```text
$(xcrun --show-sdk-path)/usr/include/ffi/ffi.h
$(xcrun --show-sdk-path)/usr/lib/libffi.tbd
runtime install name: /usr/lib/libffi.dylib
```

For a native host-only ChezScheme build, using that provider may be preferable
to building `host@devel/libffi`. The same assumption is not necessarily valid
for a `compiler`, cross, relocatable, or self-contained runtime group.

The dependency itself should remain declared by the port:

```make
LIB_DEPENDS += libffi:devel/libffi
```

The unresolved design question is whether project or group policy may select a
different provider for that logical requirement:

```text
consumer       = host@lang/chezscheme
requirement    = devel/libffi
provider kind  = system
provider       = macos-sdk
```

This follows the general idea of systems such as Yocto
`ASSUME_PROVIDED`: the dependency remains known, but the planner does not build
its recipe when an explicitly selected external provider satisfies it.

### Possible Configuration Direction

One possible spelling, not yet accepted, is:

```make
PORT_GROUP_host_ASSUME_PROVIDED += devel/libffi
```

or a more explicit provider mapping:

```make
PORT_GROUP_host_PROVIDER_devel_libffi = system:macos-sdk
```

Without such a declaration, the normal provider would remain:

```text
host@devel/libffi
```

Provider selection should be project or group policy. It should not be inferred
from whether a matching library happens to exist somewhere on the build host.
Automatic host probing could otherwise select Homebrew, MacPorts, or another
uncontrolled installation and make results host-dependent.

### Possible uports Organization

Frequently assumed packages such as `devel/libffi` could live in the built-in
`make/uports/` collection so that uports always has a maintained buildable
fallback.

System-provider checks could be framework metadata kept separately from the
port definition, for example:

```text
make/uports/devel/libffi/       buildable fallback port
make/uports/Mk/Providers/       operating-system provider checks
```

This organization must not conflate collection origin with provider
selection:

```text
collection origin
  selects where the port definition comes from

dependency provider
  selects what satisfies one dependency for one build context
```

### Required Provider Validation

If a system provider is selected, dependency handling should be automatic but
validation must be explicit. A macOS libffi provider check may need to:

1. obtain the active SDK path from `xcrun`;
2. verify the required header;
3. verify the link library or text-based stub;
4. compile and link a small `ffi_call` test;
5. verify the expected runtime install name;
6. record the SDK identity or version;
7. supply provider-specific compile and link flags;
8. fail before the consumer configure phase if validation fails.

File existence alone is not sufficient evidence of API, ABI, architecture, or
link compatibility.

### Interaction With Current `LIB_DEPENDS`

The current execution framework treats any nonempty `LIB_DEPENDS` as a reason
to add uports destination paths:

```make
CFLAGS  += -I$(DESTDIR)$(PREFIX)/include
LDFLAGS += -L$(DESTDIR)$(PREFIX)/lib
```

On Darwin it may also add an rpath to the uports destination library
directory. That behavior is inappropriate when the resolved dependency is
provided by the macOS SDK.

If provider selection is adopted, include paths, library paths, rpaths, and
runtime checks must be derived from resolved providers rather than merely from
whether `LIB_DEPENDS` is nonempty.

Changing the selected provider must also invalidate the consumer's configure
and build state.

### Implementation Timing

If this design is accepted, full system-provider support should be implemented
late in the formal group enhancement, but the normalized data model should
prepare for it early.

Recommended order:

1. normalize collections, logical ports, groups, and build instances;
2. add planning diagnostics and validation;
3. optimize `tools.mk` planning and target generation;
4. implement automatic dependency expansion using uports build instances as
   the only providers;
5. add variants and variant-qualified build instances;
6. add explicit dependency-provider selection;
7. add operating-system and SDK provider validation.

System-provider resolution depends on records that earlier phases must make
explicit:

```text
consumer build instance
dependency type
resolved logical dependency
selected provider kind
provider identity
provider validation result
compile, link, and runtime contributions
build signature inputs
```

Implementing system providers before normalized instances and dependency
resolution would likely embed additional provider policy in encoded target
strings and eager `eval` generation.

Early design work should nevertheless:

- reserve provider fields in normalized dependency records;
- distinguish the dependency requirement from its selected provider;
- avoid hardcoding that every `LIB_DEPENDS` entry comes from
  `$(DESTDIR)$(PREFIX)`;
- ensure effective environments and build signatures can include provider
  identity;
- leave inspection output able to report provider decisions later.

The practical schedule is therefore:

```text
early
  finalize terminology, reserve records, and remove blocking assumptions

middle
  implement dependency graphs with uports-only providers

late
  implement explicit system providers and platform-specific validation
```

Variants and system providers are mostly independent and their relative order
may change. Both should follow normalized build instances and reliable
dependency resolution.

### Open Questions

- Should the public concept be named `ASSUME_PROVIDED`, `PROVIDER`, or
  something else?
- Is provider policy allowed globally, per group, per port, or per build
  instance?
- Which dependency types may use system providers: `BUILD_DEPENDS`,
  `LIB_DEPENDS`, `RUN_DEPENDS`, or all three?
- Should native host groups be the only groups allowed to use host-system
  libraries by default?
- Should provider declarations include minimum API, ABI, symbol, or version
  requirements?
- How should SDK identity participate in work and package signatures?
- Should failure fall back to building the uports port, or fail because the
  explicit provider policy was not satisfied?
- Which assumed packages belong in built-in `make/uports/`, and which remain in
  project feeds?
- How should packages linked to system providers be represented in package
  manifests and runtime dependency metadata?
- How should release and CI policy prohibit accidental automatic provider
  selection?

No provider syntax or behavior is approved by this section. It records the use
case and constraints for later design discussion.

## Source Resolution

The source resolver should run before group assignment.

### Discovery

For every collection:

1. scan `<root>/<category>/<port>`;
2. require a port `Makefile`;
3. record logical identity and origin;
4. apply collection ignore policy;
5. merge by collection precedence.

### Override Result

For:

```text
uports: feeds/lang/clisp absent
project: feeds/lang/clisp present
```

the resolved record is:

```text
lang/clisp -> project:/path/to/feeds/lang/clisp
```

For a duplicate:

```text
lang/example -> product:/.../lang/example
shadowed: vendor:/.../lang/example
shadowed: uports:/.../lang/example
```

### Diagnostics

Add:

```sh
make port-origin PORT=lang/clisp
make collections-list
make overrides-list
```

Example:

```text
Port: lang/clisp
Selected collection: project
Directory: /path/to/feeds/lang/clisp
Shadowed definitions: none
```

This makes feed override behavior visible rather than implicit in `get-dir`.

## Selection And Assignment Pipeline

The wrapper should use an explicit planning pipeline:

```text
1. load collections
2. discover physical port definitions
3. resolve one definition per category/port
4. apply PORTS_LISTS selection
5. validate selected identities
6. load group profiles and membership
7. assign explicit groups
8. assign default group where allowed
9. load port variant declarations
10. select variants for each group-port pair
11. expand group, port, and variant combinations into build instances
12. compose instance environments
13. validate graphs, identities, outputs, and paths
14. generate targets
15. dispatch to per-port framework
```

This order prevents group declarations from accidentally selecting a shadowed
physical port.

## Target Design

Keep existing targets and add canonical category-qualified forms.

### Canonical Instance Target

```text
group@category/port[:variant].suffix
```

Examples:

```text
compiler@lang/clisp.build
compiler@devel/libffi:static.build
cross-aarch64@lang/gcc-14:core1.build
```

The variant qualifier is omitted for `default`.

### Compatible Short Alias

```text
group@port.suffix
```

Example:

```text
compiler@clisp.build
```

Generate this only when `clisp` identifies one active logical port and the
target selects one unambiguous variant. A variant-qualified short alias may be:

```text
compiler@libffi:static.build
```

### Default-Group Alias

```text
port.suffix
```

This points to the selected default instance only when unambiguous.

### Aggregate Targets

Preserve:

```text
category.suffix
group.suffix
ports.suffix
```

Aggregate target prerequisites should use canonical instance targets
internally.

Aggregates must expand all explicitly selected variants, but must not
implicitly select every variant declared by a port.

## Default Group Policy

Retain development convenience:

```make
PORT_GROUP_DEFAULT = compiler
PORT_GROUP_REQUIRE_EXPLICIT = no
```

Add strict mode:

```make
PORT_GROUP_REQUIRE_EXPLICIT = yes
```

In strict mode, selected ports without explicit membership fail before target
generation.

Add inspection:

```sh
make implicit-group-ports
```

This reports which ports entered the default group and why.

## Validation

Add:

```sh
make groups-check
```

It should validate all wrapper-level records.

### Collection Checks

- every collection root exists unless marked optional;
- every discovered port has a Makefile;
- collection identifiers are unique;
- override precedence is deterministic;
- ignored and shadowed ports are reportable.

### Port Checks

- selected logical ports exist;
- canonical identities are unique after resolution;
- short aliases are generated only when unambiguous;
- port-level override variables refer to selected ports.

### Variant Checks

- selected variants are declared by the resolved port;
- each group-port pair has a deterministic default variant;
- variant names are valid and unique within the port;
- work suffixes and package identities do not collide;
- variant-specific plist selections exist where required;
- aggregate targets include exactly the selected variants;
- instance dependency graphs contain no cycles;
- bootstrap stages do not overwrite outputs needed by later stages
  unexpectedly.

### Group Checks

- group names are valid and unique;
- every concrete group has `DESTDIR` and `PREFIX`;
- membership refers to logical ports, not physical paths;
- multiple membership is explicit;
- strict mode has no implicit assignments;
- suffixes do not cause work-directory collisions;
- destination roots do not overlap unexpectedly.

### Graph Checks

- all relationship targets are known groups;
- build graphs contain no cycles;
- tool-provider order is deterministic;
- runtime groups do not accidentally depend on private bootstrap roots.

### Environment Checks

- exclusions match known inherited values;
- required tool exports resolve to files after provider installation;
- derived paths are defined;
- environment output does not contain conflicting assignments unless the
  precedence rule resolves them explicitly.

### Performance Checks

- normalized collection, port, group, variant, and instance records are
  computed once where practical;
- recursive variables do not repeatedly rescan the complete port or instance
  lists;
- target and alias counts are reportable;
- diagnostic-only rules are not eagerly generated for ordinary builds where
  they can be produced by shared recipes or on-demand output;
- adding one selected variant increases generated state in proportion to that
  instance, not every possible port-variant combination;
- parse-time and make-database growth are measured against representative
  small and large plans.

## Ownership Of Configuration

The refined design should keep policy in the correct layer.

### uports Framework Owns

- built-in port definitions;
- lifecycle implementation;
- built-in group defaults such as `bs` and `host`;
- compatibility parsing;
- validation and target-generation machinery.

### Feed Owns

- external or overridden port definitions;
- optional feed-local ignore policy;
- optional suggested group membership for that feed;
- no authority to force project destination paths.

Feed group suggestions should be defaults that a project may override.

### Project Wrapper Owns

- active collection roots and precedence;
- selected ports;
- default group;
- final group membership;
- destinations and prefixes;
- environment overlays;
- tool-provider selection;
- group relationships;
- strictness policy.

### Port Owns

- package-specific dependencies and build behavior;
- supported variants and variant-specific build, package, and plist behavior;
- no project group assignment;
- no knowledge of collection precedence.

## Feed Policy Refinement

The current `feeds/group.mk` mixes feed membership suggestions with project
environment policy.

A cleaner split is:

```text
feeds/groups.mk       optional membership suggestions
project/groups.mk     final project group profiles and environments
```

For compatibility, existing `feeds/group.mk` remains loaded.

The precedence should be:

```text
framework group defaults
feed membership suggestions
project group policy
command-line selection
```

Feed files may suggest:

```make
PORT_GROUP_SUGGEST_textproc += textproc/expat2
```

The project confirms or overrides:

```make
PORT_GROUP_textproc_PORTS += $(PORT_GROUP_SUGGEST_textproc)
```

This prevents a reusable external feed from deciding where a consuming project
must install its packages.

## Compatibility Mapping

The first implementation should normalize legacy variables without changing
behavior:

```text
Legacy                              Normalized
---------------------------------------------------------------------------
FEEDS                               high-priority project collection
special_groups_all                  PORT_GROUPS
PORTS_GROUP_DEFAULT                 PORT_GROUP_DEFAULT
<group>_lists                       PORT_GROUP_<group>_PORTS
PORTS_<group>_ENVS                  PORT_GROUP_<group>_ENVS
```

Legacy and new declarations for the same property should not merge silently.
The framework should either:

- reject conflicting declarations; or
- print the selected precedence in a diagnostic mode.

## Implementation Plan

### Current Implementation Baseline

As of June 20, 2026, the standalone tools optimization task has completed:

- deterministic planner statistics and benchmark tooling;
- normalized logical-port origin and build-instance lookup records;
- deferred nonessential presentation probes;
- consolidated fresh collection discovery;
- shared canonical and short-alias lifecycle dispatch;
- shared diagnostic and aggregate target dispatch;
- explicit ambiguity rejection for duplicate short port names;
- implicit `variant=default` in every selected build instance;
- variant-aware internal instance keys without public variant targets.

The next formal group-enhancement work must build on these records and shared
dispatch paths. It should not restore per-instance or per-suffix generated rule
matrices.

### Phase 1: Observe Existing State

Add read-only inspection and validation using the current variables:

- `collections-list`;
- `overrides-list`;
- `port-origin`;
- `groups-list`;
- `group-info`;
- `port-groups`;
- `implicit-group-ports`;
- `port-env`;
- `planner-stats`;
- `groups-check`.

No target behavior changes in this phase.

`planner-stats` should report at least:

```text
collections
resolved ports
build instances
groups
categories
selected variants
lifecycle suffixes
canonical targets
aliases
aggregate targets
```

Record baseline parse time and make-database size before changing target
generation.

### Phase 2: Normalize Collections

Represent built-in uports and `FEEDS` as collection records.

Keep:

```make
feeds_lists
ports_lists
ports_all_raw_lists
```

as compatibility outputs derived from the normalized resolver.

### Phase 3: Normalize Group Profiles

Translate existing group variables into internal profile records.

Keep:

```make
groups_all
groups_<group>
<port>_groups
ports_all_group
```

as compatibility outputs.

### Phase 4: Canonical Build Instances

Generate canonical:

```text
group@category/port.target
```

and retain current short aliases where unique.

Update aggregate targets to depend on canonical instances.

Internally reserve a variant field whose value is `default`; do not change
existing target behavior in this phase.

Before adding more generated dimensions, reduce eager expansion where
compatible:

- use immediate `:=` values for normalized records that should be computed
  once;
- use shared pattern or static-pattern dispatch instead of one `eval` rule per
  instance and suffix where GNU make semantics permit it;
- generate short aliases only after uniqueness is known;
- avoid per-port diagnostic target generation when one parameterized
  diagnostic recipe can provide the same result;
- avoid repeated collection scans and repeated parsing of encoded target
  strings.

### Phase 5: Port Variants

Add:

```text
group@category/port:variant.target
```

Implement explicit variant declaration and per-group/per-port variant
selection. Give each variant an independent work identity, package identity,
environment composition result, and dependency node. Preserve unqualified
targets as aliases for the `default` variant.

Do not make cross-toolchain stages the first variant implementation. Validate
the simpler repeated-build model before adding bootstrap-stage graphs.

### Phase 6: Group Graph And Tool Providers

Add:

```make
PORT_TOOL_GROUPS
PORT_GROUP_<group>_BUILD_USES
```

Implement cycle detection and topological ordering.

Keep `USE_HOSTTOOLS` as compatibility syntax.

### Phase 7: Build-Instance Graphs

Add explicit dependencies between variant-qualified build instances. Use this
for ordered bootstrap flows such as GCC core passes, libc headers/start files,
complete libc, and final GCC.

These relationships supplement rather than replace package dependencies and
group-wide relationships.

### Phase 8: Multiple Collections

Generalize from one `FEEDS` root to ordered `PORT_COLLECTIONS`.

Preserve `FEEDS` as the common one-feed shortcut.

### Phase 9: Split Feed Suggestions From Project Policy

Introduce optional feed membership suggestions and project-owned final group
profiles.

Migrate existing `feeds/group.mk` gradually.

## Design Principles

1. A port collection provides definitions.
2. A logical port is identified by `category/port`.
3. Collection precedence resolves one active port definition.
4. A group is a project build profile, not a collection or category.
5. A variant is one repeatable configuration, ABI, or bootstrap stage of a
   logical port.
6. A build instance joins one resolved port variant with one group.
7. `tools.mk` is the planner and dispatcher for build instances.
8. The per-port framework remains responsible for lifecycle execution.
9. Feed overrides must remain supported and observable.
10. External feeds must remain valid.
11. Existing environment overlays and exclusions must remain expressible.
12. Existing targets remain compatible and imply the `default` variant.
13. Canonical internal identities should include category, origin, group, and
    variant.
14. Short target aliases are convenience only and must be unambiguous.
15. Group graphs supplement rather than replace package dependencies.
16. Build-instance graphs express variant and bootstrap-stage ordering.
17. Project policy has final authority over feed suggestions and variant
    selection.
18. Migration begins with normalization and diagnostics, not a flag-day
    rewrite.
19. Parse-time work and generated rule count should scale with selected build
    instances, not the Cartesian product of all possible groups, ports,
    variants, and targets.

## Proposed End State

The wrapper should be able to answer these questions directly:

```text
Which physical collections were scanned?
Which collection supplied this logical port?
Which definitions were shadowed?
Why is this port in this group?
Was its assignment explicit or default?
What destination, prefix, suffix, and environment does this instance use?
Which variants does this port support?
Which variants are selected in this group, and why?
Which work, package, and plist identity does each variant use?
Which tool groups are visible while it builds?
What group ordering is required?
What variant or bootstrap-stage ordering is required?
Which exact per-port target will tools.mk invoke?
```

When those answers are represented explicitly, uports keeps its reusable
per-port framework, feeds keep their override capability, and `tools.mk`
becomes a clearer wrapper planner instead of relying primarily on encoded
strings and distributed variables.
