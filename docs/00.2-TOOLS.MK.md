# tools.mk Performance Improvement Task Plan

## Purpose

This report tracks performance and scalability work for:

```text
make/uports/Tools/tools.mk
```

The task is intentionally separate from the group architecture proposal in
`docs/00.1-GROUP.md`.

The group proposal defines the desired data model and behavior. This task
improves how the current wrapper computes its plan and generates make targets,
while preserving existing behavior and leaving a suitable foundation for
future variants.

## Problem Statement

The current wrapper performs significant work while GNU make parses
`tools.mk`. It uses nested `foreach`, `call`, and `eval` expressions to:

- discover and classify ports;
- calculate category and group mappings;
- compose per-instance environments;
- generate lifecycle targets;
- generate default-port aliases;
- generate category, group, and global aggregate targets;
- generate diagnostic targets.

`eval` is not inherently incorrect. Its argument is expanded and then parsed
again as makefile syntax, however, so extensive nested use increases parse-time
work and makes the generated make database difficult to reason about.

The principal cost comes from eagerly materializing the complete target
matrix:

```text
build instances × lifecycle suffixes
+ default and short aliases × lifecycle suffixes
+ categories × lifecycle suffixes
+ groups × lifecycle suffixes
+ global and diagnostic targets
```

Future variant support adds another dimension:

```text
groups × ports × selected variants × lifecycle suffixes
```

Adding variants directly to the current eager generation model would multiply
both parse cost and implementation complexity.

## Baseline

The initial measurement was taken on June 19, 2026, using GNU Make 4.4.1 and
the current example project configuration.

The active plan contained:

```text
logical ports:                 42
build instances:               42
groups:                         4
categories:                     9
lifecycle suffixes:            17
canonical lifecycle targets:  714
```

Observed no-op parse times on the development machine:

```text
complete active plan:       approximately 0.16-0.18 seconds
PORTS_LISTS=lang/cpython:   approximately 0.09 seconds
```

A make database inspection reported approximately:

```text
rule lines:          1,873
phony target names:  1,673
```

These numbers are acceptable for the current tree. They are a warning about
growth rather than evidence of a current operational failure.

Measurements must be repeated using a documented command after each
optimization. Absolute timing varies by machine, so comparisons should use the
same host, make version, filesystem state, and command.

## Goals

1. Reduce wrapper parse time and generated make-database size.
2. Make planning cost scale primarily with selected build instances.
3. Avoid repeated scans and repeated transformations of unchanged lists.
4. Reduce eager per-port, per-group, per-category, and per-suffix rule
   generation.
5. Preserve all current public targets, variables, environment composition,
   group assignment, and feed override behavior.
6. Keep the implementation compatible with the normalized
   `group + port + variant` model.
7. Add measurements that prevent later regressions.

## Non-Goals

This task does not initially:

- change collection precedence;
- redesign public group configuration;
- add port variants;
- add cross-toolchain stage graphs;
- change package build results;
- change lifecycle implementation in per-port framework files;
- remove existing target forms.

If an optimization requires a public behavior change, it must be split into a
separate architecture task.

## Current Hot Areas

The following areas require measurement and review.

### Collection Discovery

`generate-ports-lists` invokes external `find` and `sed` commands for collection
roots during parsing.

Questions:

- Can discovery results be computed once and stored with immediate variables?
- Can one traversal collect both directories and Makefile validity?
- Can normalized collection support avoid rescanning unchanged roots?
- Is a generated cache worthwhile, and how would invalidation remain correct?

Caching must not hide newly added or removed ports.

### Repeated Recursive Expansion

Many planning variables use recursive `=` assignment and contain nested list
operations. The same logical list may therefore be expanded and transformed
multiple times.

Candidates for immediate `:=` assignment include normalized results that are
complete after configuration loading:

```text
resolved ports
selected ports
categories
groups
group membership
build instances
suffix lists
origin mappings
```

Conversion must account for command-line variables and configuration that is
intentionally defined later.

### Per-Instance Environment Generation

The current wrapper creates a separate `port_<group>_<port>_env` variable
through `eval` for every build instance.

Questions:

- Can effective environments be computed through one parameterized function?
- Which values should be normalized once?
- Can exclusions and precedence be represented without reparsing generated
  assignments?
- Will on-demand computation repeat more work than eager computation?

The result must preserve the existing overlay and exclusion order.

### Lifecycle Target Matrix

The wrapper currently lists every group-port-suffix target and declares the
complete list phony.

Investigate:

- GNU make pattern rules for canonical instance dispatch;
- static pattern rules over selected instances;
- grouped reusable recipes;
- whether `.PHONY` can be reduced without changing correctness;
- parsing the requested target once rather than generating one rule for every
  possible suffix.

Pattern rules must not accidentally accept unknown groups, ports, variants, or
suffixes. Validation must remain early and deterministic.

### Alias Targets

Default and short aliases are eagerly generated for all lifecycle suffixes.

Investigate:

- generating aliases only for selected and unambiguous identities;
- using secondary expansion or shared prerequisite mapping;
- reducing duplicate aliases when canonical and short identities coincide;
- preserving compatibility for scripts that query the make database.

### Aggregate Targets

Category, group, and global targets currently receive generated prerequisite
lists for every lifecycle suffix.

Investigate whether aggregate target families can share prerequisite
calculation without one `eval` per category/group/suffix combination.

### Diagnostic Targets

Many debug targets are generated per category, port, or group even during
ordinary builds.

Replace these where possible with parameterized inspection targets such as:

```sh
make port-origin PORT=lang/clisp
make group-info GROUP=compiler
make port-groups PORT=lang/clisp
```

Existing diagnostics must remain compatible until replacement targets are
available.

### Parse-Time Shell Commands

The wrapper executes commands such as `find`, `sed`, `which`, `uname`, `stty`,
and `tput` during parsing.

Classify each command as:

- required for every invocation;
- required only for a specific target;
- replaceable with a make built-in;
- cacheable after discovery;
- removable.

Terminal-width detection, status formatting, and similar presentation work
should not affect ordinary build startup when it can be deferred.

## Planner Statistics

Add a read-only target:

```sh
make planner-stats
```

It should report at least:

```text
collection count
discovered definition count
resolved logical port count
selected port count
group count
category count
build-instance count
selected variant count
lifecycle suffix count
canonical target count
alias target count
aggregate target count
diagnostic target count
```

Where practical, it should also report which counts are materialized rules
versus values handled by shared dispatch.

The target must not run package builds or modify the workspace.

The initial implementation reports:

```text
collections
  Distinct active physical collection roots.

discovered_definitions
  Valid physical port definitions before override resolution.

resolved_logical_ports
  Logical category/port identities after feed precedence.

selected_ports
  Logical ports selected by PORTS_LISTS, or all resolved ports by default.

groups, categories, build_instances
  Counts in the current selected plan.

selected_variants
  Zero until variant-qualified instances are implemented.

lifecycle_suffixes
  Lifecycle operations generated by the current wrapper.

canonical_targets
  Current group-port lifecycle targets.

alias_targets
  Current default short-port lifecycle aliases.

aggregate_targets
  Category, group, global lifecycle, and final ports targets.

diagnostic_targets
  Public information/debug/statistics targets.
```

These names describe current implementation structures. Later normalization
may refine which targets are materialized rules versus shared dispatch, but
the output keys should remain stable where practical for benchmark tooling.

## Measurement Method

Keep a reproducible benchmark procedure in this report or in a supporting
script.

At minimum, measure:

```text
full active plan
one selected port
one complete group
a port assigned to multiple groups
a synthetic large plan
```

Record:

```text
GNU make version
host operating system and architecture
command
wall time
user time
system time
maximum resident memory when available
make database size
rule count
phony target count
planner statistics
```

Run each timing command several times and report the median. Separate cold
filesystem measurements from warm-cache measurements when discovery cost is
being evaluated.

Benchmark commands must avoid executing real package recipes. They should also
avoid unrelated project checks, such as requiring an already installed
`pkg-config`, when measuring wrapper parse cost.

The benchmark helper is:

```sh
Tools/benchmark-tools.sh
```

It defaults to the self-contained `Tools/tests` fixture. To benchmark a
project that includes `Tools/tools.mk`, pass its directory:

```sh
Tools/benchmark-tools.sh -C /path/to/project -l full

Tools/benchmark-tools.sh -C /path/to/project -l cpython \
  PORTS_LISTS=lang/cpython
```

Options:

```text
-C directory  Makefile directory; default is Tools/tests
-n runs       number of timing runs; default is 5
-l label      machine-readable sample label
```

The output is line-oriented `key=value` data with:

- host and GNU make identity;
- planner statistics;
- median real, user, and system time;
- maximum resident memory when GNU time provides it;
- make-database bytes, rule lines, and phony target names.

Memory is reported as `unavailable` when the host timing implementation cannot
provide it reliably. The script always invokes `planner-stats` with
`USE_HOSTTOOLS=` and never runs package lifecycle recipes.

#### Phase 1A: Freeze Core Planning Lists

Status: completed

The first Phase 1 change converted stable port, category, group, and
build-instance records from recursive `=` variables to immediate `:=` values:

```text
resolved and selected port lists
category lists and port-to-category mappings
grouped build instances
group lists and port-to-group mappings
default alias instance selection
canonical target and planner-stat lists
```

`ports_all_group_extra` is now computed after per-port group mappings exist.
This preserves the previous deferred result while making the final record
immediate.

Seven-run warm-cache comparison on the baseline host:

| Scenario | Before real | After real | Before DB bytes | After DB bytes | Rules | Phony |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| full | 0.13 s | 0.10 s | 748881 | 785580 | 1873 | 1674 |

| synthetic-200 | 0.99 s | 0.12 s | 2890084 | 3099511 | 7768 | 7300 |

The synthetic improvement confirms that repeated recursive expansion was a

Generated rule and phony counts are unchanged, as expected for this phase.
Later target-generation phases remain responsible for reducing those counts
and the overall database size.

#### Phase 1B: Normalize Origin And Instance Lookups

Status: completed

The second Phase 1 change added simple lookup records for every resolved
logical port:

```text

category/port origin
selected physical collection root
```

It also added records for every selected group-port build instance:

```text
group
port
category
origin
physical root
effective environment
```

Canonical and special lifecycle dispatch, origin lookup, and `info.ports`
status paths now consume these records rather than independently reconstructing
origin and root information from encoded strings.

#### Phase 2C: Consolidate Fresh Collection Discovery

Status: completed

Persistent discovery caching and shell-free wildcard discovery were evaluated.
Wildcard discovery found the same definitions but sorted them, changing the
current default aggregate and build order. Persistent caching would require
planner-time writes and robust invalidation for external feeds, additions,
removals, renames, overrides, and ignore-policy changes.

The implemented approach keeps fresh discovery on every invocation but
consolidates built-in and feed traversal into one make `$(shell ...)`
expansion. Separate ordered `find` traversals preserve existing list order.

Regression coverage creates and removes a synthetic feed port between planner
invocations. The new definition appears immediately and disappears immediately
without an invalidation target or cache file.

Seven-run warm-cache comparison against Phase 2B:

| Scenario | Before real | After real | Rules | Phony |
| --- | ---: | ---: | ---: | ---: |
| full | 0.11 s | 0.12 s | 1767 | 1674 |
| cpython | not re-recorded | 0.07 s | 202 | 93 |
| synthetic-200 | 0.14 s | 0.14 s | 7351 | 7300 |

No timing improvement is claimed. The result is one unconditional make shell
expansion instead of separate built-in and feed shell expansions, with no
cache correctness risk.

#### Phase 3A: Share Canonical Lifecycle Dispatch

Status: completed

The canonical `group@port.suffix` matrix is retained as a normalized validation
list, but its names are no longer materialized through one giant `.PHONY`
declaration.

Seventeen shared lifecycle pattern rules now dispatch:

```text
15 normal lifecycle suffixes
2 special suffixes: package-source and makesum
```

A phony force prerequisite preserves the previous always-run behavior even if
a filesystem entry has the same name as a canonical target. Every
pattern-matched canonical target is checked against `ports_target_all` before
dispatch, so an unknown group-port combination fails explicitly. Unsupported
suffixes continue to have no matching rule.

Compatibility coverage verifies:

- normal canonical dispatch;
- special inner-make dispatch;
- aliases and aggregates;
- rejection of unknown group-port combinations;
- rejection of unknown suffixes;
- dispatch despite a same-named filesystem file.

#### Phase 3B: Simplify Instance Environment Generation

Status: completed

The previous environment generator emitted a conditional makefile fragment for
every group-port instance:

```text
ifneq blocks
multiple += assignments
instance exclusions
port and instance additions
derived TYPE_SUFFIX
```

It now uses one pure `compose-port-env` function and one simple compatibility
assignment per instance. The dynamic variable name still requires `eval`, but
the reparsed fragment is a single assignment rather than a generated
conditional program.

Environment order remains:

```text
filtered PORTS_ENVS
filtered group ENVS
port EXTRA_ENVS
group-port EXTRA_ENVS
derived TYPE_SUFFIX
```

Compatibility variables such as `port_target_libffi_env` remain available and
are now immediate values. The normalized instance environment remains
byte-identical in regression coverage.

### Phase 4: Reduce Alias And Aggregate Generation

Status: completed

Tasks:

- generate short aliases only for unambiguous active identities;

- remove duplicate generated target definitions;

Exit criteria:

#### Phase 4A: Share Default Short-Alias Dispatch

Status: completed

The explicit short-alias matrix:

```text
port.suffix -> default-group@port.suffix
```

was removed. Canonical and short targets now use the same validated lifecycle
patterns. A short target is resolved to its selected default build instance
before environment and dispatch lookup.

The conceptual alias list remains available for planner statistics,
validation, and top-level target exclusion, but its names are no longer
materialized as individual phony rules.

Compatibility coverage verifies:

- aliases select the expected default instance;
- a multi-group port alias does not dispatch its nondefault instance;
- unknown aliases fail explicitly;
- same-named filesystem entries do not suppress alias dispatch;
- normal and special suffixes both resolve through the canonical instance.

The current target grammar cannot represent two active logical ports with the
same final name. Such names previously collided silently in generated variables
and aliases. They now fail early with:

```text
ambiguous short port names: <name>
```

This validation can be relaxed later when category-qualified canonical
instances are implemented.

#### Phase 4B: Share Aggregate Target Generation

Status: completed

The generated category, group, and global matrices were replaced with one
static pattern rule over the unique aggregate target set. Secondary expansion
calculates prerequisites for the concrete requested target.

Category, group, and global prerequisite calculation remains separate, then
the results are combined. This is required when a name is both a category and
a group: the aggregate target invokes the union of both memberships without
emitting duplicate target definitions.

Compatibility coverage verifies:

- category aggregates include built-in and feed ports;
- group aggregates include all selected members;
- a category/group name collision includes both membership sets;
- same-named filesystem entries do not suppress aggregate dispatch;
- normal and special lifecycle suffixes resolve through canonical targets.

#### Explicit-Variant Performance Budget

Before variant-qualified targets may be enabled, an implementation must meet
all of these constraints on the existing synthetic benchmark:

- undeclared and unselected variants add zero records and zero targets;
- adding `N` selected variants adds exactly `N` normalized instance records;
- conceptual canonical-target growth is `N × lifecycle_suffixes`;
- materialized make rule growth is independent of `N`; shared target grammar
  may add at most two lifecycle-pattern families;
- make-database growth is linear and no more than 2 KiB per selected variant
  in the 200-port synthetic plan;
- selecting 200 additional variants keeps median parse time below the larger
  of 1.5 times the default-only median or the default-only median plus 0.05
  seconds;
- removing those selections returns planner counts and database size to the
  default-only baseline, within benchmark output noise.

These are acceptance limits for the later explicit-variant implementation,
not evidence that variant-qualified targets already exist.

Phase 5 is complete for the tools.mk optimization scope. Implementing and
benchmarking actual selected nondefault variants requires the declaration,
selection, environment, work-identity, package-identity, and target syntax
decisions owned by the group enhancement. That work must use the budget above
as an entry criterion rather than extending this optimization task into a
partial variant feature.

## Risks

### Pattern Rules May Accept Invalid Targets

Replacing explicit generated rules with broad patterns can defer errors or
dispatch misspelled targets. Shared dispatch must validate every parsed field
against normalized records.

### Immediate Assignment Can Freeze Values Too Early

Changing `=` to `:=` without understanding include and command-line precedence
can alter behavior. Each conversion needs a value-equivalence test.

### On-Demand Computation Can Repeat Work

Removing eager variables is not automatically faster if complex functions are
then expanded repeatedly by many prerequisites or recipes. Normalize reusable
records and measure both approaches.

### Cache Invalidation Can Hide Collection Changes

A persistent discovery cache must detect added, removed, renamed, or overridden
ports. A stale cache is worse than slower startup.

### Make Database Compatibility

External tooling may inspect `make -p` output or depend on explicit phony
targets. Changes should document any unavoidable database-level difference
even when command behavior remains compatible.

### Optimizing Before Normalization Can Increase Complexity

Local reductions in `eval` may preserve encoded-string dependencies and make
later variant support harder. Performance work should move toward normalized
records rather than introduce additional target-string parsing.
