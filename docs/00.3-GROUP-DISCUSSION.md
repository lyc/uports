# Group Design Discussion Notes

## Purpose

This document is a compact reference for the group-design discussions held
through June 19, 2026. It records the questions considered, the current design
direction, and topics that remain unresolved.

Detailed design and task tracking remain in:

```text

docs/00.2-TOOLS.MK.md  tools.mk performance improvement task plan
```

This note does not replace those reports.

## 1. Collections And Feeds

Status: **Agreed direction**

A collection answers:

```text
Where does this logical port definition come from?
```

A group answers:

```text
In which build and installation context is this port built?
```

These concepts are orthogonal.

The project should normally keep one `feeds/` collection even when it has many
groups such as:

```text
host
compiler
textproc
python
```

Creating another feed is appropriate only when there is a real collection
boundary, for example:

- a separately maintained repository;
- vendor, product, or project ownership;
- an independent update or release schedule;
- an external feed path;
- intentional override precedence.

A second feed should not be created merely to simplify group membership.
Multiple collections can contain the same `category/port`, but precedence then
selects one definition and shadows the others. Collections are not a mechanism
for building both definitions.

## 2. When To Create A Python Group

Status: **Agreed direction**

A `python` group is justified when CPython and related packages need a distinct
build profile, such as:

```text
separate DESTDIR or PREFIX
Python-specific environment
separate work and package identity
exported python3 or pip tools
different visibility to other groups
an independently assembled runtime
```

If CPython merely belongs to the normal compiler/runtime installation context,
it should remain in `compiler`. A group should not be used only as a package
label or category.

Dependencies such as OpenSSL, libffi, and SQLite remain package dependencies.
They should be built in the `python` group only when that group requires its
own copies or dependency instances.

## 3. Multiple Group Membership

Status: **Agreed direction**

One logical port may be built in multiple groups:

```text
compiler@devel/libffi
python@devel/libffi
```

Each group-port pair is a separate build instance with its own:

```text
environment
work suffix
destination
package/build identity
targets
```

Collection origin remains unchanged. A feed port does not become a different
logical port merely because it is built in another group.

## 4. Port Variants

Status: **Agreed direction; implementation planned**

Some ports need repeated builds within the same group. The normalized build
identity is therefore:

```text
group + resolved logical port + variant
```

Examples:

```text
compiler@devel/libffi:shared
compiler@devel/libffi:static
python@devel/libffi:shared
```

`default` is the implicit variant used by existing unqualified targets:

```text
compiler@lang/clisp.build
```

is represented internally as:

```text
compiler@lang/clisp:default.build
```

Group membership must not automatically select every declared variant.
Projects select the required variants for each group-port pair.

Each selected variant needs an independent:

```text
work identity
environment result
package identity
plist or output selection where required
dependency node
```

## 5. Versions Versus Variants

Status: **Agreed direction**

Different upstream releases should normally be separate logical ports:

```text
lang/gcc-14
lang/gcc-15
```

Variants represent configurations, ABIs, or stages of one selected release:

```text
lang/gcc-14:core1
lang/gcc-14:core2
lang/gcc-14:final
```

This keeps version selection separate from repeated configuration of one port.

## 6. Cross-Compiler And Bootstrap Stages

Status: **Agreed direction; later implementation**

Established cross-toolchain implementations use ordered stages such as:

```text
binutils
gcc:core1
libc:headers-startfiles
gcc:core2
libc:full
gcc:final
```

These are variant-qualified build instances with explicit dependencies. They
should not become separate collections.

They should not become separate groups unless a stage genuinely uses a
different build or installation context. A group describes context; a variant
or instance dependency describes repeated configuration and ordering.

A normal libc build may produce static and shared outputs together. If truly
separate static-only and shared builds are required, they are variants rather
than groups.

## 7. Suitability Of The Group Proposal

Status: **Agreed direction**

`docs/00.1-GROUP.md` remains the primary architecture proposal. It was extended
from:

```text
group + resolved port
```

to:

```text

```

The report now covers:

- collections and override precedence;
- resolved logical ports;
- group profiles;
- variants;
- build instances;
- environment composition;
- canonical and compatible targets;
- group and build-instance graphs;
- validation and inspection;
- compatibility-first migration.

## 8. tools.mk Performance

Status: **Planned as a separate task**

The current wrapper relies on nested `foreach`, `call`, and `eval` expressions
to eagerly generate planning records and target families.

The main scaling term is:

```text
build instances × lifecycle suffixes
```

with additional default aliases, short aliases, category targets, group
targets, global targets, and diagnostic targets.

Variants add another dimension:

```text
groups × ports × selected variants × lifecycle suffixes
```

Initial measurements on June 19, 2026, using GNU Make 4.4.1:

```text
logical ports:                 42
build instances:               42
groups:                         4
categories:                     9
lifecycle suffixes:            17
canonical lifecycle targets:  714
complete no-op parse:          approximately 0.16-0.18 seconds
one selected port:             approximately 0.09 seconds
make database rule lines:      approximately 1,873
phony target names:            approximately 1,673
```

Current performance is acceptable for this tree, but the target-generation
model will scale poorly if variants are added directly through another nested
`eval` dimension.

The standalone task plan is `docs/00.2-TOOLS.MK.md`.

## 9. Performance Task Direction

Status: **Planned**

The performance work includes:

1. establish repeatable baselines and add `planner-stats`;
2. normalize and freeze planning records where safe;
3. defer nonessential parse-time shell commands and diagnostics;
4. reduce per-instance/per-suffix `eval` generation;
5. reduce alias and aggregate rule generation;
6. prepare efficient dispatch for `variant=default` and later selected
   variants.

Compatibility must be checked after every phase. Existing public targets,
environment composition, feed overrides, group assignment, and package results
must remain valid.

The primary scalability requirement is:

> Parse-time work and generated rule count should scale with selected build
> instances, not the Cartesian product of all possible groups, ports,
> variants, and lifecycle targets.

## 10. System-Provided Dependencies

Status: **To Be Discussed**

The motivating case is a native host ChezScheme build on macOS:

```text
host@lang/chezscheme
  requires devel/libffi
  possible provider: macOS SDK
```

The macOS Command Line Tools SDK can provide:

```text
usr/include/ffi/ffi.h
usr/lib/libffi.tbd
runtime install name /usr/lib/libffi.dylib
```

The port should continue declaring the logical dependency. The unresolved
question is whether project or group policy may select its provider:

```text
uports provider
  host@devel/libffi

system provider
  system:macos-sdk
```

Possible syntax discussed, but not approved:

```make
PORT_GROUP_host_ASSUME_PROVIDED += devel/libffi
```

or:

```make
PORT_GROUP_host_PROVIDER_devel_libffi = system:macos-sdk
```

Provider selection should not silently choose any matching host installation.
Automatic detection could otherwise select Homebrew, MacPorts, or another
uncontrolled provider and make results host-dependent.

## 11. Built-In Fallback Packages

Status: **To Be Discussed**

Frequently assumed dependencies could have maintained fallback ports in:

```text
make/uports/devel/libffi/
```

Operating-system provider checks could be separate framework metadata:

```text
make/uports/Mk/Providers/
```

This does not change the core distinction:

```text
collection origin
  where the port definition comes from

dependency provider
  what satisfies a requirement for one build context
```

Moving a fallback port into the built-in collection must not automatically
make it assumed or system-provided.

## 12. Automatic Provider Validation

Status: **To Be Discussed**

If an explicit system provider is selected, dependency checking should become
automatic and fail before the consumer configure phase.

A macOS libffi provider check may need to:

1. discover the active SDK with `xcrun`;
2. verify headers and link stubs;
3. compile and link a small `ffi_call` test;
4. verify architecture and runtime install name;
5. record SDK identity or version;
6. contribute provider-specific compile and link flags;
7. participate in work/build signatures.

File existence alone is insufficient to validate API, ABI, architecture, and
link compatibility.

## 13. Current LIB_DEPENDS Limitation

Status: **Known constraint**

The current framework treats nonempty `LIB_DEPENDS` as a reason to add:

```make
-I$(DESTDIR)$(PREFIX)/include
-L$(DESTDIR)$(PREFIX)/lib
```

On Darwin it may also add an rpath to the uports destination library
directory.

That assumption is incompatible with a dependency supplied by the macOS SDK.
If provider selection is adopted, include paths, library paths, rpaths, and
runtime checks must come from resolved providers.

Changing provider identity must invalidate the consumer's configure and build
state.

## 14. Provider Implementation Timing

Status: **Reference direction, conditional on approving provider support**

Prepare for providers early, but implement full system-provider behavior late.

Recommended order:

1. normalize collections, logical ports, groups, and build instances;
2. add diagnostics and validation;
3. optimize `tools.mk`;
4. implement automatic dependency expansion with uports-only providers;
5. add variants;
6. add explicit provider selection;
7. add platform and SDK provider validation.

Early work should reserve fields for:

```text
consumer instance
dependency type
logical dependency
provider kind
provider identity
validation result
compile/link/runtime contributions
signature inputs
```

The middle stage should establish a reliable dependency graph using only
uports build instances. System providers should be added only after dependency
resolution is explicit and testable.

Variants and system providers are mostly independent, but both depend on
normalized build instances.

## 15. Open Questions

The following questions remain unresolved:

- What should the public provider concept be called?
- At which scopes may provider policy be set: project, group, port, or
  instance?
- Which dependency types may use system providers?
- Should only native host groups use host-system libraries by default?
- What API, ABI, symbol, architecture, and version checks are required?
- How does SDK/provider identity affect work and package signatures?
- Should a failed explicit provider fall back to uports or fail immediately?
- Which fallback packages belong in built-in uports versus project feeds?
- How are system runtime dependencies represented in package metadata?
- How should CI and release policy prevent accidental host contamination?
- What is the final public variant syntax and variable encoding?
- What performance budget must be met before variants are enabled?

## 16. Current Recommended Work Order

Status: **Agreed planning direction**

```text
1. Add normalized planning and inspection without changing behavior.
2. Establish tools.mk performance baselines and planner statistics.
3. Optimize current group-port planning and target generation.
4. Normalize dependency expansion using uports-only providers.
5. Add explicit variants and variant-qualified build instances.
6. Add build-instance dependency graphs for bootstrap stages.
7. Revisit and finalize system-provider policy.
8. Implement system-provider checks only if the policy is approved.
9. Generalize to multiple ordered collections when required.
10. Split feed suggestions from final project policy.
```

This order is not a commitment to implement unresolved provider behavior.

## 17. Reference Invariants

Future discussion should preserve these invariants unless a later decision
explicitly changes them:

1. A collection provides physical port definitions.
2. A logical port is identified by `category/port`.
3. Collection precedence selects one active definition.
4. A group is a build/install context, not a collection or category.
5. A variant is one repeated configuration, ABI, or stage of a logical port.
6. A build instance is `group + resolved port + variant`.
7. Ports declare package dependencies; groups do not replace them.
8. Short aliases are conveniences and must be unambiguous.
9. Project policy has final authority over group membership and variant
   selection.
10. Existing targets remain compatible and imply the `default` variant.
11. Performance work must not preclude normalized variants or dependencies.
12. System-provider behavior remains unresolved until explicitly approved.
