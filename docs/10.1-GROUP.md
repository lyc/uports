# uports Wrapper And Group Architecture Proposal

## Purpose

uports is a FreeBSD ports-inspired build and package system with project group
support. Groups provide a lightweight way to assemble and use project development
environments through readable Makefile settings and ordinary make commands.
Making this easier than introducing a separate configuration system is the
reason for the feature, especially for small-to-medium projects.

Simplicity of use is the primary design criterion. Judge a proposal by the
smallest complete project configuration a user must write: declare required
packages, their build/install environments and what the application consumes.
Routine setup must not require understanding special_groups_all, repeated
environment strings, exclusion tricks or hidden toolchain-profile interactions.
Keep necessary complexity inside the implementation with simple defaults and
explicit, limited overrides; avoid another configuration language or overlapping
public abstractions.

.config is a file format, commonly backed by Kconfig or another configuration
system. Such systems can overlap with package/environment selection, but are
not equivalent to the project-group model. Integration may be offered when
useful; neither project size nor group count alone requires switching to it.
This supersedes the earlier suggestion of a size-based .config cutoff.

Acceptance of group refinements must include a short end-to-end project setup
example, not only framework correctness or additional capabilities. Compare
the user-visible declarations and commands with the existing setup; an internal
refactor that leaves ordinary project configuration difficult is insufficient.

This document proposes a refined group design for uports that preserves and
combines the capabilities already present in:

```text
make/uports/                 reusable ports framework and built-in ports
make/uports/Tools/tools.mk   project-side discovery, planning, and dispatch
feeds/                       external or project-specific ports and policy
top-level Makefile           project configuration
```

The proposal is compatibility-first. It does not move project topology into
individual port Makefiles, and it does not remove existing targets such as:

```text
compiler:clisp.build
host:cmake.install
textproc.build
ports.package
```

The main change is conceptual and structural:

> A build instance is a resolved port variant, built under a group profile,
> for a lifecycle target.

Port identity, collection origin, group profile, and variant should be
represented separately even though the user-facing target syntax may combine
them.

## Current Interface And Proposal Boundary

This report retains the original group redesign proposal. Proposed variables
such as `PORT_COLLECTIONS`, `PORT_GROUP_*` and `PORT_VARIANTS` are not supported
interfaces merely because they appear below. Dated optimization measurements
and the phased outline are historical context, not the current work tracker.

Current selection uses existing `PORTS_*` group/environment variables and
port-owned `FLAVORS`/`FLAVOR` declarations. Wrapper lifecycle requests use
`[group:]port@flavor.phase`, for example `compiler:gforth@libffcall.build`.
The group can be omitted when the short alias resolves uniquely.
`group@category/port` denotes a planner identity, rather than the public
lifecycle target spelling. Explicit default Flavor names normalize to the
existing instance; unqualified root requests can use a project-selected Flavor.

All three dependency lists optionally qualify origins with `@flavor`. Without
it, the provider's declared default is selected independently of project root
selection. Provider groups remain project policy. Named configurations have
separate instance/work/state/package identities; shared providers are
deduplicated. This does not automatically map recipe options or establish safe
coinstallation.

Groups select build/install context; Flavors select port configurations.
Bootstrap stages describe ordered producer steps and dependencies. A Flavor
can identify a stage configuration but does not define ordering by itself.
The cross-toolchain design uses a shared toolchain group and profile-specific
PREFIX roots under DESTDIR, rather than requiring one group per architecture.
See the reusable [Flavor contract](10.5-FLAVOR.md). Project-specific profiles
are documented in the parent's
[cross-toolchain design](../../../feeds/lang/11-CROSS-TOOLCHAIN.md).

Ordered registration is implemented through PORTS_GROUPS. Its first entry
supplies the default; explicit PORTS_GROUP_DEFAULT file/command-line
assignments remain compatibility overrides and must name a declared group.
An inherited environment default does not override the first-entry rule.
Declaration order controls group display, not provider priority or build order.
Names allow letters, digits, underscores and hyphens, excluding a leading
hyphen. Empty/duplicate lists, invalid names, undeclared instance groups and
unknown membership origins fail. Without PORTS_GROUPS, legacy registration and
default behavior remain available.

The existing <group>_lists and environment overrides remain supported. Explicit
default-group membership no longer needs special_groups_all registration in
ordered mode. Ordinary declared groups receive missing context fields under
DESTDIR/<group>, independent of the selected default; project fields are kept.
bs/host retain their built-in native contexts. The custom-group helper
`$(eval $(call uports-native-group,toolchain))` supplies the native DESTDIR/PREFIX
and alternative-source defaults without importing membership, provider policy
or FORCE_REBUILD. Declare its group in PORTS_GROUPS; bs/host already have native
defaults and do not use this helper. Diagnostics are in make info.debug.group,
including PORTS_GROUP_DEFAULT_source. Compact display/filter controls are
described below.
Individual framework debug subtargets, including info.debug.group and
info.debug.instances, are excluded from parent application dependency scanning
just like the aggregate info.debug command.

The current dependency contract, including external providers, scoped
environments, execution and reuse, is maintained in
[10.4-DEPENDENCY.md](10.4-DEPENDENCY.md). Acceptance and next steps belong in
the work tracker and handoff. Historical phases below are not active tasks.

## Five-Group Review And Proposed Refinement

This review describes the current project and a proposed next refinement.
Examples explicitly labelled proposed are not implemented interfaces. The older
four-group model and broad redesign below remain historical design context;
they are not a requirement to implement every proposed configuration layer.

### Current Project Audit

The active project has bs, host, textproc, compiler and toolchain groups.
Recipes remain group-independent. The framework supplies bs/host lists and
standard environments; feeds/group.mk adds project groups, native prerequisite
membership, toolchain selections and provider restrictions.

Let R be the parent DESTDIR, normally project/local, and P the parent PREFIX,
normally /usr/local. These are deployment settings, not fixed host locations.

| Group | Role | Current installation context |
| --- | --- | --- |
| bs | Native bootstrap tools | R + P; FORCE_REBUILD=yes |
| host | Native build tools | R + P |
| textproc | Project text-processing packages | R/compiler + P |
| compiler | Default language/library environment | R/compiler + P |
| toolchain | Native cross-tool producers and prerequisites | Prerequisites R + P; historical producers R/i386-jos-elf |

Work directories carry TYPE_SUFFIX and declared Flavor namespaces. Current
textproc/compiler alternative sources use R/compiler/src; toolchain sources
use R/src. Explicit per-port settings can change these. Preserve existing
paths until a migration is agreed; group membership alone must not silently
relocate work, sources or installations.

The shared origins are devel/libffi, archivers/zlib and math/gmp, math/mpfr,
math/mpc, each in compiler and toolchain. The native libffi/zlib instances use
R/usr/local while compiler instances use R/compiler/usr/local. Historical math
selects mit2018 under R/i386-jos-elf; modern compiler math uses the declared
default. A shared origin is one recipe with separate configured instances.

Current special-group membership removes that origin from implicit default
membership. Restoring both memberships requires explicitly registering compiler
as a special group and listing the shared origins there. That bookkeeping,
duplicated environment construction and per-port PREFIX exclusions account
for much of the complexity; the number five itself is not the problem.

### Additional Application Groups In Scope

Allow future mplane and desktop memberships alongside the current five groups;
do not hardcode a group count or reserve compiler as the only application
default. Read-only inspection of /home/lyc/pj/builds/uports.mplane confirms its
parent Makefile already sets PORTS_GROUP_DEFAULT=mplane. Its feeds/group.mk
currently contains exclusions, rather than a separate mplane membership list.
This is a reference instance, not authorization to migrate or modify it.

| Group | Intended role | Proposed deployment default, overridable |
| --- | --- | --- |
| mplane | Libraries/runtime dependencies for M-Plane application development | R/mplane + P |
| desktop | Libraries/runtime dependencies for large desktop, graphics and multimedia applications | R/desktop + P |

These are project development contexts, not source categories or new framework
classes. The application source/module build remains owned by the parent;
uports supplies its declared package dependencies. Bootstrap/build tools can
remain in bs/host. Explicit provider policy decides whether compatible libraries
may come from another group; do not automatically import all compiler/textproc
members or share installation roots merely because two groups use the host CPU.

A recipe may belong to mplane, desktop and another group with distinct work/
Flavor/environment contexts. Membership syntax must make that straightforward.
Same-root sharing, cross-group provider eligibility and target compatibility
are separate decisions. An application's CROSS_COMPILE selects its target;
native generators/emulators must remain native. Do not infer architecture from
the names mplane/desktop, or introduce implicit bootstrap ordering between them.

Example proposed explicit membership, with ordinary application-group defaults:

```make
PORTS_GROUPS = mplane bs host textproc toolchain desktop
mplane_lists += devel/libffi archivers/zlib
desktop_lists += devel/libffi archivers/zlib
```

The real membership sets and provider policies require their own project audit;
the examples do not claim that libffi/zlib are the complete M-Plane dependencies.
Existing projects must retain their chosen default and installation layout.
The default group may be mplane, desktop, compiler or another valid project name.
Keep groups opt-in: supporting seven possible names does not create every
recipe/group/Flavor combination. Large desktop graphs make demand-driven
metadata, bounded collection, early view filters and a compact group summary
important acceptance cases. Persistent caching remains a separate decision.

Environment composition currently filters per-instance EXCLUDE_ENVS from global
and group ENVS, then appends port EXTRA_ENVS and group/port EXTRA_ENVS, finally
the generated TYPE_SUFFIX. Recursive make retains explicit caller assignment
precedence. The older proposed environment layering below is not an additional
implemented inheritance mechanism.

Provider policy remains independent of membership. Current host allows host/bs
uports providers; toolchain allows toolchain/host/bs/compiler. Validated native
system discovery remains enabled. Exact same-group origin wins before same-group
capabilities and unique allowed fallback; missing/ambiguous providers fail.
Dependency origin categories do not specify provider groups. Unqualified
dependencies select declared default Flavors, independently of project-selected
root Flavors. Do not simplify configuration by changing these rules implicitly.

Groups isolate build/state identities, not necessarily installation roots.
bs and host deliberately share a deployment context. Two groups selecting the
same package identity and root can refer to one installation receipt; they do
not acquire independent installed copies merely through TYPE_SUFFIX. Different
Flavors/versions with overlapping paths still cannot safely coinstall. Future
multi-group configuration must diagnose work/alternative-source collisions and
make deployment sharing explicit, preserving package ownership checks.

### Recommended Configuration Direction

Prefer a small extension of the existing group interface over adopting all the
older PORT_GROUP/PORT_VARIANTS proposal. Keep group/Flavor/stage meanings and
the normalized instance boundary. Do not add profiles to the reusable framework
as a new mandatory public concept.

Group registration uses one ordered public list, PORTS_GROUPS. Like
FLAVORS, its first entry selects the default when no explicit compatibility
override is supplied. Preserve declaration order; never sort this list to
derive the default or display order. The project declares every active group,
including bs/host when needed; framework-provided membership/environment
defaults do not silently prepend a group or change the first entry.

```make
PORTS_GROUPS = compiler bs host textproc toolchain
```

An M-Plane project can instead start with mplane. Keep PORTS_GROUP_DEFAULT as
an explicit compatibility override initially; when PORTS_GROUPS is present,
that override must name a declared group. New configurations normally use only
the ordered list. Legacy projects without PORTS_GROUPS retain their existing
registration/default behavior during migration. An explicitly empty new list,
invalid names or duplicates should fail clearly rather than choose a different
default silently. Environment-derived legacy defaults must not accidentally
override the new first-entry rule; define and report override provenance.

Existing <group>_lists membership remains usable. Explicit entries in the
default group's list are honored without special_groups_all hacks.
Initially preserve today's fallback behavior: a port with no explicit membership
enters the default group; explicit membership names its groups. Do not silently
make every custom-group port also a compiler port.

Current shared-membership bookkeeping:

```make
special_groups_all += toolchain compiler
toolchain_lists += devel/libffi archivers/zlib
compiler_lists += devel/libffi archivers/zlib
```

Equivalent using the ordered interface:

```make
PORTS_GROUPS = compiler bs host textproc toolchain
toolchain_lists += devel/libffi archivers/zlib
compiler_lists += devel/libffi archivers/zlib
```

Keep membership, environment and provider policy in three short sections of
feeds/group.mk, rather than splitting them into more configuration files.
The native-environment helper lets a custom group avoid copying the host
construction by hand:

```make
$(eval $(call uports-native-group,toolchain))
```

It provides native DESTDIR/PREFIX and alternative source defaults; later explicit
overrides remain available. It does not inherit host
dependency policy, membership, FORCE_REBUILD or source sharing accidentally.
Keep existing ENVS/EXTRA_ENVS/EXCLUDE_ENVS as compatibility escape hatches.
Decide any typed PREFIX helper only after the simple helper is demonstrated
against current producer exceptions; avoid adding a large parallel schema.

Keep DEPENDENCY_PROVIDER_UPORTS_GROUPS.<group> as the policy declaration rather
than creating another spelling. Group order controls default selection and
display order only; it is neither dependency build order nor provider priority.
Recipes continue declaring dependencies; the graph determines execution and
explicit provider policy/resolution rules determine provider precedence.
Unknown membership origins should diagnose typos; activation of planned recipes
must be an explicit project choice rather than silently hiding misspellings.

### Simplicity Review And Minimal Project Setup

Preserve the original two-file ownership model:

| File | Responsibility |
| --- | --- |
| make/uports/Tools/group.mk | Framework base bs/host membership and reusable group helpers |
| feeds/group.mk | Project group order/membership, context exceptions and provider policy |
| Parent Makefile/module.mk | Project paths, public targets and application integration |

tools.mk remains the normalization/dispatch engine. It loads framework
Tools/group.mk first, then project feeds/group.mk. Base-group definitions do
not silently prepend bs/host to an explicitly ordered project group list.
Projects normally reuse their framework memberships rather than copying them.
The new native helper is defined in the base file and called in the project
file; it does not move toolchain or MIT policy into the framework.

For a minimal native project whose only selected external library is the
existing self-contained textproc/ezxml recipe, the ordered-group interface is:

```make
# Parent Makefile
FEEDS = $(CURDIR)/feeds
DESTDIR ?= $(CURDIR)/local
PREFIX ?= /usr/local
include $(CURDIR)/make/uports/Tools/tools.mk
```

```make
# feeds/group.mk
PORTS_GROUPS = mplane bs host
PORTS_LISTS = textproc/ezxml
```

```sh
make mplane.install
make mplane:ezxml.install
```

The default is mplane; framework defaults place the library under
DESTDIR/mplane + PREFIX. The explicit command is an alternative to the group
aggregate, not a required second install. No special_groups_all, repeated
environment string, TYPE_SUFFIX declaration or native helper is needed for
this ordinary application group. This example illustrates package environment
setup, not the complete M-Plane application/dependency set or its module build.
Projects with transitive providers need those available in the selected root/
fallback instance set; the current planner does not automatically select every
discovered recipe just because a dependency references it.

For the current toolchain project, native context setup is one declaration:

```make
$(eval $(call uports-native-group,toolchain))
```

Listing libffi/zlib in both compiler_lists and toolchain_lists already expresses
coexisting instances without re-registering compiler as a special group.
However, this is not yet the complete simple multi-group project interface:

- Explicit PORTS_LISTS currently bypasses normal <group>_lists assignment.
  Shared roots can still require group-qualified internal selection entries.
  A follow-up should let ordinary recipe selection compose with declared
  memberships, preserve explicit instance selections and legacy behavior, and
  diagnose root/fallback overlap. Do not silently change this during a display
  or configuration-formatting patch.
- Root package selection and dependency-only provider availability remain
  separate declarations. Review the smallest real multi-library example before
  adding another convenience variable or implying automatic provider expansion.
- The project still carries per-port PREFIX exclusions and Flavor/profile
  consistency guards. These belong behind the agreed public toolchain mapping;
  they are not normal application-group setup requirements. Decide recipe-owned
  PREFIX policy explicitly rather than infer it from a port name.
- textproc intentionally shares compiler's deployment/source context. Its
  repeated environment string can be reduced to the actual differing context
  fields using existing default filling. Validate effective values and state/
  package compatibility before changing that declaration; string simplification
  must not cause gratuitous rebuilds.

Review result: ordered registration and native defaults improve the common
case and preserve existing behavior, but the full current toolchain group file
is not yet a model of minimal user configuration. Keep these improvements
bounded; address root/membership composition and public toolchain mapping in
separate changes. Compact display is useful but does not resolve configuration
complexity. Do not add a new configuration-file hierarchy or generic profile
language to hide unfinished project policy.

### Deeper Review Of On-Demand Group Instances

Decision: defer this possibility. The user considers its unresolved semantics
too broad for the current refinement. It is not an active implementation plan
or a prerequisite for finishing ordered groups/native defaults and compact
info.ports. Retain the assessment for a later discussion; preserve current
recipe selection, membership, aliases and provider rules in the meantime.

This section evaluates a possible next model; it does not describe implemented
behavior. A declared group defines an environment, and an explicit request
such as desktop:libffi.stage can create that known recipe's instance without
requiring prior membership in desktop_lists. Arbitrary recipe/group combinations
are not automatically valid or safe to build/install concurrently.

Current code is more tightly coupled: PORTS_LISTS limits ports_all_raw;
port lookup records and group instances are generated from the selected set;
resolve-unflavored-port-target accepts only generated targets; provider candidates
come from ports_all_group; metadata job targets and snapshots assume those base
instances already exist. Flavor creation is lazy above an existing group/port
base. Thus this is not just a target-parser change, although normalized
group/origin/Flavor identities can be retained.

Benefits if implemented narrowly:

- An explicit command selects its environment directly without membership edits
  or repeated PORTS_LISTS/group declarations for an ad-hoc build.
- One recipe remains reusable across project contexts; recipe Makefiles stay
  independent of group names.
- Separate cheap recipe availability from configured aggregate roots and actual
  invocation instances internally, rather than expose more public configuration
  knobs. Existing group environments/helpers remain the source of settings.
- A later closure collector could avoid unrelated metadata, but on-demand target
  creation alone does not deliver that performance improvement.

| Concern | What could worsen | Required boundary |
| --- | --- | --- |
| Metadata cost | Creating every recipe/group combination multiplies probes | Create requested instances only; never eagerly form the Cartesian product |
| Provider resolution | Automatic same-group instances can replace current providers or introduce ambiguity | Keep configured candidate sets and explicit provider policy initially |
| Native tools vs target libraries | A build generator can inherit a cross-target environment | Preserve build/lib roles and reject incompatible contexts |
| Project aggregates | group.install could unexpectedly mean every available recipe | Keep explicit configured roots; ad-hoc requests do not redefine future aggregates |
| Short aliases | cmake.install could move from host to the default application group | Preserve existing configured alias resolution; explicit group requests are unambiguous |
| Work/source isolation | Different groups can still share an alternative source root | Check effective mutable paths; namespace or reject collisions before parallel work |
| Installation/package reuse | Same package/root shares ownership; cached filenames can coincide | Preserve ownership/compatibility checks; audit concurrent cache publication |
| Cleanup/display | Ad-hoc instances may disappear from the next invocation's configured set | Support explicit cleanup, distinguish configured/available status, avoid probing all combinations |
| Recursive metadata/state | Child makes may lack the newly created base-instance mapping | Carry/reconstruct dynamic identity and context in invocation snapshots |

At the measured59 logical recipes and64 configured instances, an eager seven-
group product would create413 base instances before Flavor expansion. This
would reverse the recent performance improvement. Even a narrow explicit
constructor can slightly add to current full-set metadata cost until collection
is made demand-driven. Do not describe this interface change as an automatic
performance fix or impose a hard recipe-count limit instead of measuring it.

The most important semantic risk is provider creation. Current jos12 GCC uses
compiler-group modern GMP/MPFR/MPC because historical toolchain membership is
absent in that profile. Automatically creating toolchain-group defaults would
change that choice. Native build tools similarly must not be instantiated in
an application target environment merely because same-group lookup is easy.
Do not infer roles from categories such as devel/lang.

Lazy lookup also cannot discard capability discovery. autoconf-switch declares
PORT_PROVIDES=devel/autoconf; exact-directory lookup alone will not reproduce
current resolution. Keep curated provider metadata/discovery until a proven
capability catalog or bounded discovery scheme replaces it. Dynamic dependencies
and Flavor-dependent capabilities make a simplistic file-name scan insufficient.

Concurrency needs stronger qualification than distinct TYPE_SUFFIX. Native
custom groups currently default alternative sources to DESTDIR/src, and
textproc/compiler deliberately share a source/deployment context. The same
recipe/Flavor in those contexts may therefore share mutable sources even though
work directories differ. Different groups can also share one installed receipt.
Preserve validated layouts; diagnose or explicitly resolve such collisions
rather than silently relocate existing source trees.

Recommended staged choice:

1. Add lazy construction only for explicit qualified requests in the new ordered
   group interface. Require a declared group, a known unambiguous recipe and a
   supported Flavor/context. Keep legacy mode and configured short aliases.
2. Keep configured memberships as aggregate roots and existing dependency
   candidate/policy behavior initially. Newly requested roots join only their
   invocation. Missing providers still diagnose; do not invent a same-group copy
   that overrides an existing provider. Preserve explicit cleanup targets.
3. Separately simplify project root/provider declarations and collect the actual
   dependency closure, once capability discovery, native/target routing and
   snapshot/state identity have explicit acceptance cases. Group lists may then
   become project root declarations rather than availability restrictions, but
   that migration must not silently reduce this project's current compiler roots.

This partial model delivers the direct-command benefit with a smaller semantic
change. Keeping the static model and only fixing PORTS_LISTS composition is less
work but retains membership edits for ad-hoc environments. Fully dynamic root
and dependency instantiation is the largest change and is not recommended as
one immediate rewrite. The earlier4-6-slice estimate applies to complete support,
not just parsing a previously unavailable target.

Before implementation, settle explicit-request availability versus project
ignore/selection rules, short-alias behavior, aggregate/cleanup scope and source
collision handling. Use current libffi/zlib dual groups, historical/jos12 math,
autoconf-switch capability, native Python generators, gforth Flavors and installed
package conflicts as real cases. Compare plans, effective paths/environments,
snapshot reuse and performance; no synthetic recipe matrix or full rebuild suite.
This proposal does not discard PORTS_LISTS compatibility, redefine all current
membership lists, activate desktop/mplane or change the public toolchain plan.

### PROJECT_PORTS Discovery, Performance And Migration Review

This review establishes the PROJECT_PORTS implementation contract. Ordered
groups, the native helper, root inspection, bounded planning and project
lifecycle dispatch and compact listing are implemented. Project migration
remains pending.
This review does not reopen unrestricted on-demand group commands. Its scope
is explicitly declared project roots and the providers needed to satisfy them.

The proposed user model keeps two configuration owners. Tools/group.mk supplies
base environments/native provider defaults and reusable helpers. feeds/group.mk
declares PORTS_GROUPS, ordinary named package-set variables and PROJECT_PORTS.
Do not require another configuration file or make group order a provider policy.

```make
PORTS_GROUPS = mplane bs host desktop
mplane_ports = ezxml libyang2
desktop_ports = desktop:pixman
PROJECT_PORTS = $(mplane_ports) $(desktop_ports)
```

Named sets are ordinary Make variables combined into one list, not independent
project objects. Proposed entries are [group:]port[@flavor], without a lifecycle
phase. Unqualified entries use the configured default group. Normalize through
the existing recipe/collection lookup and Flavor declarations; reject unknown
or ambiguous names. Deduplicate identical group/origin/Flavor instances, not
different instances of the same recipe.

#### Existing Behavior And Real Evidence

PORTS_LISTS/PORTS_FALLBACK_LISTS restrict both lookup records and instantiated
provider candidates. An available recipe outside that selection cannot simply
satisfy a dependency. Metadata probes cover the selected set, not automatically
the requested dependency closure. Extra root Flavor prefetch and invocation
snapshots reduce overhead but do not change this selection model.

With current actual recipes, selecting only toolchain@emulators/qemu-mit failed
planning: Python2, pkg-config, GLib, Pixman and zlib had no allowed selected
provider. Supplying the known nine dependency-only instances restored the exact
accepted10-instance plan. That narrowed plan took2.81s versus the user's6.544s
full-set measurement. These are different workload selections, not proof that
an unimplemented automatic collector achieves2.81s. Logs:
/tmp/uports-project-ports-{root-only,closure-plan,closure-time}.log.

Read-only inspection of uports.mplane/make/ports.mk found14 application roots
plus an optional test root, with seven native bootstrap/host fallback instances.
Its separate policy enables validated host discovery. This is useful migration
evidence: roots and provider availability already have distinct purposes.
Do not edit or migrate that reference checkout as part of this review.

Aggregate expansion also differs today. ports.install and category installation
use configured roots, while a group installation aggregate includes selected
fallback instances of that group. clean/distclean include fallback work trees.
These findings come from expansion of the actual QEMU configuration, not an
executed install/cleanup. /tmp/uports-project-ports-aggregates.log records it.

#### Recommended Dependency Discovery Contract

Keep three internal sets: available recipe catalog, explicit project roots,
and providers reached for the current invocation. They need not become three
user-maintained lists. PROJECT_PORTS must describe roots, not every transitive
dependency and not all possible recipe/group combinations.

1. Normalize project roots, collect their actual selected-Flavor metadata and
   preserve explicit recipe requests even when a system library could satisfy
   another consumer's dependency.
2. Resolve edges using existing system/SDK policy and configured compatible
   uports providers first. Keep exact-origin/capability precedence, native/target
   context and explicit ambiguity errors. Never replace a working configured
   provider merely by manufacturing a same-group copy.
3. Framework bs/host lists can provide a bounded native-tool candidate pool
   without becoming installation roots. Probe only the relevant pool/candidates;
   actual metadata still validates versions, roles and PORT_PROVIDES aliases.
4. If no selected provider exists, proposed automatic exact-origin discovery
   must choose a permitted context deliberately: libraries normally use the
   consumer's target context; build generators use a compatible native context.
   Discover recursively until a fixed point, deduplicate, validate cycles and
   freeze the graph before execution. Missing/ambiguous contexts must fail.
5. Source/Flavor-dependent dependencies require actual make evaluation. Directory
   names alone cannot discover aliases such as autoconf-switch providing
   devel/autoconf. Preserve bounded capability discovery or require an explicit
   exceptional binding; do not pretend a static name scan is complete.
6. Reuse one invocation snapshot for nested planning/state/provenance. Any new
   provider instance must carry its identity, environment and context into that
   snapshot. Preserve root-scoped source overrides and installation compatibility.

The implementation contract below settles item 4 and exceptional capability
bindings for the next implementation. Automatic dependency-provider construction
is real new functionality,
even though arbitrary user requests outside PROJECT_PORTS remain deferred.
Without it or an equivalent bounded discovery mechanism, PROJECT_PORTS would
only rename PORTS_LISTS and still require manual transitive fallback lists.

#### Performance Boundary

Keep initial recipe discovery lightweight, respecting feed override precedence
and ignored definitions. Do not parse/build a recipe in every declared group.
Collect only the requested roots/provider pool/closure, using the committed
bounded jobs, deterministic output and invocation reuse. No persistent cache
is required initially. Discovery of unknown capabilities may still require a
bounded pool scan; report this cost separately instead of promising zero scans.

Measure catalog lookup, provider discovery, port probes, Flavor expansion and
graph resolution separately. Acceptance needs the same selected versions,
provider groups, effective flags/paths and errors as existing real plans, plus
bounded probe growth when unrelated recipes/groups are available. A hard recipe
count limit is not a substitute for controlling active metadata work.

| Short lifecycle aliases | Retain established configured-instance preference; do not silently move cmake from host to an application group |
| group.install / ports.install | Recommend project roots plus their dependency closure; changing current group-fallback behavior needs explicit agreement |
| Cleanup / display | Define project/visited provider scope explicitly; never expand cleanup to all inventory or trust cookie status as ownership |
| Existing caches/receipts/state | Preserve identity or diagnose incompatibility; do not rebuild merely because declarations are rewritten |

Multiple root Flavors in PROJECT_PORTS need an explicit normalized root set.
Existing group/port project_flavor stores only one project selection, although
the dependency planner can represent a multi-Flavor request union. Reuse that
capability rather than encode two Flavors into one environment assignment.
Thus migration is not a mechanical variable rename.

#### Implementation Contract After Review

This contract supersedes open alternatives in the preceding review and table.
The next implementation follows these boundaries. They apply only when
PROJECT_PORTS is defined; existing projects retain legacy behavior until they
deliberately migrate. These are design decisions, not completed functionality.

- PROJECT_PORTS contains explicit roots. Ordinary Make variables combine named
  package sets. An empty value selects no roots. Each entry identifies a
  group/origin/Flavor instance; omitted group means the configured default and
  omitted Flavor means the recipe's declared default. Keep distinct Flavors
  of one recipe as separate roots and deduplicate identical instances.
- Resolve dependencies against existing configured providers and external
  policy first. Only when none satisfies the edge may discovery construct an
  exact-origin provider in a permitted context. Library dependencies normally
  retain the consumer's context. Build dependencies retain existing native/
  target role rules; BUILD_DEPENDS alone does not prove a native generator.
  Reject missing or ambiguous contexts instead of choosing the first group.
- Keep bs/host defaults as a bounded provider pool. Existing project group
  lists and PORTS_FALLBACK_LISTS remain compatibility provider bindings in new
  mode; they do not add roots. A migration must put any desired installation
  roots from those lists into PROJECT_PORTS explicitly. Do not change the
  meaning of those lists in legacy mode.
- Preserve capability matching through evaluated PORT_PROVIDES metadata in
  the configured provider pool. Do not invent a new public binding variable
  initially: exceptional aliases can use existing provider declarations and
  policy. An alias outside the bounded pool must produce an unresolved-provider
  diagnostic rather than trigger a scan of every recipe in every group.
- ports.install starts from all project roots; group.install starts from roots
  in that group. Both execute the required closure through existing dependency
  phase rules. A provider is installed because a selected root needs it, not
  merely because it belongs to the group. Explicit provider targets remain
  available. This intentionally removes implicit fallback roots in new mode.
- Aggregate clean/distclean operate on declared roots only in new mode. They
  must not recompute, build, install or remove shared dependency providers.
  Clean a provider through its explicit qualified target when needed. Neither
  cleanup nor listing depends on a previous invocation's visited set.
- Listing includes declared roots and explicitly configured provider instances,
  distinguishes their roles, and preserves declared Flavor visibility. Automatic
  providers appear in dependency-plan diagnostics; listing them must not require
  a full dependency scan on every info.ports invocation.
- Preserve established aliases for configured instances. Require qualification
  when multiple root instances remain ambiguous; never silently redirect a
  host tool to the default application group. Snapshot, provenance, state and
  dispatch must carry the same normalized identity.

Implement in reviewable steps: first normalize roots and reject conflicting
selectors without changing legacy mode; then add bounded provider discovery
and snapshot integration; finally wire aggregate/display semantics and migrate
the active parent configuration. Do not expose an execution path whose provider
closure or instance identity is incomplete. Each step needs actual metadata/
plan comparison before execution is enabled. Keep project migration separate
from framework changes and defer commits until requested.

#### Metadata Probe Evaluation

Single-goal uports-port-status-metadata, uports-dependency-metadata and
uports-flavor-metadata probes evaluate stable architecture, OS and version
values once after port declarations are complete. Repeated path/cookie
expansion must not rerun the same uname and version-conversion shell commands.
Mixed lifecycle goals retain normal evaluation. The dependency planner likewise
evaluates its build-host facts once when records load. Explicit caller values
remain authoritative; this requires no persistent cache or provider-policy
change.

#### Root Inspection Implementation

The first implementation step adds Tools/project.mk and the read-only target
project-ports-list. For example:

```sh
make 'PROJECT_PORTS=gforth compiler:lang/gforth@default gforth@libffcall textproc:ezxml' \
  project-ports-list
```

Output is group|origin|flavor, with a header. Short names and category/port
entries resolve against the available recipe catalog, with existing feed
precedence. Groups must already exist. The target evaluates each requested
recipe's Flavor metadata in its group environment, overriding any inherited
Flavor selection so an omitted Flavor uses the recipe's declared default.
The implicit and explicit default collapse to one root after evaluation;
different Flavors remain separate. Validation completes before rows are emitted.
An explicitly empty PROJECT_PORTS prints only the header.

Root probes use DEPENDENCY_METADATA_JOBS (default four), with private per-root
files and output emitted in declaration order after successful collection.
Default normalization/deduplication therefore remains deterministic. A failed
batch stops scheduling further probes and reports errors without partial rows.

Malformed entries, unknown recipes/groups, ambiguous short names, unsupported
Flavors and simultaneous PROJECT_PORTS/PORTS_LISTS declarations fail. The conflict
diagnostic reports Make assignment origins; it does not report file line numbers.
No provider graph is collected by this inspection target. Existing projects
with PROJECT_PORTS undefined retain their selection and execution behavior.
Planning and lifecycle dispatch below consume the same root declarations.

#### Bounded Provider Discovery And Snapshots

Tools/project-dependency.mk adds read-only project-dependency-plan and
project-dependency-snapshot targets. PROJECT_PHASE selects one supported phase,
defaulting to install. These targets share the existing dependency resolver,
external-provider projection, Flavor expansion, cycle check and execution-plan
renderer; they do not execute the displayed targets.

```sh
make 'PROJECT_PORTS=toolchain:qemu-mit@mit2018' PROJECT_PHASE=stage \
  project-dependency-plan
make 'PROJECT_PORTS=gforth gforth@libffcall' project-dependency-plan
```

Initial metadata covers root base instances and explicitly configured group/
fallback provider bindings. The lightweight catalog retains implicit legacy
default-group origin bindings without evaluating every recipe. Existing
configured/external providers are resolved first. An unresolved active edge
can bring in its permitted configured origin binding lazily; otherwise an
exact-origin provider may be created in a compatible context. Prefer the
consumer context when permitted, otherwise require exactly one compatible
context. Group declaration order is not a tie breaker. Capability aliases
still require evaluated metadata from the configured pool. Invalid Flavors,
incompatible selected providers and ambiguous existing providers are errors,
not reasons to construct replacement copies.

Each added base is probed once and appended to invocation metadata. Re-resolve
until no new instance is added, retaining collected base/variant metadata.
Only PROJECT_PORTS entries choose root Flavors in this mode: legacy per-port
root selections do not activate unrelated variants. Dependency declarations
continue selecting provider Flavors, including explicit defaults.

Snapshots include project-instance|group|origin records before ordinary
dependency metadata, including discovered variants. A subsequent diagnostic
with UPORTS_DEPENDENCY_INVOCATION=yes and DEPENDENCY_METADATA_SOURCE set to that
file reconstructs base instances and imports variants. No persistent cache is
introduced. Reusing a snapshot requires the same root requests, phase and
effective project configuration, as with the existing invocation mechanism.
External provider validation still runs; a snapshot is not permission to skip
policy checks. Lifecycle dispatch uses this snapshot as described below.

Real checks cover QEMU's unchanged 10-instance plan, gforth's seven-instance
default/libffcall union and byte-identical snapshot replay, MIT2018 historical
math versus jos12 compiler-group modern math, restricted provider policy and
cycle rejection. Independent provider tie order can differ from a full catalog
plan because only reached implicit bindings are materialized; dependencies
still precede consumers. These are metadata/plan checks, not new build or
runtime validation and not an automatic-discovery performance claim.

Keep metadata collection bounded and reuse work within an invocation: expand
only reached phase/Flavor dependencies, collect new provider frontiers in
parallel, and reuse native discovery during re-resolution. The metadata probe
evaluation described above applies to all three metadata interfaces. No
persistent cache is required.

The gforth union plan took 1.60s locally after these changes, with byte-identical
plan and snapshot output; the user confirmed 1.556s. The user observed 6.451s
before the host/version-value change. This configuration still probes 37
configured bases plus one root
variant and three reached providers to preserve capability resolution; it is
not a seven-probe-only collector. Timings vary with host load.

#### Project Lifecycle And Aggregate Dispatch

Tools/project-lifecycle.mk connects declared roots to the existing port wrapper.
It evaluates the requested roots' actual Flavor metadata, deduplicates equivalent
default selections, then dispatches canonical group:port[@flavor].phase targets.
A short request prefers roots in the default group; otherwise one remaining
group/Flavor instance is required. A single selected extra Flavor can use the
short port alias. Multiple distinct Flavors require an explicit selection for
an individual port request. Non-root build/install requests fail before execution.

```sh
make 'PROJECT_PORTS=gforth@libffcall' gforth.stage
make 'PROJECT_PORTS=gforth gforth@libffcall' compiler.stage
make 'PROJECT_PORTS=toolchain:qemu-mit@mit2018' toolchain.stage
```

ports.phase selects all declared roots; group.phase and category.phase filter
those roots. Configured provider-only instances are not aggregate roots. An
empty project/group/category selection is a no-op. For dependency-aware phases,
collect one invocation snapshot for the selected union, validate and execute its
providers first, then dispatch consumers using the existing state/environment/
provenance machinery with that snapshot and private context storage. Preserve
UPORTS_DEPENDENCIES=yes/no/none and the caller's state/provenance settings. Source
phases and checksum/makesum use direct root dispatch without a dependency graph.
Cached install and FORCE_DEVELOPMENT_INSTALL retain their existing contracts.

Aggregate clean/distclean/deinstall/uninstall select declared roots only and
bypass dependency execution/state collection. An explicit group-qualified
provider cleanup/removal request remains available even if it is not a root;
it uses that recipe's configured context. For example:

```sh
make 'PROJECT_PORTS=gforth gforth@libffcall' compiler.clean
make 'PROJECT_PORTS=gforth' compiler:libltdl.clean
```

Cleanup never expands to every recipe in the catalog or to a previously visited
provider set. Default and extra Flavors still have independent work/state paths.
Selecting multiple Flavors does not make overlapping installation paths safely
coinstallable: existing package ownership checks remain authoritative.

The real ezxml wrapper check covers isolated build/package/install, installed
XML parsing, a no-work second install, root cleanup without removing installed
files, deinstallation and cached reinstallation. Its package cache and deployment
root are private test paths. Flavored gforth wrapper metadata and root/aggregate
selection checks cover the alias/Flavor boundary. Provider-bearing gforth and
QEMU lifecycle validation is tracked in the handoff before slice closeout.

#### Review Result

The proposed names and ordinary package sets improve clarity, but dependency
availability is the substantive implementation work. Preserve the two-file
ownership model and legacy mode. Compact listing and parent migration remain
separate from lifecycle integration. Do not redesign provider priority silently.

Use the implementation contract above for separate framework/project changes.
Use QEMU's accepted10-instance
plan, historical vs jos12 math, gforth's Flavor union and M-Plane's real root/
fallback configuration as acceptance references. No recipe builds, installation
changes or compatibility migrations were performed during this review.

### Compact Listing

info.ports defaults to one logical row per resolved recipe origin, combining
group-instance summaries without merging their state. It retains the leading
[*I]: format. Its status follows the primary group's declared default, with the
configured PORTS_GROUP_DEFAULT primary when present; otherwise use stable
display group order. This includes projects whose default is mplane or
desktop. These are cookie states, not proof of installed file health. Group
and Flavor selections remain visible in the summaries.

Example layout (status values depend on the working tree):

```text
[*I]: devel/libffi  v3.4.6  BSD3CLAUSE  toolchain:I compiler:I
[* ]: archivers/zlib 1.3.2 zlib        toolchain:I compiler:.
[*S]: lang/gforth 0.7.9_20260610 GPLv3+ compiler:{default:S, libffcall:S}
```

Declared extra Flavors remain visible without cookies, including after distclean.
The primary version and license are printed once; differing values annotate their
instance entries. Distinct configurations remain separate even if both show I.
Every compact output line starts with four spaces. If the group summaries do
not fit on one line, each group occupies its own line, aligned with the
GROUPS/FLAVORS column. A group's Flavor entries stay together. Compact mode
omits the large group-member listing; a short ordered group summary identifies
the default instead.

Both views display nondefault groups in reverse declaration order, followed by
the default group last. This affects summary/member sections, detailed instance
rows and compact group cells only; group declarations and provider policy retain
their existing order and meaning. The compact leading status still prefers the
default group's declared default Flavor even when its cell appears last.

When PROJECT_PORTS is defined, the last status position is - for rows not
selected in it: [*I-] is an installed default-group provider-only recipe.
Selected rows leave that position blank: [*I ]. Compact rows count as selected
if any displayed group/Flavor instance is selected; detailed rows check their
group context. Group/Flavor entries do not carry root labels. This display does
not discover automatic providers or compute a dependency graph. Unknown selected
Flavors fail when their context is collected.

Controls:

```sh
make info.ports
make INFO_PORTS_VIEW=detailed info.ports
make INFO_PORTS_GROUP=toolchain INFO_PORTS_PORT=math/gmp info.ports
make 'PROJECT_PORTS=gforth@libffcall' INFO_PORTS_PORT=gforth info.ports
```

INFO_PORTS_GROUP and INFO_PORTS_PORT accept whitespace-separated groups and
short names/origins respectively. Filters apply before status collection; they
do not create new instances. A known recipe with no matching active instance
produces an empty listing. Unknown filters and views fail explicitly. There is
no cookie-state filter in this implementation.

Both views consume the same ordered status rows and bounded INFO_PORTS_JOBS
collection. There is no second metadata pass or persistent cache. Context row
indexes let the compact renderer enumerate Flavors without rescanning every
row for each context. Both views reserve the last status position for project
selection. Rendering remains independent of execution.

Keep the agreed public commands make i386-jos-elf and
make CROSS_COMPILE=i386-jos-elf. The tuple selects the historical MIT2018 mapping;
internal configuration coordinates recipe Flavors, producer roots and consumer
tool paths. A group is not that mapping, and a bootstrap stage is not a group.
The generic framework must not hardcode MIT versions or tuple aliases.

Review whether TOOLCHAIN_PROFILE remains necessary internally after group
configuration is simplified. Do not remove it until both historical and jos12

isolation from consumer CROSS_COMPILE. Keep the existing agreed tuple/PREFIX/
DESTDIR layout and explicit ambiguity handling for shared i386 target tuples.

### Scope And Acceptance Before Implementation

Agree registration/membership semantics, helper scope and compact-view contract
first. Then implement membership/environment conveniences, display/filtering

compatible initially; do not implement the old broad redesign wholesale.

Use current libffi/zlib dual memberships, historical vs modern math, gforth's
two Flavors, host restrictions, same-root package conflicts and QEMU as real

No persistent cache or recipe-source migration is part of this proposal.
Include a non-compiler default-group case based on the mplane reference, and
an actual desktop dependency set once selected. Do not fabricate a large
synthetic desktop fixture or modify the preserved mplane checkout for testing
without authorization.

## Architecture Boundaries

The system has four distinct layers.

### Port Layer

A port is identified by:

```text
category/port
```

Examples:

```text
lang/clisp
devel/cmake
textproc/expat2
```

A port Makefile declares package behavior:

- source and version;
- dependencies;
- configure and build options;
- patches;
- staging and packaging behavior;
- package manifests.

A port should not need to know whether it came from built-in uports or a feed,
which project selected it, or which project group will build it.

### Port-Collection Layer

Port definitions can exist in multiple collection roots.

The current roots are:

```text
make/uports/<category>/<port>
$(FEEDS)/<category>/<port>
```

`FEEDS` may point inside or outside the current repository.

The current resolver gives a feed port precedence over a built-in port with the
same `category/port`. The resulting package set is therefore a merged logical
port collection, not two unrelated collections.

### Wrapper Layer

`make/uports/Tools/tools.mk` is the project-side wrapper. It currently:

- discovers built-in and feed ports;
- applies feed-over-built-in override precedence;
- validates `PORTS_LISTS`;
- assigns groups;
- calculates group and port metadata;
- composes per-instance environments;
- generates port, category, group, and global targets;
- chooses the physical source directory for a resolved port;
- exports selected host tools;
- dispatches lifecycle targets to the real port Makefile;
- reports package and build status.

This is the correct ownership layer for project group topology.

### Execution Layer

`make/uports/Mk/linux.port.mk` and related files implement one port's lifecycle:

```text
fetch -> extract -> patch -> configure -> build -> stage -> package -> install
```

The execution layer consumes the environment supplied by the wrapper. It
should not need to understand the complete project group graph.

## Historical Four-Group Model

A group is a build and installation context, not a package category and not a
port collection.

The current internal and target-oriented representation is:

```text
group@category/port
```

Examples:

```text
bs@devel/autoconf-2.72
host@devel/cmake
textproc@textproc/expat2
compiler@lang/clisp
```

The current special groups are declared through:

```make
special_groups_all += bs host textproc
```

Membership uses:

```make
bs_lists       = ...
host_lists     = ...
textproc_lists = ...
```

The wrapper defines:

```make
PORTS_GROUP_DEFAULT = compiler
```

Ports without an explicit special-group assignment enter `compiler`.

The effective groups are:

```text
bs
host
textproc
compiler
```

## Capabilities That Must Be Preserved

Any redesign must retain the following existing behavior.

### Collection Override

If both roots contain:

```text
make/uports/lang/example
feeds/lang/example
```

the feed version is selected.

Group membership applies to the resolved logical port `lang/example`, not
separately to both physical directories.

### External Feeds

`FEEDS` is a path supplied by the project. It may refer to an external
collection. The wrapper must not assume that feeds live below the project root.

### Port Selection

`PORTS_LISTS` can restrict the active port set and may include explicit grouped
entries.

`PORTS_FALLBACK_LISTS` adds selected build instances that dependency resolution
may choose without making them roots of category, global, or legacy
`ports` build/install aggregates. Explicit group commands operate on every
selected instance in that user-defined group, including fallback instances,
for every lifecycle phase. Category, group, and global `clean` and
`distclean` aggregates include all selected instances, including fallbacks,
so their work trees and completion cookies are cleaned as well.
Fallback instances retain canonical and short lifecycle
targets and participate in metadata, capability, graph, and execution planning.
They are dispatched automatically only when a resolved dependency selects them,
or directly when the user requests their lifecycle target.

Fallback selection requires an explicit `PORTS_LISTS`; an instance cannot
appear in both lists.  This keeps the default all-ports behavior unchanged and
makes root ownership unambiguous.

Unknown selected packages currently fail early. That validation must remain.

### Default And Explicit Groups

Special membership is applied first. Ports without an explicit group receive
`PORTS_GROUP_DEFAULT`.

### Multiple Build Instances

A logical port may be built in more than one group. Each group build has a
separate environment, work suffix, destination, and target.

A logical port may also be built more than once within the same group when it
declares variants. Variants represent configurations, ABIs, or bootstrap
stages of the same port definition. Each selected group-port-variant
combination must have a separate work identity, package identity, and target.

### Environment Overlays

The current environment composition supports:

```text
PORTS_ENVS
PORTS_<group>_ENVS
PORTS_<port>_EXTRA_ENVS
PORTS_<group>_<port>_EXTRA_ENVS
PORTS_<group>_<port>_EXCLUDE_ENVS
TYPE_SUFFIX
```

This is an important capability. The redesign should normalize it, not replace
it with a less expressive model.

### Work And Type Suffixes

Groups derive suffixes used for work directories and package/build identity.
This permits the same port to be built in multiple contexts without sharing
state incorrectly.

### Host Tool Export

`USE_HOSTTOOLS` selects a group whose installed tools are exported to the
wrapper process. Current examples include:

```text
PATH
PKG_CONFIG
CMAKE_BIN
```

The proposal must generalize this behavior rather than remove it.

### Generated Target Families

The wrapper generates:

```text
group:port.suffix
port.suffix
category.suffix
group.suffix
ports.suffix
```

These target forms are useful and should remain compatible.

## Problems To Solve

### Source And Group Concepts Are Easy To Conflate

A feed is a source of port definitions. A group is a build context. They are
orthogonal.

For example:

```text
feeds/lang/clisp
```

may resolve the logical port `lang/clisp`, while:

```text
compiler@lang/clisp
```

describes where and how that resolved port is built.

### Group Definition Is Distributed

Membership, destination, prefix, suffix, environment, host-tool behavior, and
dependency intent are spread across multiple variables and files.

### Encoded Strings Carry Too Much State

`group@category/port` is appropriate as a target name, but it should not be the
only normalized representation of:

- group;
- logical port identity;
- physical origin;
- environment;
- work identity.

### Default Assignment Is Invisible

New ports silently enter the default group. This is convenient during
development but risky for CI and release builds.

### Group Relationships Are Implicit

The current system suggests relationships such as:

```text
bs provides bootstrap tools
host provides executable host tools
compiler consumes host tools
textproc provides libraries
```

but there is no explicit graph or validation.

### Short Port Targets Can Be Ambiguous

The wrapper often generates aliases from the final port name, such as:

```text
clisp.build
```

The canonical identity is `lang/clisp`. Short aliases should only be generated
when the name is unique across the active collection.

### Eager Target Generation Does Not Scale Well

The original `tools.mk` used nested `foreach`, `call`, and `eval` expressions
to materialize most wrapper records and target families while make parsed the
file. `eval` is not inherently wrong, but each use expands its argument and
then asks make to parse the generated makefile text again.

The larger cost comes from eagerly generating the complete target matrix even
when the requested command needs only one port or one diagnostic:

```text
build instances × lifecycle suffixes
+ default and short aliases × lifecycle suffixes
+ categories × lifecycle suffixes
+ groups × lifecycle suffixes
+ global and diagnostic targets
```

On June 19, 2026, with GNU Make 4.4.1 and the current example configuration,
the active plan contained:

```text
42 logical ports
42 build instances
4 groups
9 categories
17 lifecycle suffixes
714 canonical instance lifecycle targets
```

A no-op parse of the complete configuration took approximately 0.16 to 0.18
seconds on the development machine. Selecting only `lang/cpython` reduced it
to approximately 0.09 seconds. A make database inspection reported roughly
1,873 rule lines and 1,673 phony target names for the complete configuration.
These measurements are small enough for the current tree, but they demonstrate
that parse cost and rule count grow with the size of the generated matrix.

The separate optimization task in `docs/00.2-TOOLS.MK.md` completed on June
20, 2026. The current wrapper now uses normalized immediate records and shared
dispatch for canonical, alias, diagnostic, and aggregate target families.

On the same development host, the final full-plan measurements are:

```text
median parse time:             approximately 0.10 seconds
make database rule lines:      388
phony target names:            4
make database size:            approximately 446 KiB
regression assertions:         103
```

The 200-port synthetic plan improved from approximately 0.99 seconds and 7,768
rule lines to approximately 0.07 seconds and 408 rule lines.

Variants make this more important. The principal term becomes:

```text
groups × ports × selected variants × lifecycle suffixes
```

Future variant work must continue treating parse-time performance and
make-database size as architectural constraints. The wrapper now reserves
`variant=default`, supports collision-free nondefault instance keys, and
creates no records for undeclared or unselected variants. Public Flavor
selection follows the interface above and must satisfy the
performance budget recorded in `docs/00.2-TOOLS.MK.md`.

## Refined Data Model

The wrapper should normalize five record types.

### Collection

A collection describes a physical root containing ports:

```text
collection id
root path
precedence
kind
optional policy file
```

Example:

```make
PORT_COLLECTIONS = uports project

PORT_COLLECTION_uports_ROOT = $(portdir)
PORT_COLLECTION_uports_KIND = builtin

PORT_COLLECTION_project_ROOT = $(FEEDS)
PORT_COLLECTION_project_KIND = feed
```

Collections listed later have higher override precedence.

### Resolved Port

A resolved port describes the selected definition for a logical identity:

```text
id       = lang/clisp
origin   = project
root     = /path/to/feeds
portdir  = /path/to/feeds/lang/clisp
shadowed = uports, if a lower-precedence definition exists
```

The resolver must produce one active definition for each `category/port`.

### Group Profile

A group profile describes a build context:

```text
name
role
destination
prefix
environment
work suffix
tool exports
group relationships
membership rules
```

### Variant

A variant describes one repeatable configuration of a logical port:

```text
name
environment
work suffix
package suffix
plist selection
variant relationships
```

Examples:

```text
devel/libffi:shared
devel/libffi:static
lang/gcc:core1
lang/gcc:core2
lang/gcc:final
```

Variants are declared by the port because the port owns the supported build
configurations and their package-specific behavior. The project selects which
variants are required in each group.

`default` is the implicit variant for ports that do not declare variants. An
unqualified existing build instance is therefore normalized internally as:

```text
group + resolved port + default
```

Variants are not collections or groups:

- a collection selects the physical port definition;
- a group selects the build and installation context;
- a variant selects one configuration, ABI, or bootstrap stage of that port.

Different upstream versions should normally remain different logical ports,
such as `lang/gcc-14` and `lang/gcc-15`. Variants should represent builds of
one selected port version, such as `core1` and `final`.

### Build Instance

A build instance is:

```text
group + resolved port + variant
```

For example:

```text
group    = compiler
port     = lang/clisp
variant  = default
origin   = project
portdir  = /path/to/feeds/lang/clisp
work     = work.compiler
destdir  = /path/to/local/compiler
prefix   = /usr/local
```

Or:

```text
group    = cross-aarch64
port     = lang/gcc-14
variant  = core1
origin   = project
portdir  = /path/to/feeds/lang/gcc-14
work     = work.cross-aarch64.core1
destdir  = /path/to/local/cross-aarch64
prefix   = /usr
```

Lifecycle targets are operations on this instance:

```text
compiler@lang/clisp.configure
compiler@lang/clisp.build
compiler@lang/clisp.install
cross-aarch64@lang/gcc-14:core1.build
```

The existing shorter form may remain:

```text
compiler:clisp.build
```

but only as an unambiguous alias.

The `:default` qualifier should be omitted from compatible targets.

## Proposed Public Configuration

The public interface should follow existing make naming conventions and avoid
requiring dot-heavy variable parsing.

### Collections

```make
PORT_COLLECTIONS = uports project

PORT_COLLECTION_uports_ROOT = $(portdir)
PORT_COLLECTION_uports_KIND = builtin

PORT_COLLECTION_project_ROOT = $(FEEDS)
PORT_COLLECTION_project_KIND = feed
```

Compatibility mapping:

```make
FEEDS=/path/to/feed
```

becomes an implicit high-priority `project` collection.

Future projects may add more than one feed:

```make
PORT_COLLECTIONS += vendor product

PORT_COLLECTION_vendor_ROOT  = /opt/vendor/uports-feed
PORT_COLLECTION_product_ROOT = $(topdir)/feeds
```

The order is the override order:

```text
uports < vendor < product
```

### Groups

```make
PORT_GROUPS += bs host compiler textproc
PORT_GROUP_DEFAULT = compiler
```

Compatibility mapping:

```make
special_groups_all
PORTS_GROUP_DEFAULT
```

remains accepted.

```make
PORT_GROUP_bs_PORTS = \
    devel/m4 \
```

```make

PORT_GROUP_compiler_DESTDIR = $(DESTDIR)/compiler
PORT_GROUP_compiler_PREFIX  = $(PREFIX)
PORT_GROUP_compiler_SUFFIX  = compiler
```

```make
PORT_GROUP_compiler_ENVS += \
```

### Per-Port Overrides

Keep the current overlay capability with clearer canonical names:

```make
PORT_lang_clisp_ENVS += WITH_READLINE=yes

PORT_INSTANCE_compiler_lang_clisp_ENVS += WITH_DOCUMENT=no

PORT_INSTANCE_compiler_lang_clisp_EXCLUDE_ENVS += USE_SCM=%

    WITH_SHARED=no

PORT_INSTANCE_compiler_devel_libffi_static_EXCLUDE_ENVS += \
    WITH_SHARED=%
```

Because `/` and `-` are awkward in generated make variable names, the

layer continues to accept:

```make
PORTS_clisp_EXTRA_ENVS
PORTS_compiler_clisp_EXTRA_ENVS
PORTS_compiler_clisp_EXCLUDE_ENVS
```

### Variants

A port declares the variants it supports:

```make
PORT_VARIANTS = shared static
PORT_VARIANT_DEFAULT = shared

PORT_VARIANT_shared_ENVS += \
    CONFIGURE_ARGS+=--enable-shared \
    CONFIGURE_ARGS+=--disable-static

PORT_VARIANT_static_ENVS += \
    CONFIGURE_ARGS+=--disable-shared \
    CONFIGURE_ARGS+=--enable-static
```

The project selects variants for a group-port instance:

```make
PORT_INSTANCE_compiler_devel_libffi_VARIANTS = shared static
PORT_INSTANCE_python_devel_libffi_VARIANTS   = shared
```

Variant-qualified instance overlays use the same encoded group and port
identity followed by the variant name:

```make
PORT_INSTANCE_compiler_devel_libffi_static_ENVS += WITH_DEBUG=no
```

This expands into:

```text
compiler@devel/libffi:shared
compiler@devel/libffi:static
python@devel/libffi:shared
```

Group membership alone must not select every declared variant. Selection is
explicit when more than the default variant is required.

Variant-specific package names, plist files, and install behavior remain owned
by the port. The framework must ensure that selected variants have distinct
work and package identities.

## Environment Composition

The effective environment for one build instance should be assembled in a
defined order:

1. framework defaults;
2. project-wide `PORTS_ENVS`;
3. inherited group-profile values;
4. group `ENVS`;
5. logical-port `ENVS`;
6. variant `ENVS`;
7. group-and-port instance `ENVS`;
8. group-port-variant instance `ENVS`;
9. command-line overrides;
10. derived work and type suffixes.

Exclusions are applied to inherited values before the instance additions.
Variant-qualified exclusions follow the same rule.

The framework should expose the result through:

```sh
make port-env GROUP=compiler PORT=lang/clisp
make port-env GROUP=compiler PORT=devel/libffi VARIANT=static
```

The output should identify the source of each value:

```text
DESTDIR=/.../local/compiler          group profile
PREFIX=/usr/local                    wrapper default
WITH_DOCUMENT=no                     instance override
TYPE_SUFFIX=.compiler                derived
```

For the implicit `default` variant, the effective environment and suffixes
must remain compatible with the current group-port result.

## Group Relationships

Group relationships should be explicit, but they must not replace per-port
dependencies.

Variant and bootstrap-stage relationships are more specific than group
relationships. For example, a cross-toolchain may require:

```text
binutils
gcc:core1
libc:headers-startfiles
gcc:core2
libc:full
gcc:final
```

That ordering belongs to build-instance dependencies. It should not be modeled
as separate collections, and stages should not become separate groups unless
they genuinely use different build or installation contexts.

### Tool Providers

Generalize `USE_HOSTTOOLS`:

```make
PORT_TOOL_GROUPS = host bs
```

Groups can export tools:

```make
PORT_GROUP_host_EXPORTS = PATH PKG_CONFIG CMAKE_BIN
```

The wrapper composes tool search order from `PORT_TOOL_GROUPS`.

For compatibility:

```make
USE_HOSTTOOLS=host
```

maps to:

```make
PORT_TOOL_GROUPS=host
```

### Build Relationships

Start with one simple graph:

```make
PORT_GROUP_host_BUILD_USES     = bs
PORT_GROUP_compiler_BUILD_USES = bs host
PORT_GROUP_textproc_BUILD_USES = host
```

This graph establishes group-wide prerequisite ordering and environment
visibility.

It does not imply that every package in `compiler` depends on every package in
`host`. Exact package dependencies remain in:

```text
BUILD_DEPENDS
LIB_DEPENDS
RUN_DEPENDS
```

### Future Typed Relationships

After build ordering is stable, add:

```make
PORT_GROUP_compiler_LINK_USES  = textproc
PORT_GROUP_compiler_RUN_USES   = compiler textproc
PORT_GROUP_compiler_IMAGE_USES = compiler
```

Meanings:

```text
BUILD_USES
  Groups providing commands used while building.

LINK_USES
  Groups whose headers and libraries may be used for linking.

RUN_USES
  Groups visible to installed runtime software.

IMAGE_USES
  Groups whose packages are eligible for a produced image.
```

These relationships define visibility and ordering. They do not synthesize
package dependencies automatically.

## To Be Discussed: System-Provided Dependencies

Status: **To Be Discussed**

Some native host build instances can use a dependency supplied by the host
operating system instead of building the corresponding uports package.

The motivating example is:

```text
host@lang/chezscheme
  requires libffi
  macOS Command Line Tools provide ffi/ffi.h and libffi
```

On macOS, the active SDK may provide:

```text
$(xcrun --show-sdk-path)/usr/include/ffi/ffi.h
$(xcrun --show-sdk-path)/usr/lib/libffi.tbd
runtime install name: /usr/lib/libffi.dylib
```

For a native host-only ChezScheme build, using that provider may be preferable
to building `host@devel/libffi`. The same assumption is not necessarily valid
for a `compiler`, cross, relocatable, or self-contained runtime group.

The dependency itself should remain declared by the port:

```make
LIB_DEPENDS += libffi:devel/libffi
```

The unresolved design question is whether project or group policy may select a
different provider for that logical requirement:

```text
consumer       = host@lang/chezscheme
requirement    = devel/libffi
provider kind  = system
provider       = macos-sdk
```

This follows the general idea of systems such as Yocto
`ASSUME_PROVIDED`: the dependency remains known, but the planner does not build
its recipe when an explicitly selected external provider satisfies it.

### Possible Configuration Direction

One possible spelling, not yet accepted, is:

```make
PORT_GROUP_host_ASSUME_PROVIDED += devel/libffi
```

or a more explicit provider mapping:

```make
PORT_GROUP_host_PROVIDER_devel_libffi = system:macos-sdk
```

Without such a declaration, the normal provider would remain:

```text
host@devel/libffi
```

Provider selection should be project or group policy. It should not be inferred
from whether a matching library happens to exist somewhere on the build host.
Automatic host probing could otherwise select Homebrew, MacPorts, or another
uncontrolled installation and make results host-dependent.

### Possible uports Organization

Frequently assumed packages such as `devel/libffi` could live in the built-in
`make/uports/` collection so that uports always has a maintained buildable
fallback.

System-provider checks could be framework metadata kept separately from the
port definition, for example:

```text
make/uports/devel/libffi/       buildable fallback port
make/uports/Mk/Providers/       operating-system provider checks
```

This organization must not conflate collection origin with provider
selection:

```text
collection origin
  selects where the port definition comes from

dependency provider
  selects what satisfies one dependency for one build context
```

### Required Provider Validation

If a system provider is selected, dependency handling should be automatic but
validation must be explicit. A macOS libffi provider check may need to:

1. obtain the active SDK path from `xcrun`;
2. verify the required header;
3. verify the link library or text-based stub;
4. compile and link a small `ffi_call` test;
5. verify the expected runtime install name;
6. record the SDK identity or version;
7. supply provider-specific compile and link flags;
8. fail before the consumer configure phase if validation fails.

File existence alone is not sufficient evidence of API, ABI, architecture, or
link compatibility.

### Interaction With Current `LIB_DEPENDS`

The current execution framework treats any nonempty `LIB_DEPENDS` as a reason
to add uports destination paths:

```make
CFLAGS  += -I$(DESTDIR)$(PREFIX)/include
LDFLAGS += -L$(DESTDIR)$(PREFIX)/lib
```

On Darwin it may also add an rpath to the uports destination library
directory. That behavior is inappropriate when the resolved dependency is
provided by the macOS SDK.

If provider selection is adopted, include paths, library paths, rpaths, and
runtime checks must be derived from resolved providers rather than merely from
whether `LIB_DEPENDS` is nonempty.

Changing the selected provider must also invalidate the consumer's configure
and build state.

### Implementation Timing

If this design is accepted, full system-provider support should be implemented
late in the formal group enhancement, but the normalized data model should
prepare for it early.

Recommended order:

1. normalize collections, logical ports, groups, and build instances;
2. add planning diagnostics and validation;
3. optimize `tools.mk` planning and target generation;
4. implement automatic dependency expansion using uports build instances as
   the only providers;
5. add variants and variant-qualified build instances;
6. add explicit dependency-provider selection;
7. add operating-system and SDK provider validation.

System-provider resolution depends on records that earlier phases must make
explicit:

```text
consumer build instance
dependency type
resolved logical dependency
selected provider kind
provider identity
provider validation result
compile, link, and runtime contributions
build signature inputs
```

Implementing system providers before normalized instances and dependency
resolution would likely embed additional provider policy in encoded target
strings and eager `eval` generation.

Early design work should nevertheless:

- reserve provider fields in normalized dependency records;
- distinguish the dependency requirement from its selected provider;
- avoid hardcoding that every `LIB_DEPENDS` entry comes from
  `$(DESTDIR)$(PREFIX)`;
- ensure effective environments and build signatures can include provider
  identity;
- leave inspection output able to report provider decisions later.

The practical schedule is therefore:

```text
early
  finalize terminology, reserve records, and remove blocking assumptions

middle
  implement dependency graphs with uports-only providers

late
  implement explicit system providers and platform-specific validation
```

Variants and system providers are mostly independent and their relative order
may change. Both should follow normalized build instances and reliable
dependency resolution.

### Open Questions

- Should the public concept be named `ASSUME_PROVIDED`, `PROVIDER`, or
  something else?
- Is provider policy allowed globally, per group, per port, or per build
  instance?
- Which dependency types may use system providers: `BUILD_DEPENDS`,
  `LIB_DEPENDS`, `RUN_DEPENDS`, or all three?
- Should native host groups be the only groups allowed to use host-system
  libraries by default?
- Should provider declarations include minimum API, ABI, symbol, or version
  requirements?
- How should SDK identity participate in work and package signatures?
- Should failure fall back to building the uports port, or fail because the
  explicit provider policy was not satisfied?
- Which assumed packages belong in built-in `make/uports/`, and which remain in
  project feeds?
- How should packages linked to system providers be represented in package
  manifests and runtime dependency metadata?
- How should release and CI policy prohibit accidental automatic provider
  selection?

The dependency architecture report defines the currently implemented read-only
provider-policy syntax, dependency matching, explicit validation adapters, and
structured environment contributions. An opt-in projection replaces validated
external providers in normalized records and omits their uports graph edges,
and dependency-aware dispatch applies their phase-scoped environment and state
only when explicitly enabled. Fallback behavior, release policy, native/cross
hardening, and package metadata remain open design work.

## Selection And Assignment Pipeline

The wrapper should use an explicit planning pipeline:

```text
1. load collections
2. discover physical port definitions
3. resolve one definition per category/port
4. apply PORTS_LISTS selection
5. validate selected identities
6. load group profiles and membership
7. assign explicit groups
8. assign default group where allowed
9. load port variant declarations
10. select variants for each group-port pair
11. expand group, port, and variant combinations into build instances
12. compose instance environments
13. validate graphs, identities, outputs, and paths
14. generate targets
15. dispatch to per-port framework
```

This order prevents group declarations from accidentally selecting a shadowed
physical port.

## Validation

Add:

```sh
make groups-check
```

It should validate all wrapper-level records.

### Collection Checks

- every collection root exists unless marked optional;
- every discovered port has a Makefile;
- collection identifiers are unique;
- override precedence is deterministic;
- ignored and shadowed ports are reportable.

### Port Checks

- selected logical ports exist;
- canonical identities are unique after resolution;
- short aliases are generated only when unambiguous;
- port-level override variables refer to selected ports.

### Variant Checks

- selected variants are declared by the resolved port;
- each group-port pair has a deterministic default variant;
- variant names are valid and unique within the port;
- work suffixes and package identities do not collide;
- variant-specific plist selections exist where required;
- aggregate targets include exactly the selected variants;
- instance dependency graphs contain no cycles;
- bootstrap stages do not overwrite outputs needed by later stages
  unexpectedly.

### Group Checks

- group names are valid and unique;
- every concrete group has `DESTDIR` and `PREFIX`;
- membership refers to logical ports, not physical paths;
- multiple membership is explicit;
- strict mode has no implicit assignments;
- suffixes do not cause work-directory collisions;
- destination roots do not overlap unexpectedly.

### Graph Checks

- all relationship targets are known groups;
- build graphs contain no cycles;
- tool-provider order is deterministic;
- runtime groups do not accidentally depend on private bootstrap roots.

### Environment Checks

- exclusions match known inherited values;
- required tool exports resolve to files after provider installation;
- derived paths are defined;
- environment output does not contain conflicting assignments unless the
  precedence rule resolves them explicitly.

### Performance Checks

- normalized collection, port, group, variant, and instance records are
  computed once where practical;
- recursive variables do not repeatedly rescan the complete port or instance
  lists;
- target and alias counts are reportable;
- diagnostic-only rules are not eagerly generated for ordinary builds where
  they can be produced by shared recipes or on-demand output;
- adding one selected variant increases generated state in proportion to that
  instance, not every possible port-variant combination;
- parse-time and make-database growth are measured against representative
  small and large plans.

## Ownership Of Configuration

The refined design should keep policy in the correct layer.

### uports Framework Owns

- built-in port definitions;
- lifecycle implementation;
- built-in group defaults such as `bs` and `host`;
- compatibility parsing;
- validation and target-generation machinery.

### Feed Owns

- external or overridden port definitions;
- optional feed-local ignore policy;
- optional suggested group membership for that feed;
- no authority to force project destination paths.

Feed group suggestions should be defaults that a project may override.

### Project Wrapper Owns

- active collection roots and precedence;
- selected ports;
- default group;
- final group membership;
- destinations and prefixes;
- environment overlays;
- tool-provider selection;
- group relationships;
- strictness policy.

### Port Owns

- package-specific dependencies and build behavior;
- supported variants and variant-specific build, package, and plist behavior;
- no project group assignment;
- no knowledge of collection precedence.

## Feed Policy Refinement

The current `feeds/group.mk` mixes feed membership suggestions with project
environment policy.

A cleaner split is:

```text
feeds/groups.mk       optional membership suggestions
project/groups.mk     final project group profiles and environments
```

For compatibility, existing `feeds/group.mk` remains loaded.

The precedence should be:

```text
framework group defaults
feed membership suggestions
project group policy
command-line selection
```

Feed files may suggest:

```make
PORT_GROUP_SUGGEST_textproc += textproc/expat2
```

The project confirms or overrides:

```make
PORT_GROUP_textproc_PORTS += $(PORT_GROUP_SUGGEST_textproc)
```

This prevents a reusable external feed from deciding where a consuming project
must install its packages.

## Implementation Plan

### Historical Implementation Baseline

As of June 20, 2026, the standalone tools optimization task has completed:

- deterministic planner statistics and benchmark tooling;
- normalized logical-port origin and build-instance lookup records;
- deferred nonessential presentation probes;
- consolidated fresh collection discovery;
- shared canonical and short-alias lifecycle dispatch;
- shared diagnostic and aggregate target dispatch;
- human-readable normalized plan, origin, instance, variant, and dispatch
  diagnostics under `info.debug`;
- explicit ambiguity rejection for duplicate short port names;
- implicit `variant=default` in every selected build instance;
- variant-aware internal instance keys without public variant targets.

The next formal group-enhancement work must build on these records and shared
dispatch paths. It should not restore per-instance or per-suffix generated rule
matrices.

### Normalized Dependency Record Boundary

The original first dependency phase was read-only. Each word from `BUILD_DEPENDS`,
`LIB_DEPENDS`, and `RUN_DEPENDS` becomes one record with these fields:

```text
consumer          normalized build-instance key
type              build, lib, or run
requirement       the text before the dependency origin
origin            logical `category/port` requirement
target            optional text after the origin
provider_kind     uports or unresolved
provider_instance selected uports build-instance key, if deterministic
resolution        selected, unselected, ambiguous, or unknown-origin
```

Provider selection first prefers an instance of the dependency origin in the
consumer's group. If none exists there, exactly one selected instance across
all groups is deterministic. Zero candidates are `unselected`; multiple
candidates are `ambiguous`. An origin with no active uports definition is
`unknown-origin`.

That initial phase did not execute dependency targets, alter compiler or linker
flags, inspect the host system, select system providers, or infer aliases for
renamed origins. The records are loaded only for `dependencies-list`,
`info.debug.dependencies`, and the aggregate debug report so ordinary planner
startup retains its current cost.

### Flavor Records

Current Flavor extension to the normalized boundary above:
`origin` also accepts `category/port@flavor`, retaining the qualifier as part of
the logical requirement. The optional target field still denotes a lifecycle
phase. Default keys remain compatible; nondefault provider/consumer keys append
`__flavor_<name>`. Additional resolution states distinguish unknown/invalid
Flavors, missing variant capabilities and incompatible provider contexts.
Metadata adds default/choice/selected Flavor and OS/architecture records;
invocation snapshots also identify variant/base relationships. These additions
do not add fields to the normalized dependency record. The current execution
and selection contract is in [10.4-DEPENDENCY.md](10.4-DEPENDENCY.md#flavor-selection-and-dependency-instances).

### Explicit Port Capabilities

A selected port may explicitly declare additional logical origins that it can
satisfy:

```make
PORT_PROVIDES += devel/autoconf
```

`PORT_PROVIDES` is provider-owned uports metadata. It is not project provider
policy, does not rename the physical port origin, and does not imply a system
provider. FreeBSD ports has no direct origin-alias variable for this use, so the
name is an intentional uports extension.

The machine-readable metadata target emits each capability as:

```text
provides|category/origin
```

Resolution order is deterministic:

1. exact selected origin in the consumer group;
2. one explicit capability provider in the consumer group;
3. one unique exact or capability provider across selected groups;
4. otherwise `unselected`, `ambiguous`, or `unknown-origin` as appropriate.

Multiple capability providers in the consumer group are ambiguous; resolution
does not fall through to a provider in another group. Capabilities are consulted
only for selected uports instances. Current execution and provider environment
behavior are described in 10.4-DEPENDENCY.md.

### Read-only Dependency Graph

Selected dependency records form a dynamic build-instance graph. Each record
contributes one typed edge:

```text
consumer instance -> provider instance
type: build, lib, or run
logical origin: category/port
```

The graph is regenerated from the current selection and port metadata whenever
its diagnostic or validation target runs. It is not stored in the repository,
and adding an unselected port does not add a graph node or edge.

Metadata probes run concurrently because each selected instance requires a
recursive port make. `DEPENDENCY_METADATA_JOBS` controls the bound and defaults
to four. Every probe writes an isolated temporary result; results are then read
in planner instance order, so concurrency does not change record order. Probe
failure is fatal and temporary results are removed. No persistent metadata or
graph cache is created.

Inspection and validation targets are:

```sh
make dependency-graph-list
make dependency-order-list
make info.debug.dependency-graph
make info.debug.dependency-order
make dependencies-check
```

Graph inspection reports selected typed edges, unresolved records, cycle state,
and the instances blocked by a detected cycle. `dependencies-check` fails when
any record is unresolved or when the selected instance graph contains a cycle.
Repeated records remain visible as typed edges, while cycle analysis deduplicates
identical consumer/provider pairs.

The dependency order contains every selected build instance exactly once,
including instances with no edges. Although graph records retain their
consumer-to-provider meaning, topological ordering interprets each edge as a
provider-before-consumer constraint. When multiple instances are ready, their
existing planner order is the deterministic tie-break. A cycle prevents a
complete order and also blocks consumers downstream of that cycle.

The displayed order is an inspection result, not lifecycle wiring. It is usable
for execution only when dependency validation also reports no unresolved records
and no cycle.

### Read-only Lifecycle Prerequisite Plan

Resolved records also map to canonical wrapper lifecycle targets:

```text
build, lib: consumer.configure <- provider.install
run:        consumer.stage     <- provider.install
```

This matches the per-port framework's existing dependency hooks: build and
library checks occur during configure, while runtime checks occur during stage.
An explicit dependency target replaces the provider's default `install` suffix
and must name a supported wrapper lifecycle suffix. Canonical targets retain the
selected group and normalized port name; unqualified short aliases are never
used in the plan.

Inspect and validate the mapping with:

```sh
make dependency-lifecycle-list
make info.debug.dependency-lifecycle
make dependency-lifecycle-check
```

Lifecycle validation rejects unresolved dependencies, graph cycles, and
unsupported explicit provider targets. The diagnostic itself remains available
for inspecting an incomplete plan.

### Opt-in Provider Execution

The first execution boundary is deliberately explicit:

```sh
make dependency-lifecycle-execute
```

It validates the complete selected project plan before dispatching anything,
then invokes the deduplicated provider lifecycle targets in provider-first
topological order. It prepares providers required anywhere in the selected plan;
it does not invoke consumer targets. A provider-command failure is returned to
the caller. This initial dispatcher uses one recursive make job so an inherited
parallel jobserver cannot violate the inspected order.

Supplying a canonical or unambiguous alias request limits validation and
execution to that target's transitive dependency closure:

```sh
make dependency-execution-plan DEPENDENCY_REQUEST=compiler:cpython.build
make dependency-lifecycle-execute DEPENDENCY_REQUEST=compiler:cpython.build
```

Configure/build/rebuild requests traverse build and library dependencies.
Stage/package/install/restage/reinstall/generate-plist requests additionally
traverse runtime dependencies. Fetch, extract, and patch requests do not require
package dependencies. Transitive providers are evaluated according to the
lifecycle target requested for that provider.

Canonical and unambiguous alias dispatch consumes this scoped plan by default:

```sh
make compiler:cpython.build
```

Providers complete before the requested consumer is dispatched. Recursive
provider targets set `UPORTS_DEPENDENCIES=no`, because the parent dispatcher has
already ordered their transitive closure. Set `UPORTS_DEPENDENCIES=no` explicitly
to suppress provider execution while retaining state and provenance, or use
`UPORTS_DEPENDENCIES=none` to bypass dependency metadata, execution, state, and
provenance together. Other values are rejected.

For category, group, and `ports.*` targets, the policy builds one multi-root
plan. The union of all consumer closures is validated before dispatch; shared
providers are deduplicated and completed first. A second dependency-neutral
recursive make then dispatches the consumers and may use the inherited jobserver.
Thus `make -j` can parallelize consumers only after provider preparation has
completed.

The inspection targets remain read-only. The explicit execution target installs
providers. The policy switch integrates scoped execution with canonical and
unambiguous alias targets and is enabled by default. Provider-derived settings
follow the environment contract in 10.4-DEPENDENCY.md.

## Design Principles

1. A port collection provides definitions.
2. A logical port is identified by `category/port`.
3. Collection precedence resolves one active port definition.
4. A group is a project build profile, not a collection or category.
5. A variant is one repeatable configuration, ABI, or bootstrap stage of a
   logical port.
6. A build instance joins one resolved port variant with one group.
7. `tools.mk` is the planner and dispatcher for build instances.
8. The per-port framework remains responsible for lifecycle execution.
9. Feed overrides must remain supported and observable.
10. External feeds must remain valid.
11. Existing environment overlays and exclusions must remain expressible.
12. Existing targets remain compatible and imply the `default` variant.
13. Canonical internal identities should include category, origin, group, and
    variant.
14. Short target aliases are convenience only and must be unambiguous.
15. Group graphs supplement rather than replace package dependencies.
16. Build-instance graphs express variant and bootstrap-stage ordering.
17. Project policy has final authority over feed suggestions and variant
    selection.
18. Migration begins with normalization and diagnostics, not a flag-day
    rewrite.
19. Parse-time work and generated rule count should scale with selected build
    instances, not the Cartesian product of all possible groups, ports,
    variants, and targets.

## Proposed End State

The wrapper should be able to answer these questions directly:

```text
Which physical collections were scanned?
Which collection supplied this logical port?
Which definitions were shadowed?
Why is this port in this group?
Was its assignment explicit or default?
What destination, prefix, suffix, and environment does this instance use?
Which variants does this port support?
Which variants are selected in this group, and why?
Which work, package, and plist identity does each variant use?
Which tool groups are visible while it builds?
What group ordering is required?
What variant or bootstrap-stage ordering is required?
Which exact per-port target will tools.mk invoke?
```

When those answers are represented explicitly, uports keeps its reusable
per-port framework, feeds keep their override capability, and `tools.mk`
becomes a clearer wrapper planner instead of relying primarily on encoded
strings and distributed variables.
