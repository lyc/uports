# uports Dependency Handling Architecture and Design

## Purpose

This document defines the dependency-handling architecture for the core uports
framework. Live checkout details, verification results, work status, and next
steps belong in `../HANDOFF.md`.

The framework follows two ownership rules:

- ports declare dependency intent and explicit capabilities;
- the project wrapper resolves providers, validates policy, orders instances,
  and dispatches lifecycle targets.

## Architecture Overview

```text
Port Makefiles
  BUILD_DEPENDS / LIB_DEPENDS / RUN_DEPENDS / PORT_PROVIDES
                              |
                              v
+-------------------------------------------------------------------+
| 1. Metadata collection                                            |
|                                                                   |
| Probe every selected build instance. Probes run concurrently,     |
| while collected output is restored to deterministic planner order.|
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 2. Normalized dependency records                                  |
|                                                                   |
| consumer, type, requirement, logical origin, optional target,     |
| provider kind, provider instance, resolution state                |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 3. Provider resolution                                            |
|                                                                   |
| exact provider in consumer group                                  |
|   -> PORT_PROVIDES capability in consumer group                   |
|   -> one unique selected provider across groups                   |
|   -> explicit unresolved state                                    |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 4. Selected-instance dependency graph                             |
|                                                                   |
| declaration: consumer ----------> provider                        |
| ordering:    provider must complete before consumer               |
|                                                                   |
| Unresolved records stay visible. Cycles are rejected.             |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 5. Provider-first ordering                                        |
|                                                                   |
| Deterministic topological order; planner order breaks ties.       |
| Shared consumer/provider pairs are deduplicated for ordering      |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 6. Lifecycle prerequisite plan                                    |
|                                                                   |
| BUILD_DEPENDS, LIB_DEPENDS: provider before consumer.configure    |
| RUN_DEPENDS:                provider before consumer.stage        |
| Default provider target:    provider.install                      |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 7. Scoped execution planning                                      |
|                                                                   |
| canonical/alias target -> one transitive closure                  |
| category/group/ports.* -> union of multiple closures              |
|                                                                   |
| Validate the relevant union and deduplicate shared providers.     |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 8. Opt-in execution                                               |
|                                                                   |
| UPORTS_DEPENDENCIES=yes                                           |
|   1. execute provider targets in deterministic order              |
|   2. dispatch consumers after all providers complete              |
|   3. allow consumer parallelism through the parent jobserver      |
+-------------------------------------------------------------------+
```

## Terminology

### Dependency

A dependency is a requirement declared by a consumer port. For example:

```make
LIB_DEPENDS += libssl.so:security/openssl
```

The declaration contains the required artifact and logical origin. It does not
by itself select a particular build instance.

### Provider

A provider is the selected build instance that satisfies a dependency. A record
may therefore resolve as:

```text
consumer:          compiler_cpython
type:              lib
requirement:       libssl.so
origin:            security/openssl
provider_instance: compiler_openssl
resolution:        selected
```

Dependency records retain the declaration direction `consumer -> provider`.
Execution reverses the precedence: the provider must complete before its
consumer.

### Capability

`PORT_PROVIDES` explicitly states that a selected port can satisfy an additional
logical origin:

```make
PORT_PROVIDES += devel/autoconf
```

Capabilities are provider-owned metadata. They do not silently rename ports and
do not assert equivalence between unrelated implementations.

## Ownership Boundary

Dependency handling is not a new dependency language invented by uports.
`BUILD_DEPENDS`, `LIB_DEPENDS`, `RUN_DEPENDS`, and the corresponding lifecycle
concepts originate in FreeBSD Ports. uports inherited those declarations, but
its dependency targets were effectively empty before the work described here:

```make
build-depends:
lib-depends:
run-depends:
```

The recent work therefore implements a previously missing capability while
preserving the FreeBSD-compatible declaration model.

That does not mean dependency handling has no relationship with the uports
project planner. The ownership is split across two levels:

```text
Per-port FreeBSD-compatible layer
  port Makefile + Mk/linux.port.mk
  - declare BUILD_DEPENDS, LIB_DEPENDS, and RUN_DEPENDS
  - export dependency and capability metadata
  - define when dependency types are needed in one port's lifecycle
                              |
                              v
Project-level uports planner
  Tools dependency planner + target dispatcher
  - select concrete providers from active build instances
  - apply group, variant, host/target, and project policy
  - reject ambiguous or unresolved providers
  - construct and validate the selected-instance graph
  - order and deduplicate providers across aggregate consumers
  - dispatch providers and consumers
```

An individual port cannot determine which project instance should satisfy a
logical origin. For example:

```make
LIB_DEPENDS += libssl.so:security/openssl
```

does not say whether the selected provider is `host_openssl`,
`compiler_openssl`, `target_openssl`, or a future validated system/SDK provider.
That decision depends on active groups, selected instances, cross-build context,
and project policy, so it belongs above the per-port framework.

### Relationship with `Tools/tools.mk`

`Tools/tools.mk` is currently both the project planner and the integration point
for dependency handling. A relationship is necessary because that file owns
selected groups, build instances, aggregate targets, environments, and lifecycle
dispatch. However, the dependency algorithms do not need to remain physically
embedded in the already-large file.

A cleaner target structure is:

```text
Mk/linux.port.mk
  FreeBSD-compatible declarations, metadata export, lifecycle hooks

Tools/tools.mk
  project planner and dependency integration point
          |
          `-- include Tools/dependency.mk
                normalized records
                provider resolution
                graph/lifecycle input
                validation and execution targets

Tools/dependency-graph.awk
  graph validation and deterministic ordering

Tools/dependency-execution.awk
  scoped and multi-root execution planning
```

In this model, `Tools/tools.mk` still integrates dependency planning, but the
dependency implementation becomes a focused module. This separation should be
completed before default enablement or system-provider work makes the planner
larger.

## Component Design

### Metadata export and normalization

`Mk/linux.port.mk` exports dependency metadata through
`uports-dependency-metadata`. `Tools/tools.mk` converts it into normalized,
inspectable records for `BUILD_DEPENDS`, `LIB_DEPENDS`, and `RUN_DEPENDS`.

Resolution states are:

```text
selected
unselected
ambiguous
unknown-origin
```

Ordinary planner startup does not collect dependency metadata. Collection occurs
only when dependency diagnostics, validation, or execution planning needs it.

### Parallel deterministic collection

Metadata probes use a bounded recursive make:

```make
DEPENDENCY_METADATA_JOBS ?= 4
```

Every probe writes an isolated temporary result. Results are concatenated in
planner-instance order, failures are fatal, and temporary data is removed. No
persistent dependency cache or generated graph is stored in the repository.

### Deterministic provider resolution

Provider selection uses this precedence:

1. exact selected origin in the consumer group;
2. one explicit capability provider in the consumer group;
3. one unique exact or capability provider across selected groups;
4. otherwise report `unselected`, `ambiguous`, or `unknown-origin`.

The resolver does not guess that differently named origins are equivalent.

### Dependency graph and ordering

The graph is generated dynamically from current selected instances and current
port metadata. It supports:

- typed edges for build, library, and runtime dependencies;
- unresolved-record visibility;
- deterministic cycle detection;
- downstream blocked-node reporting;
- provider-first topological ordering;
- isolated selected instances;
- planner-order tie breaking.

Available commands include:

```sh
make dependencies-list
make dependency-graph-list
make dependency-order-list
make dependencies-check
```

### Lifecycle mapping

Resolved records map to dispatchable group-qualified wrapper targets:

```text
build, lib: consumer.configure <- provider.install
run:        consumer.stage     <- provider.install
```

An explicit dependency target replaces the default provider `install` target,
but it must be a supported forward lifecycle target. Destructive targets such as
`clean`, `deinstall`, and `uninstall` are not accepted as dependency provider
targets.

Inspection and validation commands are:

```sh
make dependency-lifecycle-list
make dependency-lifecycle-check
```

### Target-scoped execution

A canonical target or unambiguous alias can be planned independently:

```sh
make \
  DEPENDENCY_REQUEST=compiler@cpython.build \
  dependency-execution-plan
```

Phase filtering is applied to the root request:

| Requested phase | Direct dependency types traversed |
| --- | --- |
| fetch, extract, patch | none |
| configure, build, rebuild | build and lib |
| stage, package, install, restage, reinstall, generate-plist | build, lib, and run |

Transitive providers are evaluated according to the lifecycle target requested
for that provider.

### Multi-root aggregate execution

When dependency execution is enabled, category, group, and `ports.*` aggregate
targets produce one union of all consumer closures. The implementation:

1. validates the complete relevant union before dispatch;
2. deduplicates shared providers;
3. completes provider targets in deterministic order;
4. invokes a dependency-neutral recursive make for consumers;
5. permits consumers to use the inherited jobserver only after providers finish.

This also handles a requested consumer that is simultaneously a provider for
another requested consumer: its provider phase still completes before the
consumer batch begins.

### Lifecycle integration

Dependency-aware dispatch is enabled by default:

```make
UPORTS_DEPENDENCIES ?= yes
```

Use `UPORTS_DEPENDENCIES=no` as an explicit compatibility escape hatch. Accepted
policy values are `yes` and `no`. Recursive provider dispatch forces
`UPORTS_DEPENDENCIES=no` because the parent execution planner has already
calculated and ordered the complete closure.

Provider dispatch is deliberately `-j1` today. This guarantees the inspected
topological order. Consumer dispatch may be parallel after provider preparation.

## Important Commands

### Read-only inspection

```sh
make dependencies-list
make dependency-graph-list
make dependency-order-list
make dependency-lifecycle-list
make DEPENDENCY_REQUEST=compiler@cpython.build dependency-execution-plan
```

### Validation

```sh
make dependencies-check
make dependency-lifecycle-check
make -C make/uports/Tools/tests check
```

Run project dependency validation from the project root whose selected groups
and feeds define the complete provider set. Running the same target directly in
the framework repository validates only its standalone example selection, which
may intentionally report origins supplied by a parent project as unresolved.

### Execution

The following commands perform real provider lifecycle work:

```sh
make dependency-lifecycle-execute
make UPORTS_DEPENDENCIES=yes compiler@cpython.build
make UPORTS_DEPENDENCIES=yes compiler.build
```

Do not use execution commands merely to inspect the plan. Use
`dependency-execution-plan` or replace `DEPENDENCY_EXECUTE_COMMAND` with a
recorder.

## Design Extensions

### Extract the dependency planner module

Dependency declarations and per-port lifecycle semantics belong to the
FreeBSD-compatible layer, while provider selection and build-instance ordering
belong to the uports project planner. The current implementation is correct at
that ownership boundary. The source layout should express the same separation
instead of embedding project-level dependency logic in `Tools/tools.mk`.

Extract the focused logic into a file such as `Tools/dependency.mk`, included by
`Tools/tools.mk`. Preserve behavior and tests during the move; this should be a
structural refactor, not a redesign of record or execution semantics.

### Default enablement policy

The validated default is:

```make
UPORTS_DEPENDENCIES ?= yes
```

Default enablement should require validated behavior across transitive and shared
providers, build and runtime phases, interruption and restart, provider cookies,
failures, parallel aggregates, and the rebuild, restage, reinstall, and package
workflows.

Correctness is not the only enablement gate. A completed dependency-aware target
must not repeatedly recollect the same project-wide metadata for planning,
provider execution, environment export, state handling, and provenance. Until
that no-op overhead is reduced to an acceptable project cost. Before that gate
was met, dependency-aware dispatch remained opt-in even though its lifecycle and
failure behavior was correct.
Performance work must preserve the existing deterministic records, explicit
failure propagation, and last-successful-state boundary; it must not introduce
an unvalidated persistent dependency cache merely to change the default. The
invocation-scoped snapshot described below met this gate without persistent
caching. On the validated Darwin arm64 host, steady warm no-op execution took
about 8.56 seconds with dependency handling disabled, 12.72 seconds for a
dependency-aware build, and 14.14 seconds for a dependency-aware package.

### Project policy file

A project may select one makefile containing its dependency-provider policy:

```make
UPORTS_DEPENDENCY_POLICY = $(CURDIR)/dependency-policy.mk
```

The framework resolves a relative path from the top-level make working
directory and includes the file before provider variables receive framework
defaults. The setting must name exactly one existing makefile. Naming a missing
file is a fatal configuration error; an unreadable or malformed file fails as a
normal required make include. An empty `UPORTS_DEPENDENCY_POLICY` preserves the
existing direct-variable interface.

The policy is ordinary make syntax and may set existing interfaces such as
`DEPENDENCY_PROVIDER_MODE`, `DEPENDENCY_PROVIDER_POLICIES`, target platform
values, validators, and provider environment contributions. GNU make command
line assignments retain precedence over ordinary assignments in the included
file. The framework does not silently discover or auto-load a policy file.

The generic loader belongs to `make/uports`; the selected policy and its group
bindings belong to the parent project. Loading a policy does not move
`BUILD_DEPENDS`, `LIB_DEPENDS`, or `RUN_DEPENDS` out of their individual ports,
and it does not change provider discovery, graph, or provenance ownership.

### System providers

Provider resolution may be extended to let a compatible host or SDK installation
of ncurses, readline, libffi, or another dependency replace a uports build.

System-provider support must be explicit policy, not an automatic name match:

```text
dependency requirement
          |
          +-- selected uports provider
          |
          `-- explicitly selected and validated system provider
```

A system provider may need to validate:

- executable version;
- headers;
- library ABI and architecture;
- compile and link usability;
- runtime identity;
- SDK or sysroot identity;
- host versus target build context.

Host libraries must never be selected accidentally for a cross-compiled target.

The project-level read-only policy boundary is:

```make
DEPENDENCY_PROVIDER_POLICIES += \
  system@target@compiler@linux@amd64@devel/ncurses@linux-base \
  sdk@target@compiler@darwin@arm64@devel/libffi@macos-sdk
```

Each record contains exactly:

```text
kind@context@consumer-group@opsys@arch@dependency-origin@identity
```

`kind` is `system` or `sdk`; uports providers continue to come from selected
build instances rather than policy declarations. `context` is `build` or
`target`, and SDK declarations require `target`. The consumer group is an
existing selected project group. Platform and identity fields are explicit
tokens, and the origin uses `category/port` form. Only one policy may occupy a
given context, consumer-group, operating-system, architecture, and origin key.

### Policy ownership and project scope

The consumer group belongs to the project-level selection binding, not to the
provider definition or identity. A native `pkg-config` command, for example,
does not intrinsically belong to a group named `compiler`; a project may allow
that provider for `compiler`, select a different provider for `host`, and use an
SDK-specific provider for `target`. Group scoping prevents policy intended for
one prefix or toolchain environment from silently leaking into another.

The ownership boundary is:

```text
port metadata                 dependency origin and required interface
provider registry/identity    group-independent validation contract
project provider policy       group-scoped provider selection
selected dependency record    consumer group plus selected provider
```

Group names are project-defined and may differ between projects. Ports and
reusable provider definitions must not hard-code them. Explicit policies name
the current project's groups, while automatic discovery expands successful
providers across the groups present in that project's `groups_all`.

Provider policy is consequently project-owned. The current interface already
supports per-project declarations through `DEPENDENCY_PROVIDER_POLICIES` and
the associated validator and path variables in a project Makefile, included
make fragment, or environment. Validation rejects unknown project groups and
duplicate selection keys. Provider choice remains outside port Makefiles.

Projects do not need separate Linux and macOS policy matrices when automatic
native selection is sufficient:

```make
DEPENDENCY_PROVIDER_MODE = host
```

The active Linux or macOS profile owns command candidates and native prefix
conventions. Platform-specific explicit records are required only when a
project deliberately pins a particular external installation or SDK. That
complexity represents real policy rather than something the framework should
guess.

A standardized project-policy configuration layer remains a useful follow-up
within the dependency workstream. It may define policy-file loading,
composition, portable defaults, platform overrides, source diagnostics, and
migration examples. It is an ergonomics and maintainability project, not a
prerequisite for the existing selection mechanism or native-provider
correctness, and should preserve direct variable declarations for backward
compatibility.

Inspect and validate declarations with:

```sh
make dependency-provider-policy-list
make dependency-provider-policy-check
```

This boundary does not inspect the host, invoke a package manager, select a
provider, or alter dependency records. Debian/RPM, Homebrew, and MacPorts are
installation mechanisms rather than implicit provider identities. A future
external-prefix provider may model Homebrew or MacPorts explicitly, but neither
is treated as the operating system or SDK by this policy.

Provider selection is inspected separately:

```sh
make dependency-provider-selection-list
make dependency-provider-selection-check
```

`BUILD_DEPENDS` records use the build context. `LIB_DEPENDS` and `RUN_DEPENDS`
records use the target context. The default build platform is the planner host;
the target defaults to the build platform.

The established `CROSS_COMPILE` setting is authoritative for cross-build
intent. The dependency planner reads an instance-specific value from its port
environment, falling back to a global command-line/project value, and derives
target architecture and operating system with the same
triplet conventions as `Mk/linux.port.mk`, and retains build dependencies in
the host context. All instances in one consumer group must agree on native
versus cross mode and on the cross triplet because provider policies are keyed
by group. Mixed or unknown group triplets fail before provider selection.

The following variables are optional assertions/overrides, not an independent
way to request a cross build:

```make
DEPENDENCY_BUILD_OPSYS = linux
DEPENDENCY_BUILD_ARCH = x86_64

# Cross intent and target identity come from the port environment.
PORTS_compiler_ENVS += CROSS_COMPILE=arm64-apple-darwin

# Optional consistency assertions.
DEPENDENCY_TARGET_OPSYS.compiler = darwin
DEPENDENCY_TARGET_ARCH.compiler = arm64
```

When supplied, they must match the native platform or the platform derived
from `CROSS_COMPILE`; a mismatch fails closed. A target-context `system`
provider is valid only for a native consumer. A cross consumer must select an
explicit `sdk` provider, including its required sysroot. This prevents host
libraries from satisfying cross-target dependencies merely because their
origin names match.

Cross compiler readiness is a separate boundary from SDK/provider readiness:

```sh
make dependency-cross-toolchain-list
make dependency-cross-toolchain-check
```

For every cross group, these targets derive the tool prefix from
`CROSS_COMPILE` and inspect the commands selected by `Mk/linux.port.mk`:
`gcc`, `g++`, `ld`, `as`, `ar`, `nm`, `objdump`, `ranlib`, and `strip`.
The list target reports each resolved executable path or `missing`; the check
target fails if any command is unavailable. The default set is exposed as
`DEPENDENCY_CROSS_TOOLCHAIN_TOOLS` for explicit project policy.

Dependency-aware execution performs this preflight before dispatching any
provider or consumer. A missing command is named with its consumer group and
cannot be hidden by a later successful recipe. The diagnostic does not install
a toolchain, inspect an SDK, or execute a compiler. Prefer group-specific
`CROSS_COMPILE` environments so host-tool groups remain native; a global value
correctly applies to every selected group because GNU make propagates it to
every recursive port invocation.

A matching external policy fails closed until its identity validates the exact
dependency origin. Validators are explicit project-owned shell checks:

```make
DEPENDENCY_PROVIDER_CHECK.linux-base.devel_ncurses = \
  test -r /usr/include/ncurses.h && \
  pkg-config --exists ncurses
```

The variable name is
`DEPENDENCY_PROVIDER_CHECK.<identity>.<category_port>`, with the slash in the
origin replaced by an underscore. A successful command selects the declared
system or SDK identity for the diagnostic. A missing or failing command reports
`validator-missing` or `validation-failed`; it does not silently fall back to
the uports provider. Policies for a different context, group, operating system,
architecture, or origin do not match and leave normal uports resolution intact.

Before a real build, inspect external-provider readiness without enabling
external dispatch:

```sh
make dependency-provider-readiness-list
make dependency-provider-readiness-check
```

These targets report each matching dependency's validator outcome. Optional
`DEPENDENCY_PROVIDER_READY_HEADER.<identity>.<category_port>`, and corresponding
`_LIBRARY`, `_METADATA`, and `_TOOL` variables name shell checks for individual
build requirements. Each result is `ready`, `missing`, or `unspecified`; a
failed named check is visible even if the overall validator passes. The check
target fails when either the validator or a named probe fails. Named probes are
diagnostic only: they do not select providers, install host packages, or
replace the required overall `DEPENDENCY_PROVIDER_CHECK` validator. For example,
an ncurses provider can check `test -r /usr/include/ncurses.h` for its header
and `pkg-config --exists ncurses` for metadata. A runtime `.so.6` by itself
does not prove that a host can build and link a consumer.

The selection list and readiness targets are diagnostic; opt-in projection and
dispatch are described below.

### Provider-derived build environments

Resolved providers should determine the consumer's:

- include paths and `CPPFLAGS`/`CFLAGS`;
- library paths and `LDFLAGS`;
- runtime search paths;
- `PKG_CONFIG_PATH`;
- executable/tool search path.

Paths must derive from the selected provider kind and identity, rather than the
mere presence of `LIB_DEPENDS`, so a system/SDK provider does not receive uports
destination paths.

The read-only environment boundary uses structured, origin-specific path lists:

```make
DEPENDENCY_PROVIDER_BINDIRS.linux-base.devel_ncurses = /usr/bin
DEPENDENCY_PROVIDER_INCLUDEDIRS.linux-base.devel_ncurses = /usr/include
DEPENDENCY_PROVIDER_LIBDIRS.linux-base.devel_ncurses = /usr/lib
DEPENDENCY_PROVIDER_PKGCONFIGDIRS.linux-base.devel_ncurses = \
  /usr/lib/pkgconfig
DEPENDENCY_PROVIDER_RUNTIMEDIRS.linux-base.devel_ncurses = /usr/lib

DEPENDENCY_PROVIDER_SYSROOT.macos-sdk.devel_libffi = \
  /SDKs/MacOSX.sdk
```

The suffix after `DEPENDENCY_PROVIDER_` is one of `BINDIRS`, `INCLUDEDIRS`,
`LIBDIRS`, `PKGCONFIGDIRS`, `RUNTIMEDIRS`, or `SYSROOT`. The remaining key is
the explicit provider identity and dependency origin, with the origin slash
replaced by an underscore. Path-list order is preserved and duplicate paths
are removed per consumer.

Inspect or validate the derived contribution set with:

```sh
make dependency-provider-environment-list
make dependency-provider-environment-check
```

The diagnostic aggregates all validated external dependencies of each consumer
and reports binary, include, library, pkg-config, runtime, and sysroot paths.
Runtime paths identify `LD_LIBRARY_PATH` for non-Darwin targets and
`DYLD_LIBRARY_PATH` for Darwin targets. A system provider may intentionally
contribute no paths when the compiler and loader use standard system locations.
An SDK provider must declare a sysroot, and different SDK dependencies of one
consumer must not select conflicting sysroots.

These diagnostics do not themselves modify `PATH`, compiler flags, linker
flags, pkg-config variables, runtime variables, or port environments. The
explicit opt-in dispatch described below applies validated contributions.

### Provider usage modes

`DEPENDENCY_PROVIDER_MODE` defines the public provider-selection posture:

```text
uports       use uports providers; this is the default
host         allow validated native host providers, then fall back to uports
system-only  require validated native host providers without uports fallback
explicit     allow explicitly declared system/SDK policies, including cross SDKs
```

Inspect the effective contract with
`dependency-provider-mode-list` or validate it with
`dependency-provider-mode-check`. `host` and `system-only` are native-only;
either mode rejects a group carrying `CROSS_COMPILE`. Cross builds must use
`uports` providers or the `explicit` mode with declared SDK policy. At this
stage, `host` applies validated entries from the native discovery registry and
falls back to uports for unavailable entries. `system-only` applies the same
discovery but fails whenever any selected dependency remains a uports provider.

The older `DEPENDENCY_EXTERNAL_PROVIDERS=yes` interface remains compatible and
selects `explicit` when no mode is given. New callers should select a provider
mode; the detailed policy variables remain the low-level explicit interface.

### Native provider registry

The native-provider registry in `Tools/Providers/registry.mk` is a declarative,
read-only discovery contract.
Each stable entry key names one dependency origin, discovery method,
pkg-config module, required header, and linker name:

```make
DEPENDENCY_PROVIDER_REGISTRY += example
DEPENDENCY_PROVIDER_REGISTRY_ORIGIN.example = devel/example
DEPENDENCY_PROVIDER_REGISTRY_METHOD.example = pkg-config
DEPENDENCY_PROVIDER_REGISTRY_MODULE.example = example
DEPENDENCY_PROVIDER_REGISTRY_HEADER.example = example/example.h
DEPENDENCY_PROVIDER_REGISTRY_LINK_NAME.example = example
```

The initial built-in entries are `devel/ncurses`, `devel/readline`,
`devel/libffi`, and `archivers/zlib`. Entry keys and origins must be unique;
origins, module names, relative header paths, and library names use restricted
non-shell syntax. The only discovery method currently defined is `pkg-config`.
The registry describes the complete interface the discovery engine must
validate; merely finding a library file or similarly named host package is not
sufficient.

### Maintaining the native-provider allowlist

The built-in registry is a conservative allowlist. Finding a `.pc` file,
header, similarly named package, or runtime library must never make an
arbitrary port an automatic system-provider candidate. Adding an origin changes
`host`-mode behavior and therefore requires a separately reviewed provider
slice.

A candidate is suitable only when its complete consumer-facing interface can
be validated reliably. Each proposed origin should establish:

- a stable and understood native interface;
- an unambiguous relationship between the dependency origin and implementation;
- required modules, headers, linker names, and runtime behavior;
- compatible architecture, API, ABI, and version requirements;
- safe normalized include, library, metadata, runtime, and tool paths;
- a valid uports fallback when `host` discovery is unavailable.

Controlled coverage must include success, missing metadata, missing headers,
missing linker names, compile/link failure, unsafe paths, `host` fallback,
`system-only` rejection, and explicit-policy precedence. Promotion to the
built-in registry also requires real consumers on supported host platforms,
including runtime loading, state invalidation, provenance, packaging, and
identical-repeat behavior. Projects may carry additional registry entries
before an interface is proven broad enough for the framework default.

The current registry schema fits simple pkg-config libraries with one required
header and linker name. A provider with version-sensitive APIs, multiple ABI
choices, feature requirements, generated data, or package-specific tools needs
a stronger contract before admission. The schema and probe should be extended
to prove those requirements rather than treating a weak successful link as
equivalence.

`archivers/zlib` illustrates the failure boundary. If the active macOS prefixes
contain no usable `zlib.pc`, native discovery reports the provider unavailable
and `host` mode retains the uports provider. The framework must not weaken that
decision by accepting `libz` file existence alone. Valid alternatives are a
native development installation with suitable metadata, an explicit Apple SDK
provider with its sysroot, or a separately designed and tested non-pkg-config
compile/link discovery method.

Inspect or validate declarations without probing the host:

```sh
make dependency-provider-registry-list
make dependency-provider-registry-check
```

`Tools/Providers/pkg-config.sh` implements the first native discovery method.
The selected `pkg-config` command must resolve to an absolute executable path
and pass its version probe. It is then exposed as a build-context system
provider for `devel/pkg-config`, with its directory contributed to `PATH`.
This permits a compatible system, Homebrew, or MacPorts implementation such as
`pkgconf` to satisfy the command interface without invoking a package manager.
Profile-driven command lookup is restricted to `bin` directories below the
profile's recognized native prefixes. This prevents a previously installed
uports host tool that happens to precede native tools on project `PATH` from
being reclassified as an external system provider. An explicit
`DEPENDENCY_PROVIDER_PKG_CONFIG` path remains an intentional project override.
For each registry entry it requires the module to exist, requires the declared
`-l<link_name>` in the module metadata, and compiles and links a translation
unit including the declared header. Successful records expose normalized
include, library, and pkg-config directories; unsafe paths are rejected.

Inspect all discoveries or require every registered interface to be available:

```sh
make dependency-provider-discovery-list
make dependency-provider-discovery-check
```

Discovery is used for selection only in `host` and `system-only` modes. A
successful native discovery is projected into the existing explicit system
policy and therefore retains the same environment, state, provenance, and
preflight behavior. An unavailable discovery falls back to uports in `host`
mode. `system-only` retains no such fallback. Default `uports` and `explicit`
modes perform no automatic discovery. `DEPENDENCY_PROVIDER_PKG_CONFIG` and
`DEPENDENCY_PROVIDER_CC` may explicitly select the native metadata tool and
compiler; otherwise the active profile supplies ordered command candidates.
An explicit policy for the same context, consumer group, platform, and origin
takes precedence over the automatically discovered provider.

The self-built path remains a first-class alternative. In `uports` mode,
`devel/pkg-config` resolves to the selected uports instance such as
`host_pkg-config`; `host` mode also falls back to that instance when no native
command validates. Native and self-built providers must expose the same command
interface while retaining distinct identities, paths, state, and provenance.
Provider-transition validation must confirm that changing between them
invalidates affected consumers once and that identical repeats remain no-ops.

An explicit identity such as `homebrew-pkgconf` is a project-defined label for
a deliberately selected installation. An automatic identity such as
`macos-pkg-config-arm64` describes the discovery profile, mechanism, and host
architecture; it is not a package name and does not claim that one package
manager owns every discovered library. Concrete bindirs and library/include
paths remain separate state inputs, so changing from a Homebrew path to a
MacPorts path still invalidates affected consumers even when the automatic
identity remains stable.

Platform conventions are isolated in `Tools/Providers/linux.mk` and
`Tools/Providers/macos.mk`. `DEPENDENCY_PROVIDER_PROFILE=auto` selects `linux`
for a Linux build host and `macos` for Darwin; an explicitly named profile must
match the build operating system. Inspect the effective profile with:

```sh
make dependency-provider-profile-list
make dependency-provider-profile-check
```

The Linux profile tries `pkg-config`/`pkgconf`, then `cc`/`gcc`/`clang`, and
recognizes `/usr` and `/usr/local` metadata prefixes. The macOS profile tries
`pkg-config`/`pkgconf`, then `cc`/`clang`, and recognizes `/usr`, `/usr/local`,
`/opt/homebrew`, and `/opt/local`. Existing `lib/pkgconfig` and
`share/pkgconfig` directories below those prefixes are prepended only for the
discovery subprocess. Validated native library directories also enter the
platform loader path for consumer subprocesses, so build-time tools linked to
the discovered provider can run before installation. Darwin consumers also
receive matching linker rpath flags because protected macOS executables may
strip `DYLD_LIBRARY_PATH` between recursive build processes. No Homebrew or
MacPorts command is executed. Successful
identities include profile, mechanism, and architecture, such as
`linux-pkg-config-x86_64` or `macos-pkg-config-arm64`.

Linux fixtures validate candidate selection and real profile selection. macOS
profile, prefix, identity, and environment behavior are covered synthetically;
native Mach-O compilation still requires a real macOS host. Apple target SDKs
remain explicit providers rather than native-host discovery.

The first graph-integration boundary was originally exposed as:

```make
DEPENDENCY_EXTERNAL_PROVIDERS = yes
```

With this setting, policy declarations and matching validators are checked
while normalized dependency records load. A validated system or SDK provider
replaces the selected uports provider in the record: its kind and identity are
retained, `provider_instance` becomes `none`, and resolution remains
`selected`. The project graph and lifecycle plan then omit that record's
uports-provider edge. A failed or missing matching validator stops record
loading; it never falls back silently. Without the opt-in, normalized records
and graph behavior are unchanged.

An opt-in execution plan treats a validated external record as selected but
adds no uports provider target. Its identity and platform remain part of the
normalized record. Before provider dispatch, matching external environments
are validated; an invalid path or SDK state blocks both provider and consumer.

The phase-scoped shell environment can also be inspected and exercised without
running a port phase:

```sh
make DEPENDENCY_EXTERNAL_PROVIDERS=yes \
  DEPENDENCY_REQUEST=compiler@readline.build \
  dependency-provider-environment-export

make DEPENDENCY_EXTERNAL_PROVIDERS=yes \
  DEPENDENCY_REQUEST=compiler@readline.build \
  DEPENDENCY_ENVIRONMENT_COMMAND=env \
  dependency-provider-environment-run
```

The export target emits shell assignments for validated external dependencies
needed by the requested phase. The explicit runner sources those assignments
and invokes the supplied command; it never invokes a port phase implicitly.
Both use the existing policy, validator, and path declarations. Paths must be
absolute, contain no whitespace or shell metacharacters, and contain no `..`
component. Invalid paths, missing SDK sysroots, and conflicting sysroots stop
the runner before its command executes.

Build-context tool directories prepend `PATH`; include directories prepend
`-I` flags to `CPPFLAGS`, `CFLAGS`, and `CXXFLAGS`; library directories prepend
`-L` flags to `LDFLAGS`; pkg-config directories prepend `PKG_CONFIG_PATH`.
An SDK contributes `SDKROOT`, `PKG_CONFIG_SYSROOT_DIR`, and a
platform-appropriate sysroot flag to `CPPFLAGS`, `CFLAGS`, `CXXFLAGS`, and
`LDFLAGS`. Linux-style targets use `--sysroot=<path>`; Darwin-style targets use
`-isysroot <path>`. The declared include, library, and pkg-config paths remain
explicit alongside the sysroot. Project-owned validators are responsible for
checking that the declared SDK layout and required tools actually exist.
Native runtime directories prepend `LD_LIBRARY_PATH` or
`DYLD_LIBRARY_PATH`. For a cross target, they are recorded only in
`UPORTS_TARGET_RUNTIME_DIRS`, never applied to the host loader. Existing values
are retained after provider contributions. Runtime-only dependencies are omitted
from configure/build requests and included from stage onward.

With both `UPORTS_DEPENDENCIES=yes` and `DEPENDENCY_EXTERNAL_PROVIDERS=yes`,
canonical and aggregate dispatch execute only remaining uports provider
targets. Each port subprocess receives its own validated, phase-scoped
external environment. Uports provider subprocesses also retain dependency
state checking, so a transitive external-provider change can invalidate the
provider's cookies before use. The consumer is dispatched only after provider
preflight and execution succeed; the last successful state is saved only after
the consumer succeeds.

For `LIB_DEPENDS` fulfilled entirely by external providers, the port layer
omits the otherwise automatic uports `DESTDIR/PREFIX` include, library, and
Darwin runtime-search paths. Mixed external/uports library dependencies retain
those uports paths for the selected uports libraries. Without explicit external
opt-in, port behavior is unchanged.

### Provider provenance

Before package-manifest integration, the planner exposes deterministic provider
provenance for a scoped request:

```sh
make DEPENDENCY_REQUEST=compiler@readline.package \
  dependency-provider-provenance
```

The versioned, line-oriented report records the requested instance and phase,
then each selected dependency in provider-first closure order. Every provider
record includes its consumer, dependency type and requirement, origin, provider
kind and identity, build/target context, operating system, architecture, and
either the uports lifecycle target or `external`. Uports identities are logical
instance keys; system and SDK identities are the explicitly declared policy
identities. Runtime dependencies appear for package/stage/install requests but
not configure/build requests. The report is read-only and deterministic. It is
also the input boundary for package-manifest embedding.

When dependency-aware wrapper dispatch runs a canonical `.package` target, it
passes the scoped report to the port package creator. Such packages use uports
package format `PVER: 2` and contain a delimited `PROVENANCE` block before the
plist. The package reader locates both blocks by exact delimiter lines, accepts
PVER 1 packages without provenance, and installs their payloads unchanged.
Dependency-neutral direct port packaging continues to emit PVER 1. Temporary
provenance files exist only for the duration of the consumer subprocess and do
not become port source or work-state inputs.

This metadata describes what was selected when the artifact was produced. It
does not cause package installation to provision a system/SDK provider, and it
does not convert an external provider into a packaged uports dependency.

### Provider identity and state invalidation

Changing a dependency from one provider to another must invalidate the
consumer's configure/build state. Consumer cookies or state signatures should
therefore include provider kind, identity, and relevant environment information.

The project planner exposes the normalized input to that signature for a
scoped canonical request:

```sh
make DEPENDENCY_REQUEST=compiler@cpython.build dependency-execution-state
```

The report is ordered deterministically and records the requested consumer
phase, every instance in its selected transitive closure, each instance's
effective group, origin, and environment, and every selected dependency's type,
requirement, origin, provider kind, identity or instance, and provider
lifecycle target when applicable. External records additionally include their
context, operating system, architecture, and declared environment paths. It is
inspectable text rather than an opaque digest. Cookie comparison and
invalidation consume this boundary; merely inspecting it does not modify a
port work directory.

A port can compare or explicitly save such a report beside its work cookies.
These are internal per-port targets, so invoke them from the selected port
directory with the same environment used for that build, not from the project
root:

```sh
make -C feeds/textproc/json-c \
  PORTSDIR="$PWD/make/uports" \
  DESTDIR="$PWD/local/compiler" PREFIX=/usr/local \
  TYPE_SUFFIX=.textproc \
  DEPENDENCY_STATE_CLASS=configure \
  DEPENDENCY_STATE_SOURCE=/path/to/current.state \
  uports-dependency-state-check

make -C feeds/textproc/json-c \
  PORTSDIR="$PWD/make/uports" \
  DESTDIR="$PWD/local/compiler" PREFIX=/usr/local \
  TYPE_SUFFIX=.textproc \
  DEPENDENCY_STATE_CLASS=configure \
  DEPENDENCY_STATE_SOURCE=/path/to/current.state \
  uports-dependency-state-save
```

`DEPENDENCY_STATE_CLASS` is `configure` or `stage`. The default saved path is
`$(WRKDIR)/dependency.<class>.state`. Checking reports `new`, `unchanged`, or
`changed` and never writes the saved state. Saving reports the same comparison
and atomically replaces new or changed state; unchanged state is not rewritten.
These internal port targets do not remove cookies.

Phase-aware invalidation is a separate explicit per-port action:

```sh
make -C feeds/textproc/json-c \
  PORTSDIR="$PWD/make/uports" \
  DESTDIR="$PWD/local/compiler" PREFIX=/usr/local \
  TYPE_SUFFIX=.textproc \
  DEPENDENCY_STATE_CLASS=configure \
  DEPENDENCY_STATE_SOURCE=/path/to/current.state \
  uports-dependency-state-invalidate
```

An unchanged comparison preserves every cookie. New or changed `configure`
state removes the configure, build, stage, package, and install cookies while
preserving fetch, extract, and patch state. New or changed `stage` state removes
only the stage, package, and install cookies. Both classes also remove the
derived work-package file so a later package target cannot reuse bytes carrying
stale provider provenance. An already published package is retained until the
replacement is built and copied successfully. Invalidation does not save the
new state, so a failed lifecycle retry continues to compare against the last
successfully saved identity.

Project dispatch integrates this boundary through project-root commands based
on `DEPENDENCY_REQUEST`: `dependency-state-check`,
`dependency-state-invalidate`, and `dependency-state-save`. Each accepts one
canonical request, generates its current state in a temporary file, and invokes
the corresponding internal target in the consumer port with the selected build
instance environment.

With `UPORTS_DEPENDENCIES=yes`, canonical dispatch executes providers, performs
phase-aware invalidation, runs the consumer, and saves state only after the
consumer succeeds. A consumer failure therefore retains the last successful
state. Aggregate dispatch executes the union of providers once, then enables
the same state boundary independently for each dependency-neutral consumer.
Fetch, extract, and patch requests do not participate because provider state
does not invalidate those source phases.

### Invocation-scoped metadata reuse

A dependency-aware canonical or aggregate target owns one temporary metadata
snapshot for its complete nested execution. The outer invocation collects and
validates port dependency metadata once, then passes the read-only snapshot to
provider planning, consumer environment generation, state invalidation and
saving, and package provenance submakes. The snapshot is removed when the
outer invocation succeeds or fails.

This boundary is deliberately not a persistent cache. A later user command
always collects fresh metadata, so edits to port dependency declarations and
capabilities are visible without timestamps, invalidation rules, or cache
management. Nested makes accept `DEPENDENCY_METADATA_SOURCE` only while the
internal `UPORTS_DEPENDENCY_INVOCATION=yes` marker is present. Ordinary
diagnostic targets and dependency-neutral execution retain their previous
behavior.

`dependency-metadata-snapshot` exposes the deterministic raw snapshot for
controlled testing. Canonical and aggregate regression fixtures verify exactly
one collection per outer invocation and cleanup of the temporary invocation
directory. On the 2026-10-02 Linux validation host, a fresh scoped state query
took 2.75 seconds; collection took 2.45 seconds, while state, environment, and
provenance queries reusing that snapshot took 0.34, 0.18, and 0.33 seconds.
On the validated Darwin arm64 host, the corresponding steady warm no-op build
and package timings were 12.72 and 14.14 seconds, reduced from 34.54 and 44.33
seconds before invocation-scoped reuse. This satisfied the performance gate for
default dependency-aware dispatch.

### Parallel provider scheduling

Provider execution is serialized to preserve correctness. Independent branches
of the provider graph may execute concurrently only with edge-aware scheduling
and deterministic failure behavior. Parallel scheduling is an optimization, not
a correctness requirement.
