# uports Dependency Handling Architecture and Design

## Purpose

This document defines the dependency-handling architecture for the core uports
framework. Live checkout details, verification results, work status, and next
steps belong in `../HANDOFF.md`.

The framework follows two ownership rules:

- ports declare dependency intent and explicit capabilities;
- the project wrapper resolves providers, validates policy, orders instances,
  and dispatches lifecycle targets.

## Architecture Overview

```text
Port Makefiles
  BUILD_DEPENDS / LIB_DEPENDS / RUN_DEPENDS / PORT_PROVIDES
                              |
                              v
+-------------------------------------------------------------------+
| 1. Metadata collection                                            |
|                                                                   |
| Probe every selected build instance. Probes run concurrently,     |
| while collected output is restored to deterministic planner order.|
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 2. Normalized dependency records                                  |
|                                                                   |
| consumer, type, requirement, logical origin, optional target,     |
| provider kind, provider instance, resolution state                |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 3. Provider resolution                                            |
|                                                                   |
| exact provider in consumer group                                  |
|   -> PORT_PROVIDES capability in consumer group                   |
|   -> one unique selected provider across groups                   |
|   -> explicit unresolved state                                    |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 4. Selected-instance dependency graph                             |
|                                                                   |
| declaration: consumer ----------> provider                        |
| ordering:    provider must complete before consumer               |
|                                                                   |
| Unresolved records stay visible. Cycles are rejected.             |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 5. Provider-first ordering                                        |
|                                                                   |
| Deterministic topological order; planner order breaks ties.       |
| Shared consumer/provider pairs are deduplicated for ordering      |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 6. Lifecycle prerequisite plan                                    |
|                                                                   |
| BUILD_DEPENDS, LIB_DEPENDS: provider before consumer.configure    |
| RUN_DEPENDS:                provider before consumer.stage        |
| Default provider target:    provider.install                      |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 7. Scoped execution planning                                      |
|                                                                   |
| canonical/alias target -> one transitive closure                  |
| category/group/ports.* -> union of multiple closures              |
|                                                                   |
| Validate the relevant union and deduplicate shared providers.     |
+-----------------------------+-------------------------------------+
                              |
                              v
+-------------------------------------------------------------------+
| 8. Opt-in execution                                               |
|                                                                   |
| UPORTS_DEPENDENCIES=yes                                           |
|   1. execute provider targets in deterministic order              |
|   2. dispatch consumers after all providers complete              |
|   3. allow consumer parallelism through the parent jobserver      |
+-------------------------------------------------------------------+
```

## Terminology

### Dependency

A dependency is a requirement declared by a consumer port. For example:

```make
LIB_DEPENDS += libssl.so:security/openssl
```

The declaration contains the required artifact and logical origin. It does not
by itself select a particular build instance.

### Provider

A provider is the selected build instance that satisfies a dependency. A record
may therefore resolve as:

```text
consumer:          compiler_cpython
type:              lib
requirement:       libssl.so
origin:            security/openssl
provider_instance: compiler_openssl
resolution:        selected
```

Dependency records retain the declaration direction `consumer -> provider`.
Execution reverses the precedence: the provider must complete before its
consumer.

### Capability

`PORT_PROVIDES` explicitly states that a selected port can satisfy an additional
logical origin:

```make
PORT_PROVIDES += devel/autoconf
```

Capabilities are provider-owned metadata. They do not silently rename ports and
do not assert equivalence between unrelated implementations.

## Ownership Boundary

Dependency handling is not a new dependency language invented by uports.
`BUILD_DEPENDS`, `LIB_DEPENDS`, `RUN_DEPENDS`, and the corresponding lifecycle
concepts originate in FreeBSD Ports. uports inherited those declarations, but
its dependency targets were effectively empty before the work described here:

```make
build-depends:
lib-depends:
run-depends:
```

The recent work therefore implements a previously missing capability while
preserving the FreeBSD-compatible declaration model.

That does not mean dependency handling has no relationship with the uports
project planner. The ownership is split across two levels:

```text
Per-port FreeBSD-compatible layer
  port Makefile + Mk/linux.port.mk
  - declare BUILD_DEPENDS, LIB_DEPENDS, and RUN_DEPENDS
  - export dependency and capability metadata
  - define when dependency types are needed in one port's lifecycle
                              |
                              v
Project-level uports planner
  Tools dependency planner + target dispatcher
  - select concrete providers from active build instances
  - apply group, variant, host/target, and project policy
  - reject ambiguous or unresolved providers
  - construct and validate the selected-instance graph
  - order and deduplicate providers across aggregate consumers
  - dispatch providers and consumers
```

An individual port cannot determine which project instance should satisfy a
logical origin. For example:

```make
LIB_DEPENDS += libssl.so:security/openssl
```

does not say whether the selected provider is `host_openssl`,
`compiler_openssl`, `target_openssl`, or a future validated system/SDK provider.
That decision depends on active groups, selected instances, cross-build context,
and project policy, so it belongs above the per-port framework.

### Relationship with `Tools/tools.mk`

`Tools/tools.mk` is currently both the project planner and the integration point
for dependency handling. A relationship is necessary because that file owns
selected groups, build instances, aggregate targets, environments, and lifecycle
dispatch. However, the dependency algorithms do not need to remain physically
embedded in the already-large file.

A cleaner target structure is:

```text
Mk/linux.port.mk
  FreeBSD-compatible declarations, metadata export, lifecycle hooks

Tools/tools.mk
  project planner and dependency integration point
          |
          `-- include Tools/dependency.mk
                normalized records
                provider resolution
                graph/lifecycle input
                validation and execution targets

Tools/dependency-graph.awk
  graph validation and deterministic ordering

Tools/dependency-execution.awk
  scoped and multi-root execution planning
```

In this model, `Tools/tools.mk` still integrates dependency planning, but the
dependency implementation becomes a focused module. This separation should be
completed before default enablement or system-provider work makes the planner
larger.

## Component Design

### Metadata export and normalization

`Mk/linux.port.mk` exports dependency metadata through
`uports-dependency-metadata`. `Tools/tools.mk` converts it into normalized,
inspectable records for `BUILD_DEPENDS`, `LIB_DEPENDS`, and `RUN_DEPENDS`.

Resolution states are:

```text
selected
unselected
ambiguous
unknown-origin
```

Ordinary planner startup does not collect dependency metadata. Collection occurs
only when dependency diagnostics, validation, or execution planning needs it.

### Parallel deterministic collection

Metadata probes use a bounded recursive make:

```make
DEPENDENCY_METADATA_JOBS ?= 4
```

Every probe writes an isolated temporary result. Results are concatenated in
planner-instance order, failures are fatal, and temporary data is removed. No
persistent dependency cache or generated graph is stored in the repository.

### Deterministic provider resolution

Provider selection uses this precedence:

1. exact selected origin in the consumer group;
2. one explicit capability provider in the consumer group;
3. one unique exact or capability provider across selected groups;
4. otherwise report `unselected`, `ambiguous`, or `unknown-origin`.

The resolver does not guess that differently named origins are equivalent.

### Dependency graph and ordering

The graph is generated dynamically from current selected instances and current
port metadata. It supports:

- typed edges for build, library, and runtime dependencies;
- unresolved-record visibility;
- deterministic cycle detection;
- downstream blocked-node reporting;
- provider-first topological ordering;
- isolated selected instances;
- planner-order tie breaking.

Available commands include:

```sh
make dependencies-list
make dependency-graph-list
make dependency-order-list
make dependencies-check
```

### Lifecycle mapping

Resolved records map to dispatchable group-qualified wrapper targets:

```text
build, lib: consumer.configure <- provider.install
run:        consumer.stage     <- provider.install
```

An explicit dependency target replaces the default provider `install` target,
but it must be a supported forward lifecycle target. Destructive targets such as
`clean`, `deinstall`, and `uninstall` are not accepted as dependency provider
targets.

Inspection and validation commands are:

```sh
make dependency-lifecycle-list
make dependency-lifecycle-check
```

### Target-scoped execution

A canonical target or unambiguous alias can be planned independently:

```sh
make \
  DEPENDENCY_REQUEST=compiler@cpython.build \
  dependency-execution-plan
```

Phase filtering is applied to the root request:

| Requested phase | Direct dependency types traversed |
| --- | --- |
| fetch, extract, patch | none |
| configure, build, rebuild | build and lib |
| stage, package, install, restage, reinstall, generate-plist | build, lib, and run |

Transitive providers are evaluated according to the lifecycle target requested
for that provider.

### Multi-root aggregate execution

When dependency execution is enabled, category, group, and `ports.*` aggregate
targets produce one union of all consumer closures. The implementation:

1. validates the complete relevant union before dispatch;
2. deduplicates shared providers;
3. completes provider targets in deterministic order;
4. invokes a dependency-neutral recursive make for consumers;
5. permits consumers to use the inherited jobserver only after providers finish.

This also handles a requested consumer that is simultaneously a provider for
another requested consumer: its provider phase still completes before the
consumer batch begins.

### Opt-in lifecycle integration

Dependency-aware dispatch is currently enabled explicitly:

```sh
make UPORTS_DEPENDENCIES=yes compiler@cpython.build
make UPORTS_DEPENDENCIES=yes compiler.build
```

Accepted policy values are `yes` and `no`. Recursive provider dispatch forces
`UPORTS_DEPENDENCIES=no` because the parent execution planner has already
calculated and ordered the complete closure.

Provider dispatch is deliberately `-j1` today. This guarantees the inspected
topological order. Consumer dispatch may be parallel after provider preparation.

## Important Commands

### Read-only inspection

```sh
make dependencies-list
make dependency-graph-list
make dependency-order-list
make dependency-lifecycle-list
make DEPENDENCY_REQUEST=compiler@cpython.build dependency-execution-plan
```

### Validation

```sh
make dependencies-check
make dependency-lifecycle-check
make -C make/uports/Tools/tests check
```

Run project dependency validation from the project root whose selected groups
and feeds define the complete provider set. Running the same target directly in
the framework repository validates only its standalone example selection, which
may intentionally report origins supplied by a parent project as unresolved.

### Execution

The following commands perform real provider lifecycle work:

```sh
make dependency-lifecycle-execute
make UPORTS_DEPENDENCIES=yes compiler@cpython.build
make UPORTS_DEPENDENCIES=yes compiler.build
```

Do not use execution commands merely to inspect the plan. Use
`dependency-execution-plan` or replace `DEPENDENCY_EXECUTE_COMMAND` with a
recorder.

## Design Extensions

### Extract the dependency planner module

Dependency declarations and per-port lifecycle semantics belong to the
FreeBSD-compatible layer, while provider selection and build-instance ordering
belong to the uports project planner. The current implementation is correct at
that ownership boundary. The source layout should express the same separation
instead of embedding project-level dependency logic in `Tools/tools.mk`.

Extract the focused logic into a file such as `Tools/dependency.mk`, included by
`Tools/tools.mk`. Preserve behavior and tests during the move; this should be a
structural refactor, not a redesign of record or execution semantics.

### Default enablement policy

The current default remains:

```make
UPORTS_DEPENDENCIES ?= no
```

Default enablement should require validated behavior across transitive and shared
providers, build and runtime phases, interruption and restart, provider cookies,
failures, parallel aggregates, and the rebuild, restage, reinstall, and package
workflows.

### System providers

Provider resolution may be extended to let a compatible host or SDK installation
of ncurses, readline, libffi, or another dependency replace a uports build.

System-provider support must be explicit policy, not an automatic name match:

```text
dependency requirement
          |
          +-- selected uports provider
          |
          `-- explicitly selected and validated system provider
```

A system provider may need to validate:

- executable version;
- headers;
- library ABI and architecture;
- compile and link usability;
- runtime identity;
- SDK or sysroot identity;
- host versus target build context.

Host libraries must never be selected accidentally for a cross-compiled target.

The project-level read-only policy boundary is:

```make
DEPENDENCY_PROVIDER_POLICIES += \
  system@target@compiler@linux@amd64@devel/ncurses@linux-base \
  sdk@target@compiler@darwin@arm64@devel/libffi@macos-sdk
```

Each record contains exactly:

```text
kind@context@consumer-group@opsys@arch@dependency-origin@identity
```

`kind` is `system` or `sdk`; uports providers continue to come from selected
build instances rather than policy declarations. `context` is `build` or
`target`, and SDK declarations require `target`. The consumer group is an
existing selected project group. Platform and identity fields are explicit
tokens, and the origin uses `category/port` form. Only one policy may occupy a
given context, consumer-group, operating-system, architecture, and origin key.

Inspect and validate declarations with:

```sh
make dependency-provider-policy-list
make dependency-provider-policy-check
```

This boundary does not inspect the host, invoke a package manager, select a
provider, or alter dependency records. Debian/RPM, Homebrew, and MacPorts are
installation mechanisms rather than implicit provider identities. A future
external-prefix provider may model Homebrew or MacPorts explicitly, but neither
is treated as the operating system or SDK by this policy.

Provider selection is inspected separately:

```sh
make dependency-provider-selection-list
make dependency-provider-selection-check
```

`BUILD_DEPENDS` records use the build context. `LIB_DEPENDS` and `RUN_DEPENDS`
records use the target context. The default build platform is the planner host;
the target defaults to the build platform. Cross builds must override the
target identity globally or for an individual consumer group:

```make
DEPENDENCY_BUILD_OPSYS = linux
DEPENDENCY_BUILD_ARCH = x86_64
DEPENDENCY_TARGET_OPSYS = darwin
DEPENDENCY_TARGET_ARCH = arm64

# Optional group-specific target identity.
DEPENDENCY_TARGET_OPSYS.compiler = darwin
DEPENDENCY_TARGET_ARCH.compiler = arm64
```

A matching external policy fails closed until its identity validates the exact
dependency origin. Validators are explicit project-owned shell checks:

```make
DEPENDENCY_PROVIDER_CHECK.linux-base.devel_ncurses = \
  test -r /usr/include/ncurses.h && \
  pkg-config --exists ncurses
```

The variable name is
`DEPENDENCY_PROVIDER_CHECK.<identity>.<category_port>`, with the slash in the
origin replaced by an underscore. A successful command selects the declared
system or SDK identity for the diagnostic. A missing or failing command reports
`validator-missing` or `validation-failed`; it does not silently fall back to
the uports provider. Policies for a different context, group, operating system,
architecture, or origin do not match and leave normal uports resolution intact.

This selection diagnostic remains non-integrating: it does not yet replace
dependency graph edges, suppress a uports provider build, or contribute paths
to a consumer environment. Those effects require the following environment and
execution-integration stages.

### Provider-derived build environments

Resolved providers should determine the consumer's:

- include paths and `CPPFLAGS`/`CFLAGS`;
- library paths and `LDFLAGS`;
- runtime search paths;
- `PKG_CONFIG_PATH`;
- executable/tool search path.

Paths must derive from the selected provider kind and identity, rather than the
mere presence of `LIB_DEPENDS`, so a system/SDK provider does not receive uports
destination paths.

The read-only environment boundary uses structured, origin-specific path lists:

```make
DEPENDENCY_PROVIDER_BINDIRS.linux-base.devel_ncurses = /usr/bin
DEPENDENCY_PROVIDER_INCLUDEDIRS.linux-base.devel_ncurses = /usr/include
DEPENDENCY_PROVIDER_LIBDIRS.linux-base.devel_ncurses = /usr/lib
DEPENDENCY_PROVIDER_PKGCONFIGDIRS.linux-base.devel_ncurses = \
  /usr/lib/pkgconfig
DEPENDENCY_PROVIDER_RUNTIMEDIRS.linux-base.devel_ncurses = /usr/lib

DEPENDENCY_PROVIDER_SYSROOT.macos-sdk.devel_libffi = \
  /SDKs/MacOSX.sdk
```

The suffix after `DEPENDENCY_PROVIDER_` is one of `BINDIRS`, `INCLUDEDIRS`,
`LIBDIRS`, `PKGCONFIGDIRS`, `RUNTIMEDIRS`, or `SYSROOT`. The remaining key is
the explicit provider identity and dependency origin, with the origin slash
replaced by an underscore. Path-list order is preserved and duplicate paths
are removed per consumer.

Inspect or validate the derived contribution set with:

```sh
make dependency-provider-environment-list
make dependency-provider-environment-check
```

The diagnostic aggregates all validated external dependencies of each consumer
and reports binary, include, library, pkg-config, runtime, and sysroot paths.
Runtime paths identify `LD_LIBRARY_PATH` for non-Darwin targets and
`DYLD_LIBRARY_PATH` for Darwin targets. A system provider may intentionally
contribute no paths when the compiler and loader use standard system locations.
An SDK provider must declare a sysroot, and different SDK dependencies of one
consumer must not select conflicting sysroots.

These records are inputs to later execution integration. At this stage they do
not modify `PATH`, compiler flags, linker flags, pkg-config variables, runtime
variables, or port environments.

The first graph-integration boundary is opt-in:

```make
DEPENDENCY_EXTERNAL_PROVIDERS = yes
```

With this setting, policy declarations and matching validators are checked
while normalized dependency records load. A validated system or SDK provider
replaces the selected uports provider in the record: its kind and identity are
retained, `provider_instance` becomes `none`, and resolution remains
`selected`. The project graph and lifecycle plan then omit that record's
uports-provider edge. A failed or missing matching validator stops record
loading; it never falls back silently. Without the opt-in, normalized records
and graph behavior are unchanged.

Execution and dependency-state targets deliberately reject an opt-in plan
containing external-provider records until path injection and dispatch
integration are complete. This prevents a consumer from running with a missing
uports edge but without the selected external provider's build environment.

### Provider identity and state invalidation

Changing a dependency from one provider to another must invalidate the
consumer's configure/build state. Consumer cookies or state signatures should
therefore include provider kind, identity, and relevant environment information.

The project planner exposes the normalized input to that future signature for a
scoped canonical request:

```sh
make DEPENDENCY_REQUEST=compiler@cpython.build dependency-execution-state
```

The report is ordered deterministically and records the requested consumer
phase, every instance in its selected transitive closure, each instance's
effective group, origin, and environment, and every selected dependency's type,
requirement, origin, provider kind, provider instance, and provider lifecycle
target. It is intentionally inspectable text rather than an opaque digest.
Cookie comparison and invalidation consume this boundary in a later slice;
merely inspecting the state does not modify a port work directory.

A port can compare or explicitly save such a report beside its work cookies.
These are internal per-port targets, so invoke them from the selected port
directory with the same environment used for that build, not from the project
root:

```sh
make -C feeds/textproc/json-c \
  PORTSDIR="$PWD/make/uports" \
  DESTDIR="$PWD/local/compiler" PREFIX=/usr/local \
  TYPE_SUFFIX=.textproc \
  DEPENDENCY_STATE_CLASS=configure \
  DEPENDENCY_STATE_SOURCE=/path/to/current.state \
  uports-dependency-state-check

make -C feeds/textproc/json-c \
  PORTSDIR="$PWD/make/uports" \
  DESTDIR="$PWD/local/compiler" PREFIX=/usr/local \
  TYPE_SUFFIX=.textproc \
  DEPENDENCY_STATE_CLASS=configure \
  DEPENDENCY_STATE_SOURCE=/path/to/current.state \
  uports-dependency-state-save
```

`DEPENDENCY_STATE_CLASS` is `configure` or `stage`. The default saved path is
`$(WRKDIR)/dependency.<class>.state`. Checking reports `new`, `unchanged`, or
`changed` and never writes the saved state. Saving reports the same comparison
and atomically replaces new or changed state; unchanged state is not rewritten.
These internal port targets do not remove cookies.

Phase-aware invalidation is a separate explicit per-port action:

```sh
make -C feeds/textproc/json-c \
  PORTSDIR="$PWD/make/uports" \
  DESTDIR="$PWD/local/compiler" PREFIX=/usr/local \
  TYPE_SUFFIX=.textproc \
  DEPENDENCY_STATE_CLASS=configure \
  DEPENDENCY_STATE_SOURCE=/path/to/current.state \
  uports-dependency-state-invalidate
```

An unchanged comparison preserves every cookie. New or changed `configure`
state removes the configure, build, stage, package, and install cookies while
preserving fetch, extract, and patch state. New or changed `stage` state removes
only the stage, package, and install cookies. Invalidation does not save the new
state, so a failed lifecycle retry continues to compare against the last
successfully saved identity.

Project dispatch integrates this boundary through project-root commands based
on `DEPENDENCY_REQUEST`: `dependency-state-check`,
`dependency-state-invalidate`, and `dependency-state-save`. Each accepts one
canonical request, generates its current state in a temporary file, and invokes
the corresponding internal target in the consumer port with the selected build
instance environment.

With `UPORTS_DEPENDENCIES=yes`, canonical dispatch executes providers, performs
phase-aware invalidation, runs the consumer, and saves state only after the
consumer succeeds. A consumer failure therefore retains the last successful
state. Aggregate dispatch executes the union of providers once, then enables
the same state boundary independently for each dependency-neutral consumer.
Fetch, extract, and patch requests do not participate because provider state
does not invalidate those source phases.

### Parallel provider scheduling

Provider execution is serialized to preserve correctness. Independent branches
of the provider graph may execute concurrently only with edge-aware scheduling
and deterministic failure behavior. Parallel scheduling is an optimization, not
a correctness requirement.
